UME 实现思路

回鹘蒙文编辑器（Uyghur-Mongolian Editor）前端预览的实现记录 —— 每个决策的依据、走过的弯路，以及可复核的证据。

0一页速览

蒙文排版的难点不在"把字画出来"，而在三件事：列往哪边走、字形由谁决定、 不要手贱去干预成形。第三条是本次最大的教训。

vertical-lr
蒙文竖排取值（不是 vertical-rl）
2.90 em
ᠮᠣᠩᠭᠣᠯ 正确成形的整词宽度
4.81 em
错误干预后的宽度（连字丢失）

核心结论

  1. writing-mode: vertical-lr 是蒙文正确取向；vertical-rl 是 CJK 用的，会让列序反掉。
  2. 绝对不要写 font-feature-settings 去打开 init/medi/fina/isol—— 会把每个字母钉成孤立形，覆盖 rclt 的上下文连字。默认交给排版引擎即可。
  3. "把文本框顺时针旋转 90°"是等效方案，但旋转后的包围盒落在负坐标区，需要 translateX(100%) 校正，且文本 width 要取容器高度。
  4. 可靠性来自可量化的判据（整词宽度 em 值、HarfBuzz 字形名对拍），不是肉眼。

1问题与约束

目标：一个能在浏览器里输入、显示、核对蒙文的预览工具，并且能验证字体自身的连字能力。 约束几乎全部来自蒙文本身的特性。

约束内容对实现的直接影响
竖排、列自左向右 传统蒙文自上而下书写，新列出现在右侧 CSS 用 vertical-lr；且必须显式 direction:ltr
字形由上下文决定 同一码位在词首/词中/词尾/单独是四个不同字形 不能按码位画图，必须交给 GSUB；编辑器不得插手
连字是常态 字体有 1944 个连字；rclt 以 44 条链式上下文规则驱动连写 关掉 rclt 蒙文立刻变错
不用空格分词 字母 LB=AL，AL × AL 禁止断行 长词在竖排中是不可断整体，换列算法要处理
不可见控制符 FVS1–4、U+180E 等 Default_Ignorable 渲染不可见却改变前一字形，面板要标出来
字体无竖排度量 缺 vhea/vmtx 不能依赖字体竖排度量，须由浏览器/旋转负责

为什么要"零依赖单文件"

只用 file:// 双击打开就能跑：字体经 @font-face 以相对路径 ../font/NotoSansMongolian-Regular.ttf 加载，无构建、无包管理、无服务器。 这样它既是预览工具，也是可长期保存的最小可运行样本。

2渲染分层：谁负责什么

蒙文从键盘到屏幕要穿过四层。搞清楚每层的职责边界，才知道哪些事该自己做、 哪些事必须放手 —— 我最初的错误正是越界干预了第 ③ 层。

越界的代价

第 ③ 层的规则是"上下文驱动"的：某个字母取哪个字形，取决于它前后是谁。 如果你在第 ③ 层外面用 CSS 强行指定"请使用首形/中形/尾形"，等于把上下文信息扔掉， 引擎只能退回孤立形。这就是后来连字全丢的根因。

3三个关键决策

3.1 竖排取向：vertical-lr

依据 W3C i18n《Styling vertical Chinese, Japanese, Korean and Mongolian text》：

use vertical-rl for Chinese/Japanese/Korean (lines top-to-bottom; columns progress right-to-left) and vertical-lr for Mongolian (columns progress left-to-right)

关键区别在列的增长方向。下图是同一段文字在两种取值下的实际渲染 （每列从左到右依次是 ᠮᠣᠩᠭᠣᠯ ᠪᠢᠴᠢᠭ ᠤᠨ ᠲᠣᠯᠢ）：

正确 writing-mode: vertical-lr — 列自左向右
ᠮᠣᠩᠭᠣᠯ ᠪᠢᠴᠢᠭ ᠤᠨ ᠲᠣᠯᠢ
错误 writing-mode: vertical-rl — 列自右向左（CJK 取向）
ᠮᠣᠩᠭᠣᠯ ᠪᠢᠴᠢᠭ ᠤᠨ ᠲᠣᠯᠢ

两者字形相同，差别只在列的生长方向：vertical-lr 第一列在最左， vertical-rl 第一列在最右 —— 后者会让蒙文阅读顺序整体倒转。

配套的两点

  • 必须显式写 direction: ltr：否则在 RTL 上下文里继承 rtl，列序会被再翻一次。
  • 不要设 text-orientation: upright：U+1800–U+18AA 全部 171 个码位的 Vertical_Orientation 属性都是 R（rotated）， 浏览器会自动顺时针转 90°，保持默认 mixed 即可。

3.2 成形不可干预 —— 最贵的一课

我最初写下这行"保险"代码，结果把整个成形毁掉了：

/* ❌ 曾经的错误写法 */
font-feature-settings:"rclt" 1,"ccmp" 1,"init" 1,"medi" 1,"fina" 1,"isol" 1;

/* ✅ 正确做法：什么都不写 */

看起来只是"确保特性被启用"，实际相反。下面是 HarfBuzz 对同一个 ᠮᠣᠩᠭᠣᠯ 在两种设置下选出的真实字形（数据由 tools/extract_process_data.py 从字体导出）：

默认（正确）
ᠮᠣᠩᠭᠣᠯ
5 个字形 / 6 个码位
总宽 2900 单位 = 2.90 em
含连字 u182D_u1823.GO.medi
强制打开位置特性
ᠮᠣᠩᠭᠣᠯ
6 个字形（无连字）
总宽 4810 单位 = 4.81 em
全部退化为 .init._isol 孤立形

宽度差 66%：连字丢失后每个字母各自成形，整词被拉长。这里用浏览器现场渲染字体， 上面两栏的差异是真实的（右栏通过 .ffx-bad 类复现当年的 bug）。

为什么会这样

蒙文的连写形态由 rclt（Required Contextual Ligatures）按上下文逐段判定。 把 init/medi/fina/isol 强制置 1， 等于告诉引擎"每个字母都按孤立形处理"，rclt 的链式上下文规则被覆盖， 连字（如 ᠭ+ᠣ → u182D_u1823.GO.medi）全部丢失。

正确姿势

HarfBuzz 对 script=mong 默认已启用正确的特性集合。 CSS 里不写 font-feature-settings，浏览器解析值为 normal， 成形就是对的。需要对照排查时，才用类去关闭特性（本页与编辑器都保留了这个开关）。

3.3 旋转方案（rotate(90deg)）的几何

"把文本框顺时针旋转 90°"是等效且直观的做法。它与 vertical-lr 输出一致 —— 实测两者墨迹像素数完全相同（78,954）。但旋转有三个容易踩的几何问题。

问题一：旋转后包围盒落在负坐标区

设元素横排时宽 w、高 h。以 transform-origin: top left 顺时针转 90°，局部点 (x,y) 映射为 (−y, x)，于是包围盒落在：

x ∈ [−h, 0]      ← x 是负的，内容跑到容器左侧外面，被裁掉
y ∈ [0,  w]

修正办法是再补一次 translateX(100%)。这里的 100% 指元素自身宽度， 而对旋转后的盒子来说它就是 h，正好把内容推回 x ≥ 0。 CSS 变换从右往左作用，所以写成：

/* 先 rotate，再 translateX —— rotate 写在右边 */
transform: translateX(100%) rotate(90deg);
transform-origin: top left;

下图是对应的坐标示意（左：直接旋转 → 被裁；右：补 translateX → 落回容器）：

问题二：文本的 width 要取容器的高度

元素的 width 决定"一行有多长"。转 90° 之后，这一维变成屏幕的纵向， 所以它应当等于容器的高度，而不是宽度。取错会让文字横着溢出容器。

问题三：滚动区要显式撑开

旋转不改变布局盒，所以容器算出来的滚动范围仍然按未旋转的尺寸算。 需要额外放一个占位元素，把滚动区设成旋转后的实际跨度 h × w， 否则长文的后续列会被裁掉。

与引擎 A 的一致性

修复后两种引擎输出一致，实测：

指标vertical-lrrotate(90deg)
墨迹像素数78,95478,954
墨迹包围盒高度1,974 px1,974 px
列间距164 px164 px

墨迹像素数一位不差，说明两者选出的字形完全一致 —— 它们是同一结果的两条路径。

4逐个坑与修法

以下都是实际发生并被修掉的缺陷，附判据。

#症状根因修法 / 判据
1 连字全部丢失，字形退化为孤立形 CSS 里显式打开 init/medi/fina/isol， 覆盖 rclt 的上下文判定 删除该声明。判据：整词宽度 2.90 em（错则 4.81 em）
2 旋转后文字不可见 包围盒落在 x ∈ [−h, 0]， 先后误用 translateY、translateX(−h) translateX(100%) rotate(90deg)
3 旋转后文字横向溢出容器 把 width 当成了容器的宽度 width = 容器高 − padding
4 旋转后后续列被裁 旋转不改变布局盒，滚动区按未旋转尺寸计算 加占位元素撑出 h × w
5 左栏蒙文显示成「豆腐块」 等宽字体链末尾没有蒙文字体，回退到无字形的字体 字体链末尾补 "UME Mongolian"
6 整页 JS 报错、编辑器空白 改顶栏时误删三个按钮，$("btn-clear") 取到 null 补回元素；新增启动异常捕获（CDP 监听 Runtime.exceptionThrown）
7 字符面板漏掉 15 个满文阿礼嘎礼字母 字符表手工分组时遗漏 测试断言覆盖 1800–18AA 每一个已分配码位
8 U+1806 断行判定错误 把 BB（Break Before）的"其后不可断"写成了"禁止在此断行" 用 UCD LineBreakTest.txt 成对判定对拍
9 ZWNJ 字素簇计数错 未建模其 GCB=Extend 属性 显式建模；断言 12 码位 → 11 簇
10 缺 CP × AL 禁断规则（LB30） 规则集不完整 补 LB30；对拍后涉及蒙文的成对判定 15/15 一致

方法论上的教训

第 1 条我曾"验证"过：用浏览器像素差异证明连字在变化，得到 28,688 像素差异、 IoU 0.678，于是判定成形正常。但那组差异测的是"正确成形 vs 我的错误干预"—— 我把干预当成了证据。教训是：验证要拿独立地面真相（HarfBuzz 直接读字体）， 而不是拿自己的输出前后对比。

一个反直觉的坑：不要用 canvas 测成形

Chromium 从未实现 ctx.fontFeatureSettings （实测 'fontFeatureSettings' in ctx === false）。 用它测量会得到"两种设置完全相同"的假结论，从而误判成形正常。 只有 DOM + CSS 渲染路径才反映真实成形。
