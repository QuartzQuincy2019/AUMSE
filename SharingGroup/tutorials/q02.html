C++ 的引用*

UME 项目组内部教程 · Q02（Qt） · 引用与指针的关系

C++ 本讲：给同一份数据起第二个名字

上一篇（Q01）讲的是 ::。这一篇讲另一个你很快就会到处遇到的符号： 一个 &。

它在 Qt 里出现的频率几乎和 :: 一样高 —— 你随手翻一段 Qt 代码，函数参数里全是 const QString &name 这种写法。学会读它，很多「为什么这么写」的疑问会一起消失。

本篇的论述主线

引用是「语法上的别名、实现上的指针」。 把这句话拆成两层，引用的一切性质都能推出来：

  • 实现层 —— 它本质上是一个绑定到被引用变量上的指针， 里面存的是那个变量的地址；
  • 语法层 —— 它被当作别名使用，读写时不需要写解引用运算符 *。

下面各节按这个主线展开：先看两层各是什么，再看它带来的两个好处 （免拷贝、绑定不可改），最后看这个模型在哪里要收着用。

这一篇的定位

M04《指针初步》已经把指针讲透了。这一篇只讲引用， 指针只在第 8 节做对比。没有读过 M04 也能看懂， 但要真正吃透，建议先过一遍 M04。

1先看两层：实现层与语法层

把「引用」当成一个东西去描述，很容易说不清。分成两层就清楚了。

层面它是什么表现
实现层 一个指针 —— 存着被引用变量的地址 真实存在，占用存储（通常 8 字节），指向那块存着数据的内存
语法层 那个变量的别名 写 r 就等于写 x； 不用写 *r，编译器替你做解引用

用一个具体例子把两层对齐：

ref1.cpp —— 同一个东西的两层复制
#include <iostream>

int main() {
    int x = 10;

    int& r = x;        // 绑定：r 从此代表 x

    r = 20;              // 语法层：像在改别名
                         // 实现层：改的是 r 里那个地址所指的内存 —— 也就是 x

    std::cout << "x  = " << x  << "\n";   // 20
    std::cout << "r  = " << r  << "\n";   // 20
    std::cout << "&x = " << &x << "\n";
    std::cout << "&r = " << &r << "\n";
}
输出
x  = 20
r  = 20
&x = 0x7ffd3f2a1b4c
&r = 0x7ffd3f2a1b4c      ← 和 &x 完全一样

最后两行是语法层给出的证据：对引用取地址，得到的就是被引用变量的地址。 说明 r 不是一块新内存，它代表的就是 x。

两层各解释了什么
现象由哪一层解释
r = 20 改的是 x 实现层（存的是 x 的地址）
访问时不用写 *r 语法层（编译器自动解引用）
函数传引用不产生拷贝 实现层（只传了地址，没搬数据）
引用不能改绑 绑定发生在初始化那一刻，之后由编译器锁死
引用没有空引用 语法层的硬性要求：声明时必须绑一个真实对象

2实现层：它确实是一个指针

编译器实现引用最常见的做法，就是在底层放一个指针， 然后在你每次写 r 的地方自动替你解引用。

两句源码的对应关系
你写的（语法层）
int x = 10;
int& r = x;
r = 20;
编译器大致生成的（实现层）
int x = 10;
int* r = &x;      // 存地址
*r = 20;          // 自动解引用

差别只在「自动」两个字上 —— 那个 * 由编译器替你补。 你写不出来：写 *r 是在对 x 再解引用一次，类型不对。

顺着这个模型，几个常被搞混的地方就清楚了：

引用占内存吗 实现层：占（那个指针要地方放）。 语义层：不占 —— C++ 标准规定引用不是对象， 所以 sizeof(r) 得到的是被引用类型的大小 （int& 的 sizeof 是 4，不是 8）。
这个指针能改吗 不能。它在初始化之后就被锁死了 —— 这正是第 5 节「内存更安全」的由来。
一定会有这个指针吗 不一定。标准只要求行为正确，不要求实现方式。 如果引用只用于局部、编译器看得清，它可能被完全优化掉， 变成直接操作原变量 —— 这也是「引用更快」的一个来源。
一个必须说清的边界

「引用就是一个自动解引用的指针」这句话，作为理解工具非常好用， 但不要拿它去推语法。

反例：如果引用真的只是 T* const，那 int& r; 就应该像 int* const p; 一样 可以只声明不初始化（只是之后不能改）。但引用必须当场绑定。 说明引用在语言规则上就不是指针，只是实现上常常用指针。

3语法层：为什么叫「别名」而不是「指针」

既然底层是指针，为什么不干脆让你用指针？因为别名这个说法更贴合它的用法。

int x = 10; 内存里开一块地方，名字叫 x，里面放 10
int& r = x; 没有开新地方放数据。r 是 x 的别名 —— 同一份数据，两个名字
r = 20; 通过 r 找到那份数据，写入 20。所以 x 也是 20
把引用想成「外号」。 一个人可以有大名和小名，但只有一个人。 叫小名让他做事，和叫大名让他做事，是同一件事 —— 你不需要先「按小名找到这个人」，那正是解引用要做的事。
「别名」这个说法买到了什么
写法含义
int* p = &x;  *p = 20; 「先把 x 的地址交给 p， 再顺着地址去改那个值」—— 两步，第二步容易忘
int& r = x;  r = 20; 「r 就是 x，改 r」—— 一步， 不可能忘 *

语法层省掉的那个 *，不只是少打一个字符： 它去掉了「忘记解引用」和「多解引用一次」这两类错误。 这是引用比指针好用的地方（安全性留到第 5 节）。

一个立刻能看出的好处：调用处不用改写法

call.cpp —— 调用处看不出区别复制
void byValue(int n)      { n = 99; }   // 改副本
void byRef(int& n)      { n = 99; }   // 改原对象

int a = 1, b = 1;
byValue(a);      // 调用处：a —— 看不出会不会被改
byRef(b);        // 调用处：b —— 长得一模一样

std::cout << a << " " << b << "\n";   // 1 99
输出
1 99

这正是「别名」的体现：函数内部拿到的是 b 本身，不是它的副本； 而调用处写起来和传值完全一样。

但这个「一样」也是坑

调用处看不出 byRef 会改参数 —— 这是引用被批评最多的地方。 所以业界有一条惯例：

  • 只读就用 const T&（下一篇 Q03 会专门讲），读代码时一眼知道不会被改；
  • 要改就明确一点，别在注释里藏。

4好处一：免拷贝

你的描述里这一句是关键：被引用的变量不亲自参与到函数内部的语句， 从而无需拷贝资源。下面把它拆开。

传值的时候，函数里那个变量是「另一个人」

写 void f(std::string s) 时，调用 f(name) 发生的事情是：

1分配新内存 在函数栈上开一块新地方，类型同样是 std::string
2搬一份数据 把 name 的内容拷过去（堆上的字符也要拷）
3函数改的是副本 函数里所有操作都作用在副本上，name 原封不动
4返回时销毁副本 又一次开销（析构、释放堆内存）

改成 void f(std::string& s)，第 1、2、4 步全部消失 —— 函数里那个 s 就是 name， 没有第二块内存、没有搬运、也没有销毁。

代价有多大：看两个例子

传值：每次调用都搬一整份
struct Big {
  int data[1024];   // 4 KB
};

void f(Big v) {     // 拷 4 KB
  v.data[0] = 1;
}

Big b;
f(b);               // 搬 4096 字节
f(b);               // 再搬 4096
f(b);               // 又搬 4096
传引用：只传一个地址
struct Big {
  int data[1024];   // 4 KB
};

void f(Big& v) {    // 只传地址
  v.data[0] = 1;
}

Big b;
f(b);               // 传 8 字节
f(b);               // 传 8 字节
f(b);               // 传 8 字节

三次调用：12 KB 的搬运 vs 24 字节的搬运。 而且第二栏还有一层：它改的是原来那个 b，第一栏改完就丢了。

nocopy.cpp —— 完整可跑：改到没改到，一目了然复制
#include <iostream>
#include <string>

void byValue(std::string s)  { s += "!"; }   // 改副本
void byRef(std::string& s)  { s += "!"; }   // 改原对象

int main() {
    std::string a = "UME", b = "UME";
    byValue(a);
    byRef(b);
    std::cout << "a = " << a << "\n";   // 没变
    std::cout << "b = " << b << "\n";   // 变了
}
输出
a = UME
b = UME!
「不拷贝」和「能被改」是同一件事的两面

因为函数里拿到的就是原来那个对象（不是副本），所以：

  • 省掉了拷贝 —— 这是效率；
  • 但函数里的修改会作用到调用者身上 —— 这是需要小心的副作用。

两者无法分开。如果你只想要效率、不想要副作用，就用 const T&： 不拷贝，同时也不许改 —— 这就是 const T&，下一篇 Q03 的主题。

什么时候「不拷贝」才真的有收益

类型传值 vs 传 const 引用
int / double / char / 指针 只有 4~8 字节，复制和传地址一样快。这类直接传值更好
std::string / QString 要拷贝字符缓冲、维护引用计数 —— 传 const& 明显更好
std::vector / QList / 大结构体 拷贝 = 整块内存搬运 —— 必须传 const&
小 POD 结构体（两三个 int） 差别很小，按团队习惯即可
一句话判断：这个东西「搬一次」贵不贵？
贵（字符串、容器、大结构体）→ const T&；
不贵（int、double）→ 直接 T，写起来还更短。

5好处二：绑定不可改

你的描述里第二句是：由于引用的「绑定」机制，一个引用从声明之后再也不能更改 所指向的变量，内存更加安全。这一节把「为什么更安全」讲透。

绑定发生在哪一刻

绑定 = 初始化那一刻，而且只发生一次

int& r = x; 里的 = 不是赋值，是绑定 —— 这是 C++ 里少见的「= 不表示赋值」的地方。 从这一刻起，r 和 x 的关系由编译器锁死， 没有任何语法能把它解绑。

rebind.cpp —— 看起来像改绑，其实不是复制
int x = 10, y = 99;

int& r = x;      // 绑定到 x
r = y;              // ✗ 这不是「让 r 改绑 y」
                    // ✓ 而是「把 y 的值 99 赋给 r 所指的 x」

std::cout << "x = " << x << "\n";                    // 99（被改了）
std::cout << "y = " << y << "\n";                    // 99（没动）
std::cout << "&r == &x ? " << (&r == &x) << "\n";    // 1（仍绑着 x）
输出
x = 99
y = 99
&r == &x ? 1

r = y; 这一行等价于 x = y;。 引用一旦绑好，任何操作都作用在它绑定的那个对象上，包括 =。 想换目标，引用做不到 —— 那是指针的活（p = &y;）。

「不能改绑」为什么等于「更安全」

因为指针能改绑，所以读代码时必须一路追踪它现在指向谁：

指针：目标会变，必须追踪
void f(int* p) {
  // p 现在指向谁？
  if (cond) p = &other;  // ← 变了
  *p = 1;                // 改的是哪一个？
}
引用：目标从一而终
void f(int& r) {
  // r 从进入函数起就绑着一个
  // 固定对象，永远是它
  r = 1;                 // 改的一定是它
}

由此带来三件具体的「安全」：

① 不用担心改绑 读 f(r) 时，从函数第一行到最后一行， r 指的都是同一个对象。不需要在脑子里维护「它现在指向谁」
② 不可能为空 引用必须绑定真实对象，所以没有空引用。 函数里不用写 if (!p) return;，也不可能出现「解引用空指针」
③ 不可能忘记初始化 这一条是编译器强制的，不是「建议」。 int& r; 直接编译不过
safe.cpp —— 指针要查空，引用不用复制
// 用指针：调用者可能传 nullptr，你必须防
void printPtr(const std::string* s) {
    if (!s) return;              // ← 这一句不能省
    std::cout << *s << "\n";      // ← 还要记得解引用
}

// 用引用：一定绑着真实对象，两件事都不用做
void printRef(const std::string& s) {
    std::cout << s << "\n";       // ← 直接就是对象本身
}
「绑定不可改」不是万能的

它只保证引用本身不换目标。它不保证那个对象一直活着。

如果被引用的对象先销毁了，引用就变成悬空引用。 这时候「不能改绑」反而成了麻烦 —— 你没法把它改成别的东西，只能不再使用它。 第 6 节和 Qt 的用法里都会遇到这个边界。

6两条铁律与常见错误

把前几节的结论收成两条规则，再列出对应的错误写法。

两条铁律
  1. 声明时必须绑定。不存在「先声明、以后再绑」的引用。 int& r; 编译不过。
  2. 绑定之后不能改绑。之后所有对它的操作， 都作用在它绑定的那个对象上。

① 必须绑定：编译器的报错

ref2.cpp —— 不绑定就编译不过复制
int x = 10;

int& a;          // ✗ 编译错误
int& b = x;       // ✓ 必须像这样一开始就指定绑谁
编译器报错
error: 'a' declared as reference but not initialized
    int& a;
         ^

② 不能改绑：最容易误会的一条

这一条在第 5 节已经用 r = y; 演示过。要记住的是： = 在这里是赋值，不是绑定。绑定只在初始化时发生一次。

完整错误清单

写法 / 想法问题
int& r;必须绑定，编译错
r = y; 想「改绑」那是赋值：把 y 的值写进 r 绑定的对象
int& r = *p; 且 p 可能为空未定义行为；先确认非空
返回局部变量的引用悬空引用（下面详述）
用引用当「可空的参数」表达不了「没有」；这种情况该用指针
给大对象写 T v 传参每次调用都复制一份；改 const T& v
给 int 也写 const int&不算错，但没收益（见第 4 节末尾）
for (auto n : v) 改 n改的是副本，原容器没变；要改写 auto&
以为 sizeof(r) 是指针大小是被引用类型的大小（引用不是对象）

最容易漏的一个：悬空引用

dangling.cpp —— 绝不要返回局部变量的引用复制
int& bad() {
    int local = 42;
    return local;      // ✗ local 在函数返回时已经死了
}

int& r = bad();       // r 绑着一块已销毁的内存 —— 未定义行为
std::cout << r;        // 可能打印 42，也可能打印垃圾
为什么这类错误特别难查
  • 编译不一定报错（好编译器给 warning）；
  • 运行时经常「碰巧正常」 —— 那块栈内存还没被覆盖，值还是 42；
  • 等到某次调用把它覆盖了，才突然出错，而且错在别处。

安全的做法：函数里创建的东西，按值返回（int 而不是 int&）。

7回到 Qt：const T& 为什么无处不在

前面几节的结论合起来，正好解释了 Qt 里那种签名： void setWindowTitle(const QString &title)。

为什么不传值 QString 内部有字符缓冲和引用计数，传值要维护那一套 —— 免拷贝（第 4 节）
为什么不传 QString& 那样函数就能改调用者的字符串，而 setter 不该改参数 —— 用 const 锁住
为什么不传 QString* 标题一定存在，不存在「没有标题」这种情况 —— 用引用表达「一定有效」（第 5 节）

所以 const QString &title 读作： 「我要用你的字符串，不会拷一份，也不会改它，而且你不用担心它是不是空的。」

一张表定下来怎么选

你想要的效果怎么写
只读，类型很小（int、double、指针） T v
只读，类型较大（QString、容器） const T& v  ← Qt 里最常见
要修改调用者的对象T& v
可以接受「没有」，或要重新指向别处T* v

Qt 里真实的样子

Qt 的签名为什么这么写
void setWindowTitle(const QString &title)只读、不复制
void append(const QString &str)只读、不复制
QString &operator+=(const QString &other)返回引用，好让 a += b += c 连起来
QString &operator[](int i)返回引用，于是 s[i] = 'x' 能直接改到内容
connect(..., const QObject *receiver, ...)接收者可以为空 → 用指针
void mousePressEvent(QMouseEvent *event)历史原因 + 事件对象可空，Qt 用指针
注意最后两行：Qt 不是「一律用引用」

Qt 的老接口（事件、connect）大量用指针， 因为它们诞生于「可能为空」的语义。新一些的接口（getter/setter） 则普遍用 const T&。

看到参数是 *，先想「它可能是空的吗」； 看到 &，就可以放心直接用 —— 这正是第 5 节说的「更安全」在工程上的体现。

作为返回值：引用让「改到本体」成为可能

ret.cpp —— 返回引用改到原对象复制
#include <iostream>
#include <vector>

std::vector<int> v{1, 2, 3};

int& at(int i) { return v[i]; }   // 返回容器里那个元素的别名

int main() {
    at(1) = 99;                        // 直接改到容器里
    std::cout << v[0] << " " << v[1] << " " << v[2] << "\n";
}
输出
1 99 3

at(1) = 99; 能编译通过，正是因为 at(1) 返回的是引用 （v[1] 的别名），而不是一个临时副本。 这也是 std::vector::operator[] 能赋值的原因 —— 它返回的就是引用。

8这个模型的边界：与指针的关系

「实现上是指针、语法上是别名」这句话在绝大多数场合够用。 但有几处必须收着点，否则会推出错误结论。

逐项对比

对比项指针 T* 引用 T&
语法上是什么一个变量，里面存着地址一个别名，不是对象
必须初始化不必须 int* p; 必须 int& r; 编译错
能否为空可以（nullptr）不可以
能否改指向可以 p = &y;不可以
访问目标要解引用 *p直接用 r
取目标地址p 本身就是要写 &r
sizeof指针大小（64 位上是 8） 被引用类型的大小
算术运算可以 p + 1、p++ 不可以

三处「不能类推」的地方

① sizeof 如果引用真是一个指针，sizeof(int&) 应该是 8。 实际是 4。因为标准规定引用不是对象， sizeof 作用在它身上就等于作用在被引用对象上
② 「不允许只声明」 int* const p; 是合法的（只是不能改）； int& r; 不合法。说明引用在语言规则上比「常量指针」还严 —— 它不是常量指针
③ 「一定占 8 字节」 局部引用经常被编译器完全优化掉， 直接对原变量操作，机器码里根本没有那个指针。 成员引用（struct 里的引用）则确实会占空间
正确的说法

引用在实现上通常是一个指针，但在语义上不是。

所以：用「指针」去理解它的行为和性能（为什么不拷贝、为什么改得到本体）； 用「别名」去理解它的语法和规则（为什么不用 *、为什么不能改绑）。

两个模型各管一半，合起来才是完整的引用。

它们之间可以互相转换（但一半是危险动作）

引用 → 指针 int* p = &r; —— 对引用取地址，得到被引用对象的地址。 绝对安全：引用一定绑着真实对象
指针 → 引用 int& r = *p; —— 解引用指针，得到对象的引用。 前提：p 不是空，否则是未定义行为
第二行是危险动作

int& r = *p; 在 p == nullptr 时是未定义行为。 编译器不一定报错，程序可能「看起来正常」跑很久。

所以「指针转引用」只在你刚刚确认过非空的紧邻位置才安全。 这也是为什么很多老代码宁可在函数里继续用指针。

9一页速查

五句话

① 实现层：它是一个指针 —— 里面存着被引用变量的地址。
② 语法层：它是一个别名 —— 访问时不用写 *，编译器替你解引用。
③ 免拷贝 —— 被引用的变量不参与函数内部的语句，函数直接操作本体，省掉整份拷贝。
④ 绑定不可改 —— 绑定只在初始化时发生一次，之后由编译器锁死； 不可能为空、不可能忘初始化。
⑤ 边界 —— sizeof 和「必须初始化」这两处不能按指针类推； 另外「不能改绑」不保证对象一直活着（悬空引用要自己防）。

写法速查

写法读作用途
int& r = x;r 是 x 的别名给变量起第二个名字
T& v传进来的是你的对象要修改调用者的对象
const T& v只读，且不复制大对象只读传参 —— Qt 里最常见
T& f()返回的是别名让 f() = x 或 v[i] = x 成立

for (const auto& n : v)不复制地遍历只读遍历首选
