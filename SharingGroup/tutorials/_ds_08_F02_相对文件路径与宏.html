相对文件路径与宏*

UME 项目组内部教程 · 08-F02（File）· 与本项目施行密切相关

已学：cmd 初步 已学：字符串 本讲：文件放在哪、怎么找到它

为什么这一篇对本项目重要

UME 要读取字体文件、加载配置、导出 SVG —— 这些都涉及「文件在哪」。

而实际开发中最常遇到的一类怪事就是：

「我在 IDE 里跑得好好的，双击 exe 就找不到字体了。」

原因几乎总是相对路径。这一篇把它讲清楚，很短。

文中所有演示均在 Windows 上实际运行核对。

1绝对路径与相对路径

绝对路径相对路径
长相 D:\Path\To\UME\font\NotoSansMongolian-Regular.ttf font\NotoSansMongolian-Regular.ttf
含不含盘符含，从磁盘根开始不含
唯一吗唯一，写死了不唯一，要看你在哪
换台机器会失效（盘符可能不同） 通常还能用
适合临时调试、写脚本项目里正式使用
为什么项目里要用相对路径

因为绝对路径会写死「你机器上的位置」。同事 clone 到 D:\Path\To\UME，你的 D:\Path\To\project 就全废了。

相对路径描述的是「相对于项目根目录的位置」， 只要项目内部结构不变，换到谁机器上都能用。

2三个特殊符号

假设项目结构是这样，你正站在 UME 目录里：

D:\Path\To\UME\ ← 当前目录（CWD） ├─ font\ │ └─ NotoSansMongolian-Regular.ttf ├─ web\ │ └─ UME.html ├─ report\ └─ FONT_ANALYSIS.md
.\ 或 什么都不写 当前目录 —— font\Noto....ttf 等于 .\font\Noto....ttf
..\ 上一级目录 —— ..\ 就是 D:\Path\To\
. （单个点） 就是「当前目录」本身
\ （开头一个反斜杠） 当前盘符的根目录 —— \Windows 指 D:\Windows

所以 ..\..\font\x.ttf 的意思是 「往上两级，再进 font 目录，找 x.ttf」。

千万别把 \ 和 .\ 搞混
.\font\a.ttf 当前目录下的 font 文件夹里 → 你要的
\font\a.ttf 当前盘符根目录下的 font → 通常是 D:\font\a.ttf，不是你要的

少了那个点，位置会跑到磁盘根目录去 —— 这是很难一眼看出的错误。

3相对路径「相对于谁」

这是本篇最重要的一点。

结论

相对路径是相对于「当前工作目录」（CWD）， 不是相对于 exe 文件所在的位置。

而 CWD 是「你敲命令时待在哪个目录」。

下面这个实验能一次说清。程序只做一件事：打印 CWD 和它自己的路径。

打印 CWD 与程序自身路径复制
#include <stdio.h>
#include <direct.h>       /* Windows 下的 _getcwd */

int main(int argc, char *argv[]) {
    char buf[4096];
    _getcwd(buf, sizeof(buf));

    printf("当前工作目录 (CWD) = %s\n", buf);
    printf("程序自己的路径     = %s\n", argc > 0 ? argv[0] : "?");
    return 0;
}

把编译出的 path1.exe 放到 build\ 里， 然后在两个不同的目录各运行一次：

在 build 目录里运行
D:\Path\To\project\build>path1.exe
当前工作目录 (CWD) = D:\Path\To\project\build
程序自己的路径     = D:\Path\To\project\build\path1.exe
在上一级目录里运行同一个 exe
D:\Path\To\project>build\path1.exe
当前工作目录 (CWD) = D:\Path\To\project
程序自己的路径     = D:\Path\To\project\build\path1.exe

两次的程序路径一样，但 CWD 不同。 这说明：CWD 由「你从哪运行」决定，与 exe 放哪无关。

这会导致什么后果

写一个只做一件事的程序：用相对路径打开 data.txt。

用相对路径读文件复制
#include <stdio.h>

int main(void) {
    FILE *fp = fopen("data.txt", "r");      /* 相对路径 */
    if (fp != NULL) {
        char line[256];
        printf("打开成功，内容:\n");
        while (fgets(line, sizeof(line), fp) != NULL) {
            printf("  %s", line);
        }
        fclose(fp);
    } else {
        printf("打开 data.txt 失败（当前目录里没有它）\n");
    }
    return 0;
}

把 pathread.exe 放进 build\， data.txt 也放在 build\，然后做三次实验：

A · 在 build 目录里运行（data.txt 就在旁边）
D:\Path\To\project\build>pathread.exe
打开成功，内容:
  hello from build dir
B · 在上一级目录里运行同一个 exe（那里没有 data.txt）
D:\Path\To\project>build\pathread.exe
打开 data.txt 失败（当前目录里没有它）
C · 把 data.txt 也放到上一级，再在上一级运行同一个 exe
D:\Path\To\project>build\pathread.exe
打开成功，内容:
  hello from parent dir
三次实验说明了什么

完全相同的 exe，读到的文件却不一样 —— 因为 "data.txt" 这个相对路径每次都从 CWD 开始找。

这正好解释了那个经典现象：

  • IDE 里运行正常 —— IDE 通常把 CWD 设成项目目录
  • 双击 exe 就找不到文件 —— CWD 变成了 exe 所在目录
  • 从命令行运行有时行有时不行 —— 取决于你在哪敲命令
怎么避免

三条实用做法：

  1. 资源文件跟着 exe 一起放（比如统一放 assets\）， 并约定「程序从自己的目录找资源」。
  2. Qt 里用资源系统：把文件写进 .qrc， 用 :/font/x.ttf 访问。 资源被编译进 exe，彻底没有路径问题 —— 这是 Qt 项目最省心的做法。
  3. 需要时自己算绝对路径： 用 QCoreApplication::applicationDirPath() 拿到 exe 所在目录， 再拼上资源子路径。

4什么是环境变量

定义

环境变量（environment variable）是操作系统为每个程序准备的一批 「名字 = 值」的小纸条。

程序启动时，系统把这一叠纸条交给它；程序想知道什么， 就按名字去查值。

在 cmd 里，用 %名字% 就能取到值。例如 %TEMP% → C:\Users\Your_Username\AppData\Local\Temp。

具体一点：它长什么样

在 cmd 里敲 set，会看到几十行「名字=值」，那就是全部环境变量：

set：列出全部
C:\>set
ALLUSERSPROFILE=C:\ProgramData
APPDATA=C:\Users\Your_Username\AppData\Roaming
COMPUTERNAME=MY-PC
PATH=C:\Windows\system32;C:\Windows;...
TEMP=C:\Users\Your_Username\AppData\Local\Temp
USERNAME=Your_Username
...

C:\>set TEMP
TEMP=C:\Users\Your_Username\AppData\Local\Temp

三个关键性质

性质含义为什么重要
① 是「名字→值」的对照 名字固定，值可以变 代码里写名字，就不依赖具体路径
② 由系统 / 用户设置 不在代码里，在系统里 换台电脑只改系统设置，代码一个字不用动
③ 程序启动时读入 启动后再改系统设置，已经跑着的程序不知道 这就是「改了 PATH 必须重开 cmd」的原因
用一句话说清它的价值

环境变量是「把会变的东西从代码里搬出去」的标准做法。

你的程序要用临时目录 —— 不要写死 C:\Users\张三\AppData\...， 因为同事的用户名不叫张三。写 %TEMP%， 系统会替你填上对的那个。

4.1 它和「编译器宏」不是一回事

「宏」这个词在不同场合指不同的东西，这是最容易混的地方：

场合「宏」指的是写法谁替换它
命令行 / 操作系统 环境变量 %PATH% cmd（执行命令前）
Visual Studio（本篇第 8 节） 属性宏 $(SolutionDir) MSBuild（生成时）
编译器预处理 #define 的文本替换 #define MAX 100 预处理器（编译前）
它们共同的思路

都是「用一小段符号，代表一段会变的内容」。 但由谁替换、什么时候替换、在哪里能写完全不同 —— 不能互相通用。

本节的 %...% 只在命令行里由 cmd 替换； $(...) 只在 VS 的工程配置里由 MSBuild 替换 （见第 8 节）；#define 只在源文件里由预处理器替换。

4.2 它是怎么工作的

把「设置 → 启动 → 读取 → 替换」这条链走一遍，很多现象就都解释得通了。

① 设置
在「环境变量」对话框里，
或 set X=Y 临时设
② 启动程序
你打开 cmd（或 IDE、
双击 exe）
③ 复制一份
系统把当时的全部变量
拷进这个进程
④ 读取 / 替换
程序或 cmd 按名字取值
（%X% 被替换成值）
第 ③ 步解释了几乎所有「环境变量怪现象」
  • 改了系统设置，已经开着的窗口不生效 —— 它在第 ② 步就已经把旧的那份拷走了。必须重开。
  • 在窗口里 set X=Y，别的窗口看不到 —— 只改了当前进程自己那份副本，没写回系统。
  • IDE 里能编、命令行不能（或反过来） —— 两者是不同时间启动的进程，拿到的可能是不同的两份。
  • 子进程能继承父进程的环境变量 —— cmd 里启动的程序，会拿到 cmd 那一份（加上你临时 set 的）。

「临时设」与「永久设」的区别

临时（set X=Y）永久（对话框里改）
存在哪当前进程的内存里注册表（系统或用户）
影响范围只有这个窗口及其子进程以后所有新进程
关掉窗口后消失还在
适合试一下能不能跑通真正配置开发环境

程序里怎么读它

三种语言读环境变量的写法，可以对照着记：

读取环境变量复制
/* C：用 getenv，取不到返回 NULL */
const char *tmp = getenv("TEMP");
if (tmp != NULL) printf("临时目录: %s\n", tmp);

/* cmd 批处理 */
echo 临时目录: %TEMP%

/* Python */
import os
print(os.environ.get("TEMP"))
注意 getenv 可能返回 NULL

这个变量不一定存在 —— 别的机器上可能没设。 所以一定要判断，否则后面用这个指针就会崩。

这和第五讲「malloc 之后要判 NULL」是同一条原则： 凡是「可能拿不到」的东西，都要先检查再使用。

再看一眼效果

在 cmd 里敲这几条，看它替换成什么：

场合「宏」指的是例子
命令行 / 系统 环境变量：用 %名字% 取它的值 %PATH%  %TEMP%
编译器预处理 #define 定义的文本替换 #define MAX_HP 100
Office / 游戏 录好的一串操作，一键重放 「宏病毒」说的就是这个
这一篇只讲第一种

命令行里的「宏」= 环境变量，写法是 %名字%。

它的核心思想和编译器的宏一样：用一小段符号， 代表一段会变的内容。你写 %TEMP%， cmd 会把它替换成实际的临时目录路径。

怎么配开发环境、怎么让命令行找到你装的工具 —— 全靠它。

先看一眼效果

在 cmd 里敲这几条，看它替换成什么：

看环境变量的实际值
C:\>echo %USERPROFILE%
C:\Users\Your_Username

C:\>echo %TEMP%
C:\Users\Your_Username\AppData\Local\Temp

C:\>echo %USERNAME%
Your_Username

C:\>echo %COMPUTERNAME%
MY-PC

echo 的作用就是「把后面那串东西打印出来」， 而 %...% 会先被替换掉，然后才打印。 所以这个命令最好用来确认「某个变量现在到底是什么」。

和「相对路径」有什么关系

环境变量给的是绝对路径，而且人人不同、换台机器就不同。

所以写脚本、写配置时，想引用「我的临时目录」「我装工具的地方」， 就用环境变量而不是把路径写死 —— 这样换台机器也能跑。 这和前面讲的「用相对路径代替绝对路径」是同一个目的： 让位置可以变，而代码不用改。

5最常用的几个环境变量

变量含义典型值
%PATH%去哪找可执行程序 C:\Windows\system32;...
%TEMP%临时文件目录 C:\Users\你\AppData\Local\Temp
%USERPROFILE%当前用户的个人目录 C:\Users\Your_Username
%USERNAME%当前用户名Your_Username
%APPDATA%程序存配置的地方（漫游） C:\Users\你\AppData\Roaming
%COMPUTERNAME%电脑名MY-PC
%CD%当前目录D:\Path\To\project

5.1 %PATH%：为什么命令能直接敲

你能直接敲 dir、notepad、python， 是因为它们在 %PATH% 列出的某个目录里。

PATH 长什么样
C:\>echo %PATH%
C:\Windows\system32;C:\Windows;C:\Windows\System32\Wbem;...
↑ 若干条路径，用分号 ; 隔开

cmd 收到一个命令名时，会按 %PATH% 里的顺序逐个目录去找 有没有这个 .exe。找到就运行，全找完都没有就报那句老朋友：

找不到命令时
C:\>gcc --version
'gcc' 不是内部或外部命令，也不是可运行的程序或批处理文件。

（这通常不是「没装」，而是「装了但没加进 PATH」）
这就是配置环境变量的典型场景

装了 MinGW / Python / Qt 之后要做的「配置环境变量」， 十有八九就是往 %PATH% 里加一条 —— 让命令行知道「工具装在这儿」。

加完必须新开一个 cmd 窗口才生效，见第 7 节的坑。

临时加一条 %PATH%

只在当前窗口生效
C:\>set PATH=D:\Path\To\mingw64\bin;%PATH%
         ↑ 新目录放在最前面（优先找到）   ↑ 保留原来的，别忘了 

C:\>gcc --version
gcc (x86_64-posix-seh-rev1, Built by MinGW-Builds project) 13.1.0
注意 ;%PATH% 不能漏

set PATH=D:\...\bin 会把整个 PATH 替换掉， 于是 dir、cd 这些也找不到，窗口基本废了。

想追加就必须写 ;%PATH% —— 在原有值后面接上新的。

5.2 %TEMP% / %USERPROFILE%

这两个在写脚本时特别常用 —— 它们让脚本不依赖具体用户名。

把文件放到临时目录
C:\>copy output.log %TEMP%\
        1 个文件已复制。

C:\>cd %USERPROFILE%\Desktop
（切到当前用户的桌面 —— 不管用户名是什么都对）
不要这样写应该这样写
cd C:\Users\Your_Username\Desktop cd %USERPROFILE%\Desktop
copy a.log C:\Users\你\AppData\Local\Temp\ copy a.log %TEMP%\

理由一样：把会变的部分（用户名）交给环境变量。 同事拿到你的脚本，不用改一个字就能跑。

5.3 %~dp0：批处理里最重要的一个

写 .bat 脚本时，最难的是「怎么知道脚本自己放在哪」—— 因为用户可能在任何目录下双击运行它。

%~dp0 就是答案：它替换成「这个脚本所在的目录」。

写法替换成
%0脚本的完整路径
%~dp0脚本所在的目录（结尾自带反斜杠）
%CD%当前工作目录（不是脚本所在目录！）
build.bat：把「脚本所在目录」当成项目根复制
@echo off
rem %~dp0 是「本脚本所在目录」—— 不管从哪里运行都对
cd /d "%~dp0"

echo 项目根目录: %CD%
gcc -std=c99 src\main.c -o build\app.exe
运行结果（从别的目录运行也没问题）
项目根目录: D:\Path\To\project
（编译成功）
为什么这比 %CD% 好

用户可能在 C:\ 下敲 D:\Path\To\project\build.bat， 这时 %CD% 是 C:\， 而 %~dp0 仍然是 D:\Path\To\project\。

脚本里的相对路径要相对于谁？几乎总是「脚本自己」。 所以开头加一句 cd /d "%~dp0" 是批处理的标准起手式 —— 这样后面的相对路径就都有了明确基准。

这一段和前面第 3 节连上了

第 3 节说过：相对路径相对于当前工作目录（CWD）， 而 CWD 是「你在哪敲的命令」，不是「脚本在哪」。

cd /d "%~dp0" 的作用就是把 CWD 强制设成脚本目录， 于是所有相对路径都有了确定的基准。这是最常用的解法。

6怎么设置环境变量

两种方式，用途不同。

① 只在当前窗口生效（临时调试用）

set：只影响这个窗口
C:\>set MY_ROOT=D:\Path\To\project
C:\>echo %MY_ROOT%
D:\Path\To\project

（关掉窗口就没了 —— 适合试一下能不能跑通）

② 永久生效（真正「配置环境变量」）

  1. Win 键搜索「环境变量」→ 选「编辑系统环境变量」
  2. 点「环境变量」按钮
  3. 上半部分是当前用户的，下半部分是整台机器的 —— 优先改上半部分（不需要管理员权限，也只影响你自己）
  4. 找到 Path，双击 → 「新建」→ 填目录 → 确定
建议：把 UME 用到的工具都加进 Path

Qt / MinGW 装好后，通常要把它们（或者 Qt 自带的那个 「命令提示符」快捷方式）配好。判断标准很简单：

验证是否配好
C:\>where gcc
D:\Path\To\mingw64\bin\gcc.exe
（能印出路径就说明 PATH 配对了；印不出来就是没配或没重开窗口）

③ 在脚本里临时设置

脚本内自己配好环境再干活复制
@echo off
rem 只在本脚本运行期间生效，不会污染系统设置
set PATH=D:\Path\To\mingw64\bin;%PATH%
set UME_ROOT=%~dp0

gcc -std=c99 "%UME_ROOT%src\main.c" -o "%UME_ROOT%build\app.exe"
运行结果
（编译成功，退出后 PATH 恢复原样）
为什么项目脚本要自己设 PATH

因为不能假设每个同事都配好了环境变量。 脚本开头自己设一遍，就「自带环境」了 —— 谁拿到都能跑，不用先看一堆配置说明。

这也是排查「我这儿能编，他那儿编不了」这类问题的常用手段。

7常见坑

坑 1 · 以为相对路径是相对 exe

对比含 C++复制
/* ❌ 想当然：以为从 exe 所在目录找 */
FILE *fp = fopen("data.txt", "r");   /* 实际是从 CWD 找！ */

/* ✅ 明确从 exe 所在目录找（下面这行是 Qt / C++） */
QString dir = QCoreApplication::applicationDirPath();
FILE *fp2 = fopen((dir + "/data.txt").toUtf8().constData(), "r");

坑 2 · 反斜杠被当成转义符

对比复制
/* ❌ C++ 字符串里 \f 是转义符（换页），\n 是换行 */
const char *p = "font\NotoSans.ttf";    /* \N 不是合法转义，\f 是换页！ */

/* ✅ 三种正确写法 */
const char *a = "font\\NotoSans.ttf";   /* 双反斜杠 */
const char *b = "font/NotoSans.ttf";    /* 正斜杠，Windows 也认 */
const char *c = R"(font\NotoSans.ttf)";  /* 原始字符串，C++11 */

实用建议：代码里的路径统一用正斜杠 /。 Windows 和 Linux 都认，而且不用转义。

坑 3 · 改了环境变量但没重开窗口

最常见的困惑
（在「环境变量」对话框里加了 Path，点确定）
C:\>gcc --version
'gcc' 不是内部或外部命令...
↑ 明明加了，怎么还不行？

原因是：环境变量是 cmd 启动时读进去的，之后就一直用内存里那份。 你改了系统设置，已经开着的窗口不知道。

解决：关掉 cmd，重新开一个。 （IDE 也一样 —— 改完环境变量要把 IDE 也重启。）

坑 4 · 追加 PATH 时忘了 ;%PATH%

对比复制
rem ❌ 把整个 PATH 覆盖了，dir / cd 都找不到了
set PATH=D:\Path\To\mingw64\bin

rem ✅ 追加：旧值放后面，用分号隔开
set PATH=D:\Path\To\mingw64\bin;%PATH%

记法：set 变量=新值;%变量% 才是「在前面插一条」。

坑 5 · 路径里有空格没加引号

对比复制
rem ❌ C:\Program Files 里的空格会被当成参数分隔
cd C:\Program Files\MyTool

rem ✅ 加引号
cd "C:\Program Files\MyTool"

rem ✅ 环境变量也一样，整体加引号
cd "%USERPROFILE%\My Documents"

和第一部分讲的路径规则是同一条：只要路径可能含空格，就加引号。

坑 6 · % 忘了配对

对比复制
echo %TEMP          rem ❌ 只写了一半，cmd 会原样打出来
echo %TEMP%         rem ✅ 前后都要有 %

echo %%~dp0         rem 在 .bat 里想要「字面的 %」就写两个

8另一种宏：VS 的 $(...)

这一节解决两个具体问题
  1. Visual Studio 里 项目 → 属性 → 输出目录 默认写着 $(SolutionDir)$(Platform)\$(Configuration)\ —— 这一串 $(...)$ 到底是什么？
  2. 要包含自己写的头文件，在 配置属性 → C/C++ → 附加包含目录 里写的 $(SolutionDir) 又是什么？

答案：它们是 MSBuild 的「属性宏」 —— 和第 4 节的环境变量是同一个思路，但换了一套记号和替换者。

本节所有展开结果，都用本机的 MSBuild（Visual Studio Community 2026 · 18.10.3）实际跑出来核对。

8.1 输出目录里的那串是什么

先看 VS 里那个默认值：

项目属性 → 输出目录（默认值）复制
$(SolutionDir)$(Platform)\$(Configuration)\

它不是一条真实路径，而是四个宏拼起来的式子。 MSBuild 在生成时把它们各自替换成实际值，拼出一条真路径。

假设解决方案放在 D:\Path\To\UME\，里面有个项目 UME.vcxproj，当前选的是 Debug | x64。逐个展开：

宏展开成含义
$(SolutionDir) D:\Path\To\UME\ 解决方案（.sln）所在目录，结尾带反斜杠
$(Platform) x64 目标平台（x64 / Win32 / ARM64）
$(Configuration) Debug 生成配置（Debug / Release）
四个拼起来就是 →
整串展开 D:\Path\To\UME\x64\Debug\ 这就是 exe 会被放到的目录
本机实测：把这四个宏交给 MSBuild 打印出来
SolutionDir    = [D:\Path\To\UME\]
Platform       = [x64]
Configuration  = [Debug]
OutDir（那串展开后） = [D:\Path\To\UME\x64\Debug\]
TargetPath           = [D:\Path\To\UME\x64\Debug\UME.exe]
为什么要费劲拼，而不直接写死

因为一个项目要同时支持好几种组合： Debug / Release × x64 / Win32，就是 4 种。

写死的话得为每种组合各配一遍，改一处要改四处。 用宏之后一套式子自动适配所有组合：

当前选的是输出目录自动变成
Debug | x64D:\Path\To\UME\x64\Debug\
Release | x64D:\Path\To\UME\x64\Release\
Debug | Win32D:\Path\To\UME\Win32\Debug\

这正是环境变量的那套理由： 把会变的部分（配置名、平台名）换成符号，式子就不用改。

实测确认：换个配置，输出目录真的跟着变

同一个工程，只把生成配置从 Debug 换成 Release：

配置MSBuild 展开出的 OutDir
Debug…\x64\Debug\
Release…\x64\Release\

式子一个字没改，输出目录自己就换了 —— 这就是宏的意义。

VS 界面上在哪里改

顶部菜单 → 项目 → 属性（或右键项目 → 属性），打开属性页：

配置属性
 └─ 常规
     ├─ 输出目录            ← $(SolutionDir)$(Platform)\$(Configuration)\
     └─ 中间目录            ← $(Platform)\$(Configuration)\
 └─ C/C++
     └─ 常规
         └─ 附加包含目录     ← 在这里加 $(SolutionDir)include
两个容易踩的点

① 注意左上角的「配置」下拉框。 属性页顶部有 配置 和 平台 两个下拉框， 默认可能是「所有配置」。改的时候要想清楚： 是只改 Debug，还是所有配置都改？ 选「所有配置」改一处，四个组合一起生效 —— 通常这才是你要的。

② 结尾那个反斜杠不能丢。 $(SolutionDir) 自带结尾反斜杠， 所以写 $(SolutionDir)include 就对了； 写成 $(SolutionDir)\include 会变成两个反斜杠 （Windows 一般能容忍，但不该这么写）。

8.2 附加包含目录里的 $(SolutionDir)

现在回答第二个问题：要包含自己写的头文件，那个 $(SolutionDir) 是什么？

它就是上一节那个 $(SolutionDir) —— 解决方案所在目录。同一个宏，在不同地方写，含义完全一样。

先看没有它会怎样

假设项目结构是这样：

D:\Path\To\UME\ ← 解决方案目录（$(SolutionDir)） ├─ UME.sln ├─ UME\ ← 项目目录（$(ProjectDir)） │ ├─ UME.vcxproj │ └─ main.c └─ include\ ← 自己写的头文件放这里 └─ font.h

在 UME\main.c 里写 #include "font.h"， 编译器会去哪几个目录找 font.h？

  • 先找 main.c 自己所在的目录，也就是 UME\ —— 但 font.h 在 include\ 里，找不到
  • 再找「附加包含目录」里列的目录 —— 还没配，是空的
  • 再找系统头文件目录 —— 更不会有
  • 结果：报 fatal error C1083: 无法打开包括文件: "font.h"

配上它就解决了

附加包含目录里填复制
$(SolutionDir)include

/* 展开后 = D:\Path\To\UME\include  ← font.h 就在这里 */
本机实测：MSBuild 展开出的 IncludePath 前两项
D:\Path\To\UME\include;  ← 我加的那一条（= $(SolutionDir)include）
D:\MicrosoftVisualStudio\Community\VC\Tools\MSVC\...\include;  ← VS 自带
...（后面一串 Windows SDK 的目录）

看第一项：$(SolutionDir)include 被替换成了 …\_vs_check\include， 正是解决方案目录下的 include 文件夹。配对了。

为什么用 $(SolutionDir) 而不是相对路径

因为「附加包含目录」里的相对路径是相对于项目文件（.vcxproj）， 不是相对于解决方案。这个基准很难记住，而且换个位置就错。

用 $(SolutionDir) 之后，基准写明白了、一眼能看懂， 而且项目挪到别的盘、别的机器上依然正确。

它的作用和第 3 节讲的 %~dp0 是同一招： 把「相对于谁」这件事显式写出来，不靠默认约定。

要加多个目录怎么写

用分号隔开复制
$(SolutionDir)include;$(SolutionDir)src\core;D:\third_party\zlib\include

/* 在 VS 界面里：双击那一行 → 点右侧的「...」→ 一行一个目录 → 确定
   VS 会自动帮你拼成分号分隔的形式，不用手打分号 */
改完要重新生成

改「附加包含目录」之后，已经编译过的 .obj 不会自动重编 —— 因为 VS 不认为「头文件搜索路径变了」算源文件变了。

所以改完包含目录，习惯性做一次 生成 → 重新生成解决方案，别只点「生成」。

否则会出现「明明改对了却还是报找不到头文件」的假象。

8.3 常用属性宏一览

下面这些值全部是本机 MSBuild 实际展开出来的， 用同一个演示工程（解决方案在 …\_vs_check\， 项目在 …\_vs_check\Demo\，配置 Debug | x64）。

目录与文件名

宏实测展开含义
$(SolutionDir) …\_vs_check\ .sln 所在目录（结尾带 \）
$(SolutionPath) …\_vs_check\Demo.sln .sln 的完整路径
$(SolutionName) Demo.sln 的文件名（不含扩展名）
$(ProjectDir) …\_vs_check\Demo\ .vcxproj 所在目录（结尾带 \）

$(ProjectName) Demo项目名
$(ProjectFileName) Demo.vcxproj项目文件名（含扩展名）
$(ProjectExt) .vcxproj项目文件扩展名

$(VisualStudioVersion)18.0 VS 主版本号
$(MSBuildToolsVersion)Current MSBuild 工具集版本

两个必须知道的行为

① 没有的宏会展开成「空」，不会报错

实测：写一个不存在的 $(NO_SUCH_MACRO_XYZ)， MSBuild 不报错，直接替换成空字符串：

实测
不存在的宏 = []

这很危险：如果宏名打错了， 路径会静默地少一段，你只会看到「找不到文件」， 而不会看到「宏名拼错」。

所以路径拼不对时，第一件事是怀疑宏名拼写。 VS 属性页里有个「宏 >>」按钮，可以列出所有可用宏、 并显示当前值 —— 拿它对照最省事。

② 没有 .sln 时，$(SolutionDir) 会退化成项目目录

实测：直接用 MSBuild 生成单个 .vcxproj（没有 .sln）时：

情况$(SolutionDir)
有 .sln …\_vs_check\  .sln 所在
没有 .sln …\_vs_check\Demo\  退化成项目目录

所以在 VS 里正常打开解决方案时它是可靠的； 但如果你绕过 .sln 单独编译项目，含义就变了 —— 这时要用 $(ProjectDir) 才稳。

顺带一个会遇到的报错

如果你在命令行用 MSBuild 指定了一个解决方案里没配置过的平台， 会直接失败（本机实测）：

实测
error MSB4126: 指定的解决方案配置"Debug|Win32"无效。
请使用 Configuration 和 Platform 属性指定有效的解决方案配置。

意思是「这个解决方案里没有 Debug|Win32 这个组合」。 在 VS 里对应的是顶部工具栏那两个下拉框 —— 配置管理器里没建的组合，命令行也编不了。

8.4 它和 %环境变量% 的关系

这两套宏最容易混。一张表看清：

%名字%$(名字)
叫什么环境变量MSBuild 属性宏
谁替换cmdMSBuild
什么时候敲命令执行前生成项目时
在哪写有效cmd 里、.bat 里 VS 属性页、.vcxproj 里
典型例子%PATH%$(SolutionDir)
互相能换吗 不能 —— 在 cmd 里 %SolutionDir% 是空的； 在 VS 属性页里 $(PATH) 也取不到你想的那个 PATH
但有一处它们确实相通

MSBuild 能读环境变量。实测：在 .vcxproj 里写 $(TEMP)、$(PATH)，MSBuild 会把它们 当成属性名去找 —— 找不到同名属性时，就去环境变量里取：

实测
PATH 前 60 字 = [C:\Windows\system32;C:\Windows;C:\Windows\System32\Wbem;C:\W]
TEMP          = [C:\Users\Your_Username\AppData\Local\Temp]
USERPROFILE   = [C:\Users\Your_Username]

所以环境变量是一种「兜底的宏」： 实在没有同名属性时，MSBuild 会去环境里找。

实用价值：如果你想让工程配置跟着一个环境变量走 （比如团队里每个人把第三方库放在不同地方）， 可以设一个 UME_ROOT，然后在属性页里写 $(UME_ROOT)include —— 每个人各自设自己的，工程文件不用改。

怎么快速查一个宏现在是什么值

VS 属性页里改「附加包含目录」这类字段时， 输入框右侧有个「宏 >>」按钮。

点开它会列出所有可用宏 + 当前展开值， 还可以双击插入。想确认 $(SolutionDir) 在你机器上到底是什么，这是最快的办法。

另外，改完属性页 VS 会立刻把宏展开显示在下方预览里， 不用编译就能看到结果。

本节的结论，压成三条

  1. $(...) 是 MSBuild 的属性宏，不是环境变量。 在 VS 的工程配置里用，由 MSBuild 在生成时替换。
  2. $(SolutionDir) = .sln 所在目录（自带结尾反斜杠）。 输出目录那串靠它 + $(Platform) + $(Configuration) 拼出「哪个配置放哪」； 附加包含目录靠它把「自己写的头文件在哪」写清楚。
  3. 宏名写错不报错，只会静默变成空串 —— 路径找不到时，先用属性页的「宏 >>」核对拼写。
这一篇要记住的四件事
  1. 相对路径相对于「当前工作目录」（CWD）， 不是相对于 exe 所在位置 —— 这是大多数「找不到文件」的根因。
  2. .\ 是当前目录，..\ 是上一级； 别把 \font 当成 .\font。
  3. 代码里的路径用正斜杠 /， 不用转义，跨平台都能认。
  4. 命令行里的「宏」就是环境变量（%PATH%、%TEMP%）， 用它代替写死的路径；%~dp0 是脚本里最重要那个。
