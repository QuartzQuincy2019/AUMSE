1一个字符，三种问法

看见屏幕上这个字：中。它其实是三件事：

问法答案概念名
它是哪个字？U+4E2D 码位（code point）
它在内存里占几个字节？UTF-8 下 3 个 编码（encoding）
那 3 个字节分别是多少？E4 B8 AD 编码后的字节序列
一句话分清

Unicode 是「给每个字符编个号」；UTF-8 是「把这个号写成字节」。

前者是字典（编号表），后者是写法（存法）。它们不是一回事。

比喻：Unicode 像「身份证号」—— 每个人（字符）有个唯一号码。
UTF-8 像「用什么字体写这个号码」—— 号码不变，写法可以变长变短。

2码位：字符的编号

Unicode 给世界上每个字符分配了一个编号，写作 U+ 加十六进制。

字符码位说明
AU+0041拉丁字母，编号很小
中U+4E2D汉字
ᠮU+182E回鹘蒙文 MA
😀U+1F600表情符号，编号超过 0xFFFF

蒙文的码位分布

范围内容
U+1800 ~ U+18AF蒙文主区段：标点（U+1800~U+180A）、 FVS 变体选择符（U+180B~U+180D）、数字、以及传统蒙文字母
U+1820 ~ U+18AA传统蒙文字母（含满文、锡伯文扩展）
U+11660 ~ U+1167F蒙文补充区段

注意 U+182E 这个数比 255 大得多。 这就是为什么一个字节装不下它 —— 一个字节最大只能表示 255。

3UTF-8 的字节规律

UTF-8 的聪明之处：用一个到四个字节表示一个码位，按码位大小自动决定用几个。

码位范围字节数典型字符
U+0000 ~ U+007F1A、数字、英文标点（和 ASCII 完全一样）
U+0080 ~ U+07FF2é、希腊字母、西里尔字母
U+0800 ~ U+FFFF3汉字、蒙文、日文
U+10000 ~ U+10FFFF4表情符号、罕见古文字

实测：四种字符的字节

字符 / 码位 AU+0041 41 1 字节
éU+00E9 C3A9 2 字节
中U+4E2D E4B8AD 3 字节
ᠮU+182E E1A0AE 3 字节 · 蒙文 MA
😀U+1F600 F09F9880 4 字节

3.5 为什么设计成变长？—— 设计思路与历史

前面那张表里藏着一个「故意为之」的设计。这一节讲清它为什么这样做， 以及它是怎么从历史里长出来的。

先看三种「朴素方案」各自的毛病

方案 A：定长 4 字节
每个字符都用 4 字节（这就是 UTF-32）。
好处：定位极简单 —— 第 n 个字符就在第 4n 字节。
毛病：太浪费。一篇纯英文文档体积直接变 4 倍， 而英文内容占互联网的绝大多数。
方案 B：定长 2 字节
每个字符 2 字节（UTF-16 的早期想法）。
好处：比 4 字节省一半。
毛病：装不下。Unicode 有 100 多万个码位， 2 字节最多 65536 个 —— 表情、古文字、罕用汉字全没地方放。
方案 C：变长
按码位大小决定用几个字节（UTF-8 走的就是这条）。
好处：英文 1 字节、汉字 3 字节、表情 4 字节， 又省又能装。
毛病：不能再用「第 n 个字符 = 第 k 字节」直接跳转， 得从头数。
变长编码的核心取舍

用「随机访问变难」换「空间大幅节省」，并且能表示无限多的码位。

这个取舍在当年是对的：网络传输和磁盘存储是瓶颈， 而「从字符串开头数到第 n 个字符」这种操作相对少见。

为什么是 1 / 2 / 3 / 4 字节，而不是别的分法

关键在「前面几个 1」当标志位。先看 UTF-8 的字节形状：

字节数字节的二进制形状说明
10xxxxxxx 最高位是 0 → 说明「这是一个单字节字符」
2110xxxxx 10xxxxxx 开头 110 → 两字节的第 1 个
31110xxxx 10xxxxxx 10xxxxxx 开头 1110 → 三字节的第 1 个
411110xxx 10xxxxxx 10xxxxxx 10xxxxxx 开头 11110 → 四字节的第 1 个
后续10xxxxxx 所有后续字节都以 10 开头，用来看家

这套形状带来三个非常实用的性质：

① 不会认错
看到 10 开头就知道「这是尾巴」， 看到 0 开头就知道「这是新字符」
② 能自同步
就算从中间随便一个字节开始读， 最多跳几个字节就能对上边界，不会一直错下去
③ 英文完全兼容
ASCII 都是 0xxxxxxx， 和 UTF-8 的单字节形式一模一样
性质③ 才是 UTF-8 赢的关键

因为 UTF-8 下的纯 ASCII 内容，字节和几十年前的 ASCII 完全相同。

这意味着：一个存英文的旧文件，用 UTF-8 打开照样正确。 于是从旧编码迁移到 UTF-8 不需要一次性转换所有文件 —— 可以一个文件一个文件慢慢来，新旧混着用也不炸。

对比一下 UTF-16：它在英文里会插入一堆 00 字节， 旧程序读它会看到满屏乱码。兼容性差，是 UTF-16 在文件与网络上输给 UTF-8 的主要原因。

来历：这一切是怎么发生的

按时间线看，能明白为什么会有「变长」这个想法。

时期方案要解决的问题
1960sASCII（7 位） 只有 128 个位置 —— 够英文用，但装不下任何其他语言
1980s各种「代码页」 每种语言各占一个 256 格的表（GBK、Shift-JIS、Latin-1…）。 毛病：同一个字节在不同代码页里是不同字 —— 这就是「乱码」的来源
1988–1991Unicode 诞生 提出「给全世界所有字符统一编号」，一个字符一个码位。 但一开始倾向于「码位就是 16 位」（那时以为字符总数不到 65536）
1992UTF-8 出现 在 Unix 社区设计出来，目标很明确：既要能装全世界， 又要和 ASCII 二进制兼容，好让已有的英文系统平滑过渡
1996 起UTF-16 定型 码位突破了 65536（发现了更多汉字和古文字）， 于是 UTF-16 改成「基本用 2 字节，超出范围时用 4 字节」—— 也成了变长
2000s 之后UTF-8 成为主流 网页、Linux、JSON、源码文件……事实标准。 Windows 内部仍用 UTF-16，这正是 Qt 里 QString 也是 UTF-16 的原因
三条能记住的结论
  1. 变长是为了省空间：不让英文为「全世界字符」买单。
  2. 变长必须「自己认得出边界」： 靠 0 / 110 / 1110 / 11110 这些前缀，让程序不看上下文也能切分字符。
  3. 兼容 ASCII 是它胜出的决定性因素： 能用最小的代价把旧世界接过来 —— 技术方案能不能推广，常常取决于这一点，而不只是它「设计得多好」。

回到我们的代码

现在再看前面那三行输出，含义就清楚了：

再看一次这些字节
ASCII 里的 A (1 字节): 41                     ← 0x41 = 01000001，最高位 0
e 带音标 (2 字节): C3 A9                      ← C3 = 11000011，开头 110

笑脸 (4 字节): F0 9F 98 80                     ← F0 = 11110000，开头 11110

每个字符的第一个字节都在告诉你「后面还有几个字节」—— 这就是变长编码能工作起来的全部秘密。

自己打印出来看复制
#include <stdio.h>
#include <string.h>

void dump_bytes(const char *s, const char *label) {
    printf("%s (%d 字节): ", label, (int)strlen(s));
    for (int i = 0; i < (int)strlen(s); i++) {
        printf("%02X ", (unsigned char)s[i]);
    }
    printf("\n");
}

int main(void) {
    dump_bytes("A", "ASCII 里的 A");
    dump_bytes("\xC3\xA9", "e 带音标 U+00E9");
    dump_bytes("\xE4\xB8\xAD", "中 U+4E2D");
    dump_bytes("\xE1\xA0\xAE", "蒙文 MA U+182E");
    dump_bytes("\xF0\x9F\x98\x80", "笑脸 U+1F600");
    return 0;
}
运行结果
ASCII 里的 A (1 字节): 41 
e 带音标 (2 字节): C3 A9 
中 (3 字节): E4 B8 AD 
蒙文 MA (3 字节): E1 A0 AE 
笑脸 (4 字节): F0 9F 98 80
UTF-8 兼容 ASCII 的好处

看第一行：A 就是 41 一个字节， 和几十年前的 ASCII 完全相同。

这意味着纯英文的旧文件用 UTF-8 打开依然正确， 所以 UTF-8 能顺利取代旧编码，成了今天的主流。

4为什么 char 装不下蒙文

char 是 1 字节（第三讲）：范围 -128~127 或 0~255。最多只能表示 256 个不同的值。

而蒙文字母的码位在 U+1820（十进制 6176）以上 —— 远超 255。所以：

结论

一个 char 装不下一个蒙文字母。 一个蒙文字母在 UTF-8 下要 3 个字节。

这就是第八讲最后那个提醒的原因： 「减 32 变大写」那些规律只对英文字母成立。

于是 strlen 的含义就变了

strlen 数的是字节，不是字母复制
/* ᠮᠣᠩᠭᠣᠯ：6 个蒙文字母，每个 3 字节 */
const char *mongol =
    "\xE1\xA0\xAE\xE1\xA0\xA3\xE1\xA0\xA9"
    "\xE1\xA0\xAD\xE1\xA0\xA3\xE1\xA0\xAF";

printf("strlen = %d 字节\n", (int)strlen(mongol));
运行结果
ᠮᠣᠩᠭᠣᠯ 的 size() = 18 字节（6 个蒙文字母）
用 strlen 得到 18，那不是「几个字母」
你想要的在 C 风格字符串里
几个字母strlen 给不出 —— 它数的是字节
占多少字节strlen(s)  或  s.size()
第几个字母的码位不能用 s[i] —— 那只是第 i 个字节
这是处理多语言文本最容易踩的坑
/* ❌ 想「取第 2 个蒙文字母」，实际取到的是第 2 个字节 */
char second = mongol[1];      /* = 0xA0，半个字符，没意义 */

/* ✅ 要按「字符」处理，必须用能理解编码的类型 */
QString s = QString::fromUtf8(mongol.c_str());
QChar  c = s[1];                 /* 这才是第 2 个字符 */

凡是「按字符」的操作（取第几个、截取、反转、统计字数）， 都不能直接用 char*。

5三种 UTF 编码

同一个码位，有三种常见写法：

UTF-8
变长：1~4 字节
英文 1 字节，汉字/蒙文 3 字节
兼容 ASCII

文件和网络的事实标准
UTF-16
2 或 4 字节
常用字符（含蒙文）都是 2 字节
处理起来「一个字符一个单位」比较直观

Windows 内部、Qt 的 QString 用它
UTF-32
固定 4 字节
一个码位一个单位，最好处理
但很占空间（英文也占 4 字节）

很少用于存文件

同一个「中」，三种编码

码位U+4E2D
UTF-8 E4B8AD 3 字节
UTF-16 4E2D 2 字节
UTF-32 00004E2D 4 字节

C++ 里对应的类型

类型Windows 大小对应
char1 字节 UTF-8 的一个字节（不是字符！）
wchar_t2 字节 Windows 上是 UTF-16；Linux 上是 4 字节（不一致，所以别依赖）
char16_t2 字节 明确的 UTF-16 单元（C++11）
char32_t4 字节 明确的 UTF-32 码位（C++11）
wchar_t 到底多大复制
printf("sizeof(char)    = %d\n", (int)sizeof(char));
printf("sizeof(wchar_t) = %d\n", (int)sizeof(wchar_t));
运行结果（Windows / MinGW）
sizeof(char)    = 1
sizeof(wchar_t) = 2  (Windows 上是 2)
wchar_t 的宽度依平台而异

Windows 上 2 字节，Linux 上 4 字节。所以不要依赖它的宽度。

需要明确宽度就用 char16_t / char32_t。 而跨平台存文件一律用 UTF-8。

6回到本项目

把前面几讲和这一篇串起来，就是 UME 实际会遇到的东西。

① 读文件：字节进来，要「解码」成字符

磁盘上是字节，内存里要字符复制
/* 文件里存的是 UTF-8 字节（蒙文每字母 3 字节） */
QFile f("text.mn");
f.open(QIODevice::ReadOnly);
QByteArray raw = f.readAll();          /* 原始字节，此时还不是「文字」 */

/* 解码：按 UTF-8 解释这些字节，变成字符 */
QString text = QString::fromUtf8(raw);

/* 现在才能按「字符」操作 */
int n = text.size();                   /* 字符个数，不是字节数 */
QChar c = text[0];                     /* 第 1 个字符 */
类型装的是什么什么时候用
QByteArray原始字节 读文件、网络、二进制数据
QString字符（UTF-16） 显示、编辑、按字符处理
Qt 里最该记住的一条

QByteArray 是字节，QString 是文字。 两者之间必须显式「解码 / 编码」，不能直接混用。

QString  s = QString::fromUtf8(bytes);   /* 字节 → 文字（解码） */
QByteArray b = s.toUtf8();                /* 文字 → 字节（编码） */

② 画字：字体是按码位取字形的

要显示一个蒙文字母，流程是：

字符
ᠮ
码位
U+182E
字体里的字形
查 cmap 表，按上下文选 init/medi/fina
绘制
把字形轮廓画到屏幕上

关键点：字体文件里的 cmap 表，就是把码位映射到字形。 一个蒙文字母有多个字形（词首、词中、词尾、孤立）， 具体用哪个要看上下文 —— 这就是「成形（shaping）」。

和字体文件打交道时
  • 码位是 U+182E 这种值，不是字节， 所以查 cmap 时传的是码位。
  • 字体加载失败时，显示出来的「方块」叫豆腐块（tofu）—— 意思是「这个码位在字体里找不到字形」。
  • 一个字体不覆盖某些码位是正常的，不是 bug。

③ 字符串比较与排序

比较蒙文时要注意：按字节比较和按码位比较结果可能不同。 一般做法是先解码成 QString 再比：

比较要按字符复制
/* ❌ 比字节：UTF-8 下不同字母的字节数可能不同，容易出错 */
if (rawA == rawB) { }

/* ✅ 比字符 */
if (QString::fromUtf8(rawA) == QString::fromUtf8(rawB)) { }

7常见乱码与排查

「乱码」的本质只有一句话：写的时候用了一种编码，读的时候用了另一种。

乱码的成因

UTF-8 下「中」是 E4 B8 AD 三个字节。 如果读的时候按 GBK 解释，就会被当成三个 GBK 字符（或两个半）—— 屏幕上就出现看不懂的符号。

字节没变，解释方式变了。

现象常见原因
中文显示成「涓枃」之类的怪字 文件是 UTF-8，被按 GBK 读了
中文显示成「���」 文件是 GBK，被按 UTF-8 读了（解不出来就替换成问号）
蒙文显示成方块 / 豆腐块 不是编码问题 —— 是当前字体里没有这些字形
命令行里中文乱码 cmd 默认 GBK，程序输出 UTF-8。用 chcp 65001 切换
文件开头多出「﻿」 UTF-8 BOM。见下面

关于 BOM

有些 Windows 程序在 UTF-8 文件开头写三个字节 EF BB BF， 叫 BOM（字节顺序标记）。它的作用是声明「这是 UTF-8」。

BOM 带来的麻烦

很多工具不认 BOM，会把它当成正文的第一个字符， 于是文件第一行就莫名多出不可见的内容 —— 写脚本、读配置时经常因此出错。

建议：源文件与数据文件都用「UTF-8 无 BOM」。

（这一点我们在前几讲就踩过：用 PowerShell 的 Out-File -Encoding UTF8 写出的 C 源文件带 BOM， 编译器直接报 ';' expected (got "#")。）

实用排查顺序
  1. 先分清是「编码问题」还是「字体问题」： 显示成方块 → 字体缺字形；显示成乱七八糟的字母符号 → 编码不匹配。
  2. 编码问题就换一种方式重新解码（UTF-8 ↔ GBK）试试。
  3. 项目里统一用 UTF-8 无 BOM，能免掉绝大多数麻烦。
  4. 读文件时永远显式指定编码，不要依赖系统默认。
