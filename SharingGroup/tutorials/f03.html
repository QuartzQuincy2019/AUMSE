Shell 本讲：三步原理 + 头文件与文件依赖

为什么这一篇对本项目重要

点一次「生成」，背后其实有三步。 分成哪三步、每步会报什么错 —— 搞清楚这个， 编译报错就不再是天书，而是「一眼能定位」的信息。 第 7 节还会用一个三文件的真实小工程，讲清声明与定义分别写在哪里。

第 3~6 节用 gcc 讲清原理，第 7 节起改用 MSVC 做对照。 文中的报错、产物路径与命令输出，都是实际跑出来的。

平时练习用的 小熊猫CPP 里，工具栏上并排两个按钮： 左边彩色方块＝编译，右边绿色三角＝运行。 这一篇要讲的，就是「编译」这一个按钮背后，到底替你做了什么。

★1从源码到程序的三步

你写的是 main.c，最后得到的是 main.exe。 中间发生了三件事：

① 预处理
处理所有 # 开头的行： 展开宏、把 #include 的文件内容粘进来
main.c → main.i
② 编译
把 C 翻译成机器指令， 但地址还没填
main.i → main.o
③ 链接
把多个 .o 和库 拼成一个 exe，填好地址
main.o → main.exe

平时一句 gcc main.c -o main.exe 就把三步都做完了。 但报错发生在哪一步，含义完全不同 —— 这就是本篇的核心。

2谁在执行这三步：gcc、MinGW、MSVC

三步不会自己发生 —— 有一个程序在替你执行。这个程序统称编译器。 但在 Windows 上你会同时听到三个名字，很容易混着叫。先把它们分清， 以后装环境、换工具、看报错，才不会一头雾水。

gcc 是什么

gcc 是 GNU Compiler Collection（GNU 编译器集合）的缩写， 它是一整套编译器的名字。日常打交道的两个入口是：

名字管什么 什么时候用它
gccC 语言 写 .c 时用。它不会自动帮你链上 C++ 标准库
g++C++ 写 .cpp 时用。它在 gcc 的基础上多做了 C++ 那一部分

它就是一个可执行文件，躺在磁盘某个目录里，名字叫 gcc.exe / g++.exe。 你在终端敲 gcc main.c -o main.exe，敲的就是它 —— 并不是什么咒语，只是「把参数交给这个程序去干活」。

一个常见坑：文件叫 .c 还是 .cpp

同一份代码，文件名是 .c 时用 gcc， 是 .cpp 时用 g++。用错了通常不是干脆地报错， 而是链接时找不到 C++ 的那几个符号 —— 报错信息会很莫名其妙。 所以先看扩展名，再决定敲哪个。

MinGW 是什么

gcc 原本是 Linux / Unix 上的东西。要在 Windows 上用它， 就得有人把它移植过来 —— MinGW（Minimalist GNU for Windows， Windows 上的极简 GNU 工具集）就是这份移植。

它把 gcc / g++ 连同 Windows 需要的那些运行库打包在一起。 装好 MinGW 之后，它的 bin 目录下就躺着 gcc.exe、g++.exe —— 正是上一小节说的那两个文件。 现在常见的是它的 64 位分支，叫 MinGW-w64。

一句话记住关系：
gcc 是编译器本身；MinGW 是把 gcc 搬到 Windows 上的那份打包。
说「我用 MinGW 编译」，意思就是「我在 Windows 上用的是 gcc」。

MSVC 是什么

MSVC（Microsoft Visual C++）是微软的编译器， 随 Visual Studio 一起安装，命令行里的名字叫 cl.exe。

它不是 gcc，两者互不相干。由此带来一个很实际的后果： 同一份代码，用 MinGW 编可能过，用 MSVC 编可能报错 —— 反过来也一样。 不是谁做错了，而是两家在细节规矩上并不完全一致。

gcc / g++ MSVC
全名GNU Compiler CollectionMicrosoft Visual C++
可执行文件gcc.exe / g++.exe cl.exe
怎么拿到装 MinGW（或 MinGW-w64） 装 Visual Studio
报错长相error: expected ';' before ... error C2143: 语法错误
本篇哪里用第 3~6 节，讲原理第 7 节起，MSVC 对照

报错长相不同，但说的是同一件事。看报错时先分清是哪一家的措辞， 再对号入座 —— 第 8 节会专门讲这件事。

那 小熊猫CPP 用的是哪一个？

用的是 MinGW（具体是 MinGW-w64 + GCC 11.5.0）。 而且它自己就把这件事写在你脸上 —— 见下一小节的截图。 所以你在它里面看到的报错，长得和第 4 节那些 gcc 报错一样。

逐条读，挑重点：

它写的是是什么意思
编译器配置: MinGW-w64 GCC 11.5.0 64-bit Debug 上一小节那三个名字，这里出现了两个：MinGW-w64（打包） 和 GCC 11.5.0（编译器本身及其版本）。 64-bit 指目标程序是 64 位；Debug 是「调试配置」—— 生成的程序带着调试信息，方便设断点。

命令: g++.exe … -o …untitled1.exe 这一条最值得看。-o 后面直接就是 .exe， 中间没有 .i、也没有 .o —— 说明这一条命令把第 1 节那三步一口气全做完了。 第 4、5 节会故意把它们拆开敲，才看得见中间产物。
-Wall 把常用的警告全打开。不加它，很多问题它一声不吭。
-Werror=return-type 「该返回却没返回」这件事，从警告升级成错误， 不让你带着它继续往下走。第 8 节讲错误与警告的分界。
-Werror=vla 变长数组（vla）同样升级成错误。这一条正好呼应 M01 的结论： 方括号里的长度必须是确定的数，不可以是变量。
-Wl,--stack,12582912 -Wl, 的意思是「后面这些不是给编译器，是转交给链接器的」。 这里要求把栈设成 12582912 字节 = 12 MB。 从这一个参数就能看出编译与链接是两件事 —— 第 5 节讲。
错误数: 0 / 警告数: 0 两件事分开数。所以「没报错」和「没问题」不是一回事 —— 警告数不为 0 时，程序照样能生成。
输出文件大小: 107.46 KiB 源码才 5 行，生成的 exe 却有 107 KiB。多出来的是链接时 拼进去的启动代码和标准库 —— 正是第 5 节的内容。
这块信息为什么值得看一眼

很多人点完「编译」，只看一眼「成功」就关掉了。 但这一小块里其实写着谁在编、用什么参数编、有没有警告、产物在哪 —— 真出问题时，这四样恰好就是最先要看的东西。

同一件事，gcc 与 Visual Studio 2026 两种做法

原理是通用的，不分编译器。本讲第 3~7 节用 gcc 这一行命令 把三步「摊开」；Visual Studio 里同样的三步由 IDE 替你按下去， 你只要点「生成」。两者的对应关系是：

对照表
阶段命令行（gcc） Visual Studio 2026
预处理 + 编译 gcc -c main.c -o main.obj 点「生成」时自动做，不用手敲
链接 gcc main.obj helpers.obj -o app.exe 右键项目 → 生成，链接器由 MSBuild 调起
指定头文件目录 -I 目录 C/C++ → 常规 → 附加包含目录
指定库 -L 目录 -l 名字 链接器 → 输入 → 附加依赖项
链接器 → 常规 → 附加库目录
看报错 打印在窗口里 输出窗口 + 错误列表窗口

学会看「哪一步出错」比记住命令更重要 —— 这一点两种方式完全一样。

3预处理：#include 做了什么

#include 不是「引用」，而是「把那个文件的内容原样粘到这里」。

include 是文字替换复制
/* 你写的 */
#include <stdio.h>
int main(void) { printf("hi"); }

/* 预处理之后，等价于（几万行） */
/* ...stdio.h 的全部内容粘在这里... */
int main(void) { printf("hi"); }
想亲眼看？

用 -E 让 gcc 只做预处理就停：

查看预处理结果
D:\Path\To\demo>gcc -E main.c -o main.i
D:\Path\To\demo>dir main.i
main.i    1,234,567 字节     ← 一个 10 行的源文件变成 100 多万字节

这就是为什么 #include 太多会拖慢编译。

<> 和 "" 的区别

写法去哪里找用途
#include <stdio.h> 系统头文件目录标准库、第三方库
#include "my.h" 先找当前目录，再找系统目录自己写的头文件

找不到头文件时报的是预处理期错误：

真实报错（已核对）
nohdr.cpp:1:10: fatal error: no_such_header_xyz.h: No such file or directory

看到 fatal error: ... No such file or directory， 就知道是找文件找不到，而不是代码写错了 —— 先检查路径、拼写、有没有把目录加进搜索路径（-I）。

★4编译：各自翻译

这一步把 C++ 变成机器指令，但只处理一个文件。 输出是 .o（目标文件）：里面机器指令写好了， 但「调用了别人的函数」这些地址还空着。

在 小熊猫CPP 里，这一步就是点工具栏上那个彩色方块按钮 —— 。 它只编译、不运行，所以你不会看到任何运行结果， 得到的只可能是一句「成功」，或者一条报错。

只编译，不链接
D:\Path\To\demo>gcc -c main.c -o main.o
（-c 表示 compile only，到这里就停）
D:\Path\To\demo>dir /b
main.c
main.o        ← 中间产物

这一步报的错是代码本身的错：语法、类型不匹配、 变量没声明、函数参数不对……

真实报错（已核对）
syn.c:1:26: error: expected expression before ';' token
    1 | int main(void) { int x = ; return 0; }
      |                          ^

error: expected ... before ';' token 的意思是 「在 ; 之前缺少了点什么」—— 编译器能精确指到列号，照着改就行。

★5链接：拼起来

把多个 .o 和用到的库拼成一个 exe，同时把地址填好。

问题来了：如果你声明了一个函数却忘了定义它， 编译期看不出来（有声明就够编过了），到了链接期才发现 「这个函数根本没实现」：

只有声明，没有定义复制
int add(int a, int b);      /* 声明了，但没人实现它 */

int main(void) {
    printf("%d\n", add(1, 2));   /* 编译能过，链接会失败 */
}
真实报错（已核对）
ld.exe: lk1.c:(.text+0x6c): undefined reference to `add'
collect2.exe: error: ld returned 1 exit status
认出链接错误的关键字

看到下面这些词，就是链接期问题，不是代码语法问题：

  • undefined reference to ... —— 找不到实现
  • multiple definition of ... —— 同一个东西定义了多次
  • ld.exe / collect2.exe —— 链接器在报错

而编译期错误长这样：error: expected ...、 error: 'x' was not declared。

常见的 undefined reference 原因

原因解决
忘把实现所在的 .cpp 加进编译命令 把它一起写上，或用构建系统管理
函数名拼写不一致（声明和定义不同） 对一下两边签名
声明在 namespace C++ 里，定义不在（或反过来） 名字必须完全一致，包括命名空间
忘了链接某个库 加 -L 目录 + -l 名字 （第 2 节那张 gcc↔VS 对照表里有对应项）
C++ 与 C 混编时没写 extern "C" C++ 会对函数名做「名字修饰」，C 不会 —— 链接时名字对不上

★6头文件为什么存在

既然 #include 就是粘贴，那为什么不直接把代码都写一个文件里？

假设有两个 .cpp，main.c 想用 tools.c 里的 add：

没有头文件时的困境复制
/* main.c —— 编译 main.c 时，编译器不知道 add 长什么样 */
int main(void) {
    printf("%d", add(1, 2));   /* ❌ 编译器：add 是什么？ */
}

/* tools.c —— 定义在这里，但编译 main.c 时看不到它 */
int add(int a, int b) { return a + b; }

每个 .cpp 是独立编译的，编译器不会自动去看别的文件。 所以需要把「这个函数长什么样」抄一份给每个用它的文件 —— 这份「抄件」就是头文件。

tools.h（头文件）
只写声明：告诉别人「有这么个函数，长这样」

int add(int a, int b);
tools.c（实现）
写定义：真正怎么做

#include "tools.h"
int add(int a,int b){ return a+b; }
main.c（使用）
包含头文件，就有声明可用了

#include "tools.h"
printf("%d", add(1,2));
头文件的核心规则
放哪里
函数声明头文件（.h）
函数定义（函数体）.cpp 文件
类 / 结构体的定义头文件（成员函数可以只写声明）
常量头文件里用 const 或 constexpr
全局变量头文件写 extern，某一个 .cpp 里定义

为什么头文件里不能随便写函数体

因为 #include 是粘贴。如果头文件里写了函数体， 被两个 .cpp 包含，那这个函数就被定义了两遍 —— 链接时报 multiple definition。

下面这个例外用到了 C++ 的 inline

「头文件里放函数体」有一个合法的例外：给函数加 inline。 但 inline 是 C++ 的关键字，C 里没有。

它为什么能解决重复定义、以及它另外两层含义， 在第 10 节专门讲。这里先知道「有这么个东西」就够了。

对比C++复制
/* tools.h */
int add(int a, int b) { return a + b; }   /* ❌ 被两个 .cpp 包含就重复定义 */

/* ✅ 头文件里只写声明 */
int add(int a, int b);

/* ✅ 例外：加 inline 可以放头文件（多个定义会被合并） */
inline int add(int a, int b) { return a + b; }

头文件的第一行和最后一行

同一个头文件可能被间接包含多次（a.h 包含 b.h， main.c 两个都包含）。这会导致「同一个类定义了两遍」。 所以每个头文件都要加保护：

include guard复制
#ifndef UME_TOOLS_H          /* 如果没定义过这个名字 */
#define UME_TOOLS_H          /* 那就定义它 */

/* ... 头文件真正的全部内容 ... */

#endif                       /* 结束 */

或者更省事地写一行：#pragma once（几乎所有编译器都支持）。 两种任选一种，但每个头文件都必须有。

★7实际项目中的文件依赖

前面的例子都是「一个 .cpp 打天下」。真实项目里一个类通常拆成 三个文件：头文件一份、实现一份、用它的那个源文件一份。

下面这个三文件的小工程是实际编译链接跑过的，后文的报错也都是它的真实输出。

文件写什么不写什么
widget.h 类的定义（成员函数与成员变量的声明）、 函数的声明 函数体；变量的定义
widget.cpp 成员函数的定义（函数体） 再抄一遍类定义（已经 include 了）
main.cpp 只 #include "widget.h"，然后使用 任何实现细节
这套三文件布局，就是 Qt 项目的基本结构

后面 Q 系列真正动手写界面时，每一个窗口、每一个控件， 基本都是这三件套：

  • widget.h —— 类的定义（class Widget : public QWidget、 槽函数的声明）
  • widget.cpp —— 构造函数、槽函数的实现
  • main.cpp —— QApplication + 创建窗口 + exec()

在 Qt Creator 里新建一个 Widget 项目，生成的就是这三个文件 —— 名字一样、分工一样。所以这一节不是造的玩具例子， 而是本项目后面所有界面代码的骨架。

一句话

头文件放「声明」，源文件放「定义」。

头文件会被多处包含，所以里面不能有「只能有一份」的东西 （函数体、变量的定义）；源文件只被编译一次，所以定义放这里。

widget.h：类写在这里，函数只写声明

widget.h复制
#pragma once
#include <string>

class Widget {
public:
    Widget();                                   /* 声明：构造函数 */
    void setTitle(const std::string& t);   /* 声明：只有分号 */
    std::string title() const;

private:
    std::string title_;                         /* 成员变量 */
};

注意三件事：

  • 类本体（class Widget { … };）写在头文件里 —— 因为 main.cpp 也要用它，而 main.cpp 不该去抄一遍定义。
  • 成员函数只写声明，末尾是分号，没有花括号。
  • #pragma once 防止同一个 .cpp 里把这份内容包含两遍 （第 6 节讲过）。

widget.cpp：定义写在这里

widget.cpp复制
#include "widget.h"

Widget::Widget() : title_("untitled") {}

void Widget::setTitle(const std::string& t) {
    title_ = t;                                 /* 函数体在这里 */
}

std::string Widget::title() const {
    return title_;
}
那个 Widget:: 不能省

成员函数的定义必须带 类名::。漏了它，编译器会把它当成 一个普通自由函数 —— 和类里那个成员函数毫无关系。 编译能过，链接时才炸（见后面的 LNK2019 实测）。

main.cpp：只用，不实现

main.cpp复制
#include "widget.h"
#include <cstdio>

int main() {
    Widget w;
    w.setTitle("UME");
    std::printf("title = %s\n", w.title().c_str());
    return 0;
}

main.cpp 里没有 Widget 的任何实现 —— 它只从 widget.h 知道了「有个类叫 Widget，它有这些函数」， 具体怎么做它根本不需要知道。这就是第 6 节说的「声明是承诺」。

编译与链接：两个 .cpp 各自编译，最后拼起来

实机执行（已核对）
> cl /nologo /EHsc /std:c++17 /c main.cpp widget.cpp
main.cpp
widget.cpp
> link /nologo main.obj widget.obj /out:app.exe
> app.exe
title = UME
产物大小是什么
main.obj48,516 B main.cpp 单独编译的结果；里面只有对 Widget::setTitle 的调用
widget.obj55,519 B widget.cpp 单独编译的结果；定义在这里
app.exe161,280 B 链接器把两个 .obj 拼起来、并接上库之后的结果
为什么两个文件「能对上」

两个 .cpp 都 #include "widget.h"， 于是各自的 .obj 里都存着一份一模一样的「声明」。

main.obj 说「我要调用 Widget::setTitle(const string&)」， widget.obj 说「我这里有 Widget::setTitle(const string&) 的定义」。 链接器看到两边的名字和签名完全一致，就把调用接到定义上。

签名对不上就接不上 —— 这就是下一节 LNK2019 的来源。

#include 就是文本复制。 每个 .cpp 被单独预处理、单独编译，头文件里的内容会被 原样复制进每一个包含它的 .cpp。所以： 头文件里写「只能有一份」的东西，包含它的文件有几个，就重复几份。

三条硬规矩

规矩违反了会怎样（实测）
① 函数体、变量的定义，不写进头文件 LNK2005 重复定义 + LNK1169
② 成员函数的定义要带 Widget:: LNK2019 找不到 Widget::setTitle
③ 头文件要防重复包含 同一个 .cpp 里包含两次 → 类被定义两次

违反规矩 ①：在头文件里写定义

widget.h（错误示范）复制
#pragma once

int twice(int x);              /* ✓ 声明：没问题 */

int twice(int x) { return x * 2; }  /* ✗ 定义：每个 .cpp 各来一份 */

int g_counter = 0;                 /* ✗ 变量的定义，同样各来一份 */
实机报错（已核对，main.cpp 与 widget.cpp 都包含它）
widget.obj : error LNK2005: "int g_counter" (?g_counter@@3HA) 已经在 main.obj 中定义
widget.obj : error LNK2005: "int __cdecl twice(int)" (?twice@@YAHH@Z) 已经在 main.obj 中定义
x.exe : fatal error LNK1169: 找到一个或多个多重定义的符号

两个 .obj 各带一份定义，链接器不知道听谁的，直接报重复。 正确写法：头文件里只留 int twice(int); 和 extern int g_counter;，定义放进某个 .cpp。

一个反直觉的例外：成员函数

如果把成员函数的定义写进头文件（void Widget::setTitle(…) { … } 写在类外面、但仍在 .h 里），MSVC 实测并不报错 —— 成员函数在目标文件里是 COMDAT，链接器会把重复的那些合并掉。

但这只是运气好：标准要求这类定义在全程序里只有一份， 多了就是 ODR 违规。换个编译器、或写法稍有不同，就可能变成 LNK2005。 别依赖链接器替你收拾。

头文件里的函数，哪些要加 inline

「头文件里不能写函数体」有一个合法例外，就是 inline。 但并不是所有写在头文件里的函数都要加它 —— 该加的没加会 LNK2005， 不该加的加了纯属噪音。下面这张表是判断依据：

函数的写法要加 inline 吗 为什么
类体内部直接写出函数体 不用 类内定义隐式就是 inline
类外定义，但仍然写在 .h 里 要 否则每个包含它的 .cpp 各来一份定义
自由函数的定义写在 .h 里 要 同上
模板函数的定义写在 .h 里 不用 模板本来就会在每个用到的地方各实例化一份，语言允许
只声明（末尾分号，没有函数体） 不用 没有定义就不会有多余副本
头文件里的全局常量 inline constexpr C++17 起用它，才允许在头文件里定义
ume_tools.h —— 五种写法混在一个头文件里复制
#pragma once
#include <string>

/* ① 自由函数，定义写在头文件里 → 必须 inline */
inline int clamp(int v, int lo, int hi) {
    return v < lo ? lo : (v > hi ? hi : v);
}

/* ② 模板函数，定义写在头文件里 → 不用 inline */
template <class T>
T maxOf(T a, T b) { return a > b ? a : b; }

/* ③ 只声明，定义在 widget.cpp 里 → 不用 inline */
int parseCount(const char* s);

/* ④ 头文件里的全局常量（C++17）→ 用 inline constexpr */
inline constexpr int kUmeVersion = 2026;

class Widget {
public:
    /* ⑤ 写在类体内 → 隐式 inline，不用写 */
    int id() const { return id_; }

    /* ⑥ 只声明，定义在 widget.cpp 里 → 不用 inline */
    void setTitle(const std::string& t);

private:
    int id_ = 0;
    std::string title_;
};

这个头文件被 main.cpp 和 widget.cpp 同时包含，照样能链接通过、正常运行：

实机运行（已核对）
clamp(-5,0,10) = 0
maxOf(3,9)     = 9
parseCount     = 125
kUmeVersion    = 2026
w.id()         = 0
怎么记

看「这份定义会不会被复制很多份」。 会被复制（自由函数、类外的成员函数、全局常量）→ 加 inline；本来就允许多份（模板）或压根没有定义（只有声明）→ 不用加； 类体内写的已经自动算 inline，再加是多余。

反证：把 ① 的 inline 删掉

只删 `clamp` 前面那个 inline，同样两个 .cpp，立刻变成：

实机报错（已核对）
widget.obj : error LNK2005: "int __cdecl clamp(int,int,int)" (?clamp@@YAHHHH@Z) 已经在 main.obj 中定义
y.exe : fatal error LNK1169: 找到一个或多个多重定义的符号

而 maxOf（模板）、parseCount（只有声明）、 id()（类体内）都没有动，也都不会报错 —— 正对上表里「不用加」的那几行。

违反规矩 ②：漏了 Widget::

实机报错（已核对）
main.obj : error LNK2019: 无法解析的外部符号
    "public: void __cdecl Widget::setTitle(class std::basic_string<…> const &)"
    (?setTitle@Widget@@QEAAXAEBV?$basic_string@…@@@Z)，函数 main 中引用了该符号
x.exe : fatal error LNK1120: 1 个无法解析的外部命令

读法：main 里调用了 Widget::setTitle，但全程序找不到它的定义。 原因就是你把它写成了自由函数 setTitle —— 名字里少了 Widget::，和 main 要的那个根本不是同一个符号。

看报错的第一步：分清是编译错还是链接错

LNK 开头的都在链接阶段，说明每个 .cpp 自己都编译过了，问题出在「拼起来」这一步。第 8 节有那张对照表。

这一节要记住的
  1. 类写头文件，成员函数体写 .cpp，调用者只 include 头文件。
  2. 头文件是「承诺」的集合，源文件是「兑现」。 声明可以有很多份，定义只能有一份。
  3. 每个 .cpp 单独编译；#include 只是把文本复制进去。 两个 .obj 靠「签名一致」在链接时对上。
  4. 链接错的典型长相：LNK2005（定义多了）、 LNK2019（定义找不到）。

8三种错误怎么分

这一节是全篇最实用的部分。看报错信息里的关键字，就能判断问题在哪一步：

阶段典型关键字说明
预处理 fatal error: xxx.h: No such file or directory 找不到文件。检查路径、拼写、-I 目录
编译 error: expected ...
error: 'x' was not declared
error: no matching function		 代码本身有问题。看行号列号去改
链接 undefined reference to ...
multiple definition of ...

一个实用的排查顺序
  1. 先看有几个错误。如果几百个，通常只有第一个是真的 —— 它把后面的都带崩了。先只改第一个。
  2. 看是哪一步（上表）。预处理错先查文件路径。
  3. 如果是链接错，第一反应是：我是不是漏了某个 .cpp？
  4. 从最上面那一条开始改，改完重新编译再看。

8.1 看两条真实输出：错误与警告

上面那张表是「怎么从关键字判断阶段」。再来看一个真实的例子 —— 它把好几件事一次讲清了：

← 图片较宽，可左右滑动查看 →
一段很短的代码，编译器给出的两条输出。 想看清原字可点开放大。

代码只有 5 行有用：

会报错的那 5 行复制
int main(){
    int n = 0;
    scanf("%d", &n);
    int arr[n];   /* ← 长度是个变量 */
    return 0;
}

它错在哪？方括号里的 n 是个变量。 这正是 M01 讲过的结论：长度必须是确定的数，不可以是变量。 而这里的 n 要等到程序跑起来、读到用户输入才知道， 编译器在写代码阶段根本定不下来 —— 于是报错。

把图片下半部分那张表拆开看：

它写的怎么读
In function 'int main()': 先给上下文：下面这些都在 main 里。 别忽略这一行，函数一多它就能省你几分钟。
untitled1.cpp
5 13		 文件名 + 行 5、列 13。精确到列， 所以光标能一按就跳到那个位置 —— 照着改就行。
[错误] variable length array
'arr' is used [-Werror=vla]		 正式的说法：用了变长数组。 方括号里的 [-Werror=vla] 是关键 —— 它说明这条本来是 -Wvla 那条警告， 因为 §2 截图里那个 -Werror=vla，被升级成了错误。 没有那个参数，它会是一条警告，程序照样生成。
[警告] unused variable 'arr'
[-Wunused-variable]		 同一行、同一列，还挂着第二条 —— 警告。 因为 arr 定义完之后一次都没用过。 一行代码可以同时踩好几个坑，而它们分属「错误」和「警告」两类。
cc1plus.exe
some warnings being treated as errors		 这一条的「文件名」不是你的文件，而是编译器内部的一个程序 （cc1plus 就是 gcc 里真正做 C++ 编译的那一步）。 它直译过来是「有些警告被当成错误处理了」 —— 对上一行那个 -Werror 的字面解释。
这张图值得记住的三件事
  1. 错误和警告是分开数的。同一行可以既有错误又有警告 —— 错误挡住你，警告不会。有警告的程序照样能生成、能跑。
  2. -Werror=xxx 能把某类警告变成错误。 这是团队故意设的：与其让你忽略，不如直接拦住。 §2 的截图里就开着 -Werror=vla 和 -Werror=return-type。
  3. 报错信息里的「文件」不一定是你的文件。 看到 cc1plus.exe 这种名字，说明消息来自编译器内部， 通常是在总结全局情况（比如「有些警告被当成错误」）。
那「变长数组」到底能不能用？

换个编译器、把 -Werror=vla 去掉，它可能只是一条警告、能编过。 但本讲统一按「不可以」来讲，理由有两条：

  • 它不是 C++ 标准的一部分 —— 这次能过，换个环境就未必；
  • 长度在运行前就能定下来的话，就该写死或用常量 —— 写得死一点，编译器才能替你检查（M01 就是这个意思）。

长度真的要等运行时才知道（比如读文件、用户输入）， 用 M09《vector 和 array》 里的 vector —— 那才是正经做法。

★9库：静态库与动态库

第 5 节说过：链接就是把多个 .o / .obj 拼起来。 但如果有一堆功能很多项目都要用，总不能每次都把源码拷一遍。 把编译好的目标文件打包起来，就是库。

静态库动态库
Windows 后缀.lib.dll
链接时 把用到的代码复制进 exe 只在 exe 里留一个「引用」
exe 体积大小
运行时需要 不需要额外文件 必须带着 .dll，否则启动就失败
更新库之后 要重新编译 exe 换掉 dll 就行，exe 不用动
适合 工具函数、算法、自己写的公共代码 插件、需要热更新、多个程序共用一份
新手选哪个

先学静态库。它只有一个 .lib 文件要管， 不用操心「dll 放哪、找不到怎么办」，把「怎么把库用起来」这件事先弄懂。

动态库多出来的复杂度全在运行期找 dll 上（搜索路径、版本冲突）， 那是后面的事。

库和头文件是两个东西，别混
它是什么什么时候用
.h 头文件 函数的声明（告诉编译器「有这么个函数，长这样」） 编译时需要 —— 否则 #include 找不到
.lib 静态库 函数的实现（编译好的机器码） 链接时需要 —— 否则报 LNK2019

两个都要给对，缺一个都编不出来。 而且报错发生在不同阶段：少了头文件是编译错，少了 lib 是链接错 —— 正好用上第 8 节那张「三种错误怎么分」的表。

10inline 到底解决什么

8.2 里我在头文件里写了 inline int ume_max(...)， 还写了一行 inline const int kUmeVersion。 现在说清为什么非加不可 —— 这是做静态库时绕不过去的一个点。

10.1 冲突从哪来

先回顾第 6 节的两条规则，它们直接打架：

规则一：头文件靠「粘贴」生效

#include 就是把文件内容原样拷进来。 所以头文件里写的每个函数，在每一个包含它的 .cpp 里都会出现一份。

规则二：一个函数只能定义一次

链接器要求每个符号全局只有一处定义（ODR 原则）。 出现两处就报「重复定义」。

把两条放一起：头文件里写函数体，被两个 .cpp 包含 → 定义了两份 → 冲突。

冲突是怎么发生的复制
// ume_math.h
int ume_max(int a, int b) { return (a > b) ? a : b; }   // 没有 inline

// ume_math.cpp                          // extras.cpp
#include "ume_math.h"                    #include "ume_math.h"
// ↓ 编译后得到一份 ume_max              // ↓ 编译后又得到一份 ume_max

// 链接时：两个 .obj 里都有 ume_max → 冲突

10.2 实测那个报错

我把 inline 去掉、并且让两个 .cpp 都包含这个头文件， 重新生成，得到的是这个（本机实测原文）：

实测报错（去掉 inline 之后）
extras.obj : error LNK2005: "int __cdecl ume_max(int,int)" (?ume_max@@YAHHH@Z) 已经在 main.obj 中定义
x.exe : fatal error LNK1169: 找到一个或多个多重定义的符号

把这句话拆开读，每个部分都有信息：

片段意思
extras.obj 冲突的一方：extras.cpp 编出来的目标文件
已经在 main.obj 中定义 冲突的另一方：main.cpp 编出来的目标文件
"int __cdecl ume_max(int,int)" 人类能读的函数签名
?ume_max@@YAHHH@Z 同一个符号的「修饰名」（见下方说明）
LNK2005 错误码：符号重复定义
LNK1169 它引发的最终结果：链接失败
那个 ?ume_max@@YAHHH@Z 是什么

这叫名字修饰（name mangling）。 C++ 支持函数重载，所以编译器要把参数类型也编进符号名， 这样 f(int) 和 f(double) 才是两个不同符号。

拆开看：?ume_max@@YA 是「全局函数」， H 是 int（H 来自 int 的 「4 字节整数」内部代号），所以 HHH = 两个参数 + 返回值都是 int， @Z 表示结束。

报错里同时给修饰名和可读名，是为了让你能拿去搜索 —— 搜索时用修饰名更准。

10.3 inline 的三层含义

「inline」这个词直译是「在行内」，但它在现代 C++ 里主要不是那个意思。 搞清这三层就不容易混了。

第一层（也是最重要的）：允许在多个 .cpp 里重复定义

这才是 inline 的本职

inline 告诉链接器：「这个函数可能出现在多个 .obj 里，它们是同一份，别报错，随便挑一个用。」

于是「头文件里写函数体」就合法了 —— 这正是静态库/头文件库需要的。

前提是每个定义必须一模一样（同样的代码、同样的名字）。 如果两个地方写得不一致，那是未定义行为 —— 出了怪问题很难查， 所以不要手写两份，一定是同一个头文件被包含。

第二层：建议编译器「直接展开」

这是名字的来源。函数调用本身有开销（压栈、跳转、返回）， 对很短的函数来说这个开销比函数体还大。加上 inline 等于给编译器一个建议：「这个小，干脆把函数体直接填到调用处，省掉调用」。

「展开」是什么意思复制
// 你写的
int m = ume_max(x, y);

// 编译器「展开」之后等价于
int m = (x > y) ? x : y;     // 没有函数调用，直接算
这只是「建议」，编译器可以不听

现代编译器自己就会判断该不该展开 —— 哪怕你不写 inline，它也会把小函数自动展开（尤其开了优化）； 你写了 inline，它觉得不划算也可能不展开。

所以不要为了「快」而加 inline。 要性能就开优化（Release 配置自带 /O2）， 而不是手工到处标 inline。

换句话说：第一层是「必须」，第二层是「随便」。 你加 inline 是为了过链接，不是为了提速。

第三层：类内定义的成员函数「自动」是 inline

这一点M06其实已经用过，只是没说破：

类内直接写函数体 = 自动 inlineC++复制
class Player {
    int hp;
public:
    // 写在类里面 → 隐含 inline，可以放进头文件、被多个 .cpp 包含
    int getHp() const { return hp; }
};

这就是为什么M06的 Player 类整个放在头文件里 也没报重复定义 —— 类内定义的成员函数隐含 inline。 而如果你把 getHp 的函数体写到类外面 （int Player::getHp() const { ... }）并且放在头文件里， 就必须自己加 inline，否则又回到 9.1 那个冲突。

C++17 起：inline 变量

变量也能 inline。看 8.2 里那行：

头文件里的常量复制
// C++17 之前：这样写会「重复定义」，因为每个 .cpp 都有一份
const int kUmeVersion = 2026;

// C++17 起：加 inline，同样允许多份
inline const int kUmeVersion = 2026;

C++17 之前要在头文件里放常量，得用 static const 或 enum 绕； 现在 inline 直接解决。

三条实用规则

情况要不要 inline
函数声明写在头文件、定义写在 .cpp 不用 —— 这是标准做法
函数定义直接写在头文件里 必须加
成员函数写在 class 里面 不用写（隐含 inline）
成员函数定义写在 class 外面、但在头文件里 必须加
头文件里的全局常量（C++17 起） 加 inline
模板函数 不用写（模板本身就有类似待遇）
一句话记住

「头文件里凡是带函数体的东西，都得能让多份共存」 —— 这就是 inline 在现代 C++ 里的主要职责。 看到 LNK2005 / LNK1169， 第一反应就是「头文件里是不是有个函数忘了加 inline？」

这一篇到这里 —— 但真实项目不会这样敲

回头看一遍：本篇每一条命令都是你亲手敲的 —— cl /c 负责编、link 负责链、 -I 找头文件、-L -l 找库。 三五个文件时，这样最快，也最能看清每一步到底在干什么。

但文件一多，手敲就撑不住了，卡在三个地方：

  • 记不住依赖：改一个头文件，到底哪些 .cpp 要重编？
  • 跨平台要重写：Windows 上敲 cl、Linux 上敲 g++， 参数、后缀、库名全不一样
  • IDE 读不懂：Visual Studio 要的是解决方案与工程文件， 不是一串命令行

下一篇 F04 就把这些交给一条四层流水线： 项目描述 → 生成器 → 构建文件 → 构建引擎 → 编译器驱动。 最底下那层还是本篇这个 cl / g++， 只是上面多了几层，替你去记依赖、挑工具、按顺序调度。

而且 F04 会拿本篇第 7 节那个三文件工程 （main.cpp / widget.cpp / widget.h） 原样再走一遍 —— 这次先用 CMakeLists.txt 把它描述出来， 再交给 Ninja、GNU Make、MSBuild 分别建一遍，最后对比三个产物的输出。
