组件化编程与解耦合*

UME 项目组内部教程 · Q06（Q） · 什么叫耦合、高耦合的代价、组件化的三条准则

设计原则 组件化

C++

Q05 的结论是：不能什么需求都往 Actor 里加。

这一篇接着说下去 —— 不能那样加，那该怎么加。 在给方案之前，先把「为什么那样加会出事」说成一个有名字的概念： 耦合。

一句话

耦合 = 两段代码之间的牵连程度。

牵连越多，改一个地方要动的地方就越多。 所谓「解耦」，就是把这种牵连减少到刚好够用。

1什么是耦合

没有牵连的代码是不存在的 —— 只要能一起工作，就有牵连。 问题不在「有没有」，而在有多少、是哪种。

牵连少牵连多
我知道你叫什么名字、怎么用你 我还知道你内部怎么实现的
你改了内部实现，我不用改 你改了内部实现，我跟着崩
想换掉你，只改一处 想换掉你，要翻遍半个项目

三种最常见的「牵连」是这个样子：

类型表现例子
知道别人的内部 直接读写了不该碰的数据 战斗代码直接改 actor.hp， 绕过了 Actor 自己的规则
依赖具体实现 写死了「用哪一个」 刷怪逻辑里写死 new 史莱姆， 加一种怪就得改它
职责缠在一起 一个类里有好几件事 Actor 同时管属性、战斗、背包、地图

★2高耦合与低耦合

用 Q05 那个例子，两种写法摆在一起看最清楚。同一个需求： 角色受到伤害时，要扣血、要触发护盾、要记日志。

高耦合：什么都写在一个类里

高耦合的样子复制
class Actor {
    // ……属性……

    void takeDamage(int dmg) {
        hp -= dmg;
        if (shield > 0) { /* 护盾的事 */ }
        if (hp <= 0) { /* 死亡的事：掉落、经验、复活点 */ }
        log("受伤");              // 日志的事
        refreshUI();              // 界面的事
        if (inParty()) { /* 队友的事 */ }
    }

    void buyItem(int id) { /* 商城、价格、库存、货币 */ }
    void changeMap(int id) { /* 地图数据、传送点、加载 */ }
};
它的症状
  • 一个类要认识所有人 —— 护盾、日志、界面、队友、商城、地图， 全得 #include 进来。
  • 改一处，全都得重测 —— 加一种护盾类型要动 takeDamage，而死亡判定也在里面。
  • 没法单独用 —— 想只测试「扣血」这一件事？ 得先把日志、界面、队友都准备好。
  • 所有人都在改它 —— 管战斗的和管商城的改同一个文件。

低耦合：各管各的

低耦合的样子复制
// ① 角色只管自己的状态和规则
class Actor {
    public:
        void takeDamage(int dmg);   // 只负责改 hp，别的不管
        bool isDead() const;
};

// ② 战斗管流程，它“知道有 Actor 这回事”，但不知道 Actor 内部
class BattleSystem {
    public:
        void hit(Actor& who, int dmg);
};

// ③ 别的事各归各的
class ShieldSystem  { /* 护盾 */ };
class LootSystem    { /* 掉落 */ };
class BattleLog     { /* 日志 */ };

战斗流程变成了「把几件事串起来」，而不是「自己做完所有事」：

BattleSystem::hit 要做的复制
void BattleSystem::hit(Actor& who, int dmg) {
    int left = shield_.absorb(who, dmg);   // 先问护盾
    who.takeDamage(left);                 // 剩下的给角色
    log_.write(who, left);                // 记一笔
    if (who.isDead()) loot_.drop(who);     // 死了才掉落
}

两种写法差在哪

看什么高耦合低耦合
Actor 认识谁 护盾、日志、界面、队友、商城、地图 只有它自己
加一种护盾 改 Actor::takeDamage 只改 ShieldSystem
改日志格式 也在 Actor 里改 —— 有碰坏战斗的风险 只改 BattleLog，碰不到战斗
单独测「扣血」 得先备好日志、界面、队友 直接建一个 Actor 就行
谁在读这个文件 所有人 各自读自己那个
低耦合的好处，说白了三条
  1. 改动不外溢 —— 改一处只影响一处，不用重测一大片。
  2. 能单独替换 —— 想换掉日志实现，改一个类就够。
  3. 能单独理解 —— 想知道护盾怎么算，只看 ShieldSystem。
注意：耦合不是越低越好。把两件事拆得谁也不认识谁， 它们就没法一起工作了 —— 最后要靠一个「谁都认识」的中枢去连， 耦合只是换了个地方。目标是「够用的耦合」， 而不是零耦合。

3为什么低耦合这么重要

Q05 讲过的四条代价，根子都在耦合上。换个说法再点一遍：

代价因为耦合而放大
改动波及面 牵连越多，一次改动牵动的文件越多
回归测试成本 被动过的代码若被别人依赖，所有依赖者都要重测
协作冲突 耦合把多个人的改动挤进同一个文件
理解成本 想知道一件事，得先读懂牵连到的另外几件
一个立刻能用的判断方法

想问自己「这段代码耦合高不高」，就问：

「如果我要把这部分整个删掉重写，需要动几个文件？」

答案是「一个」→ 低耦合；答案是「一片」→ 高耦合。

★4怎么解耦：组件化

解耦不是一句口号，它有一个成型的做法： 把系统拆成一块块「组件」，让组件之间的牵连减到最少。

组件化有三条准则，正好对应第 1 节那三种「牵连」。

准则一：一个组件只做一件事

这条直接治「职责缠在一起」。拆完之后， 每个组件都能用一句话说完自己是干什么的：

Actor 保管角色的状态，并守住状态的规则（血量不超上限）
BattleSystem 按顺序组织一次攻击：护盾 → 扣血 → 日志 → 掉落
ShieldSystem 算出护盾能挡掉多少伤害
Inventory 保管背包里有什么、有多少
MapManager 保管地图数据，负责把角色挪过去

注意最后一条的方向变了：不是「角色会换地图」， 而是「地图管理器把角色挪过去」。角色只需要知道自己现在在哪。

怎么判断「一件事」的边界

如果一句话里出现了「并且」，那多半是两件事：

  • ❌「保管角色状态 并且 算伤害」→ 拆
  • ✅「保管角色状态」→ 一件事
  • ✅「算伤害」→ 一件事

准则二：只依赖「接口」，不依赖「实现」

这条治「依赖具体实现」。想让「加一种新的」不用改老代码， 就得让调用方只知道有个接口，不知道背后是谁。

Q04 讲过的接口在这里正好派上用场。以护盾为例 —— 调用方只需要知道「有个东西能吸收伤害」：

依赖接口，而不是依赖某一个类复制
// 接口：只说“能做什么”，不说“怎么做”
class IShield {
public:
    virtual ~IShield() = default;
    virtual int absorb(Actor& who, int dmg) = 0;
};

// 想加多少种护盾，就加多少个实现 —— 都不用改调用方
class FireShield : public IShield { /* … */ };
class HolyShield : public IShield { /* … */ };

// BattleSystem 只认识 IShield，不认识具体是哪一种
void BattleSystem::hit(Actor& who, int dmg) {
    int left = shield_->absorb(who, dmg);
    who.takeDamage(left);
}
这条准则就是 Q05 那个验收标准的答案

Q05 留了一个问题：「加一种新道具，需要改 Actor 吗？」

依赖接口之后，答案变成「不用」—— 新护盾是一个新类，一个老文件都不用动。

准则三：让数据只从一个口子进出

这条治「知道别人的内部」。Q04 讲过的做法在这里继续用： 状态留在自己家里，外面只能通过接口函数来改。

不要这样复制
// 战斗代码直接改 hp —— 它现在必须知道
// “hp 不能小于 0”“要检查是否死亡”这些规则
actor.hp -= dmg;
if (actor.hp < 0) actor.hp = 0;

// 于是每个改 hp 的地方都得抄一遍这段 —— 漏一处就是 bug

// 换成：规则留在 Actor 里，外面只说“受到伤害”
actor.takeDamage(dmg);

改完之后，hp 的规则只有一份， 而且它写在 Actor 里 —— 谁也不用知道。

Q04 那些 set / get 的问题，也是这一条

给每个字段配一对 setX / getX， 表面上是「通过接口改」，但那个接口只是在搬运字段 —— 调用方照样得知道「有几个字段、各是什么类型、改的顺序有没有讲究」。

真正的解耦是让接口表达一件事（受到伤害）， 而不是暴露一个字段（setHp）。

5组件之间怎么说话

拆开之后，组件总要互相通知。这里有个很容易走偏的地方。

❌ 直接互相调用
// 角色死了，自己去通知一圈
void Actor::die() {
    loot_.drop(*this);
    log_.write(*this);
    ui_.refresh();
    party_.notify(*this);
}

// Actor 又认识了 4 个组件
✅ 只发一个通知
// 角色只报告“我死了”
void Actor::die() {
    dead_ = true;
    onDied(*this);      // 发出去，不关心谁听
}

// 谁关心谁自己订阅：
//   LootSystem 订阅 → 掉落
//   BattleLog  订阅 → 记日志
//   UI         订阅 → 刷新
//   PartySystem 订阅 → 通知队友

右边这种做法（发布 / 订阅）的好处是： 加一个新关心方，Actor 一个字都不用改。 想加个「死亡成就」系统，它自己订阅就行。

这套东西你在 Qt 里已经见过

Qt 的信号与槽就是发布 / 订阅： connect(btn, &QPushButton::clicked, this, &MainWindow::onClicked)。

按钮不认识 MainWindow —— 它只是发出 clicked，谁想听谁自己 connect。 所以同一个按钮可以同时被十处关心，而按钮的代码一行不动。

Qt 把这件解耦的事做成了框架能力， 这也是 Qt 代码里很少见到「一个类认识所有人」的原因。

6组件化之后长什么样

Q05 那个越加越胖的 Actor组件化之后
一个类几百上千行每个组件几十到一两百行
改属性、战斗、背包、地图都在里面 各在各的组件里
加一种新道具要改 Actor 加一个新类 / 一份新数据
改一处 → 重测半个项目 改一处 → 只测那一处
所有人都要读、都要改同一个文件 各读各的，可以并行改
三句话记住这一篇：
① 耦合 = 牵连程度。牵连多 → 高耦合；牵连少 → 低耦合。
② 高耦合的代价是「改动会外溢」 —— 波及面大、要重测、难替换、难读懂。
③ 解耦靠组件化 —— 一个组件一件事、只依赖接口不依赖实现、数据只从一个口子进出。
一句话

好的组件，是可以被整个删掉重写、而不影响别人的那种。

反过来也成立：如果一个组件你不敢动，那它一定耦合得太紧了。
