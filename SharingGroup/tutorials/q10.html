C++ 内存安全 智能指针

这一篇讲智能指针（std::unique_ptr / shared_ptr / weak_ptr）。

但重点不是「怎么用」—— 用法三分钟就能查完。重点是： 它到底替你挡住了哪几类内存错误。所以每一节都从「不用它会出什么事」讲起。

一句话

智能指针不是「更高级的指针」，而是「把释放内存这件事交给类型系统」。 它的对手不是指针，是泄漏、重复释放和悬空指针。

1手动 new / delete 的三类事故

先看清楚敌人。裸指针 + new / delete 的写法， 出错方式其实只有三类，但每一类都很常见。

事故怎么发生后果
泄漏 new 了却忘了 delete； 或者中途 return / 抛异常，跳过了 delete 内存一直占着，程序越跑越胖，最后被系统杀掉
重复释放 同一次 new 被 delete 了两次； 或两份代码都以为自己是所有者 堆结构被破坏，通常当场崩溃，而且现场看不出原因
悬空指针 delete 之后指针没置空，后面又用了它 读到的可能是别人的数据，也可能是垃圾 —— 最难查的一种

最容易被忽略的是「泄漏」里的第二种

忘记 delete 好理解。但「中途退出跳过了 delete」才是 真正让人栽跟头的地方 —— 而且它看起来完全正确：

裸指针 + 提前退出 = 泄漏复制
void load(const char* path) {
    int* buf = new int[1024];

    if (!path) {
        return;              /* ← 泄漏：buf 没人 delete */
    }
    if (!open(path)) {       /* 也可能抛异常 */
        return;              /* ← 又一条泄漏路径 */
    }

    delete[] buf;           /* 只有走到底才释放 */
}

每加一个「提前返回」，就多一条泄漏路径。 靠人工保证「每条路都记得 delete」是不现实的 —— 尤其在多人维护的代码里。

真正的结论

问题不在「你粗心」，而在这种写法要求人记住每一条退出路径。 只要结构上存在「必须手动配对」的地方，早晚会漏。

所以解法不是「更小心」，是换一种结构：让释放由对象生命周期自动触发。

2RAII：把释放绑在对象的生命周期上

这条思路叫 RAII（Resource Acquisition Is Initialization， 资源获取即初始化）。名字拗口，做法只有一句话：

把资源和对象绑在一起：构造时拿到，析构时还掉。
这样一来，「什么时候还」由编译器保证，不由你记性保证。

为什么这能解决上一节的问题？因为 析构函数一定会执行 —— 不管是正常走到函数末尾、提前 return、还是抛异常把栈展开。 这是语言保证的，不需要你写任何东西。

下面这段就是智能指针的全部原理（当然真实实现要复杂得多）：

一个最小的 RAII 包装复制
class IntBuf {
public:
    explicit IntBuf(int n) : p_(new int[n]) { }
    ~IntBuf() { delete[] p_; }          /* ← 一定会执行 */

    IntBuf(const IntBuf&) = delete;            /* 不许拷贝，防止两份都去 delete */
    IntBuf& operator=(const IntBuf&) = delete;

private:
    int* p_;
};

注意那两个 = delete：一旦有了析构函数负责释放， 就绝不能让这个对象被随便拷贝 —— 否则两份副本都以为自己该释放， 就变成上一节的「重复释放」。

这条约束，正是 unique_ptr 和 shared_ptr 的分界线。

3unique_ptr：独占所有权

std::unique_ptr 表达的是：这块资源只有一个主人。 所以它禁止拷贝，只允许转移（move）。

独占：能 move，不能 copy复制
#include <memory>

std::unique_ptr<Widget> a(new Widget);
/* std::unique_ptr<Widget> b = a;        ✗ 编译不过：拷贝构造已被删除 */
std::unique_ptr<Widget> b = std::move(a);  /* ✓ 转移：现在 b 是主人，a 变成空 */

硬要拷贝，编译器会直接拒绝：

实机报错（已核对）
error C2280: “std::unique_ptr<int,std::default_delete<int>>::unique_ptr(
    const std::unique_ptr<int,std::default_delete<int>> &)”:
    尝试引用已删除的函数
note: “std::unique_ptr<int,…>::unique_ptr(const std::unique_ptr<int,…> &)”: 已隐式删除函数

这条报错看着吓人，但只要认出 C2280 和「已删除的函数」， 就知道是你在拷贝一个不准拷贝的类型 —— 改成 std::move 即可。

它怎么保证不泄漏：实测

下面这段用一个「活着几个」的计数器来观察：

转移与提前退出复制
#include <cstdio>
#include <memory>

struct Tracked {
    static int alive;
    int id;
    explicit Tracked(int i) : id(i) { ++alive; }
    ~Tracked() { --alive; }
};
int Tracked::alive = 0;

int main() {
    {
        std::unique_ptr<Tracked> a(new Tracked(1));
        std::printf("created, alive = %d\n", Tracked::alive);

        std::unique_ptr<Tracked> b = std::move(a);
        std::printf("after move, a is null = %s\n", a ? "no" : "yes");
        std::printf("alive = %d (no extra object)\n", Tracked::alive);
    }
    std::printf("out of scope, alive = %d\n", Tracked::alive);

    {
        std::unique_ptr<Tracked> p(new Tracked(2));
        std::printf("before early exit, alive = %d\n", Tracked::alive);
        goto skip;                 /* 模拟提前退出 */
    }
skip:
    std::printf("after early exit, alive = %d (released)\n", Tracked::alive);
    return 0;
}
运行结果（已核对）
created, alive = 1
after move, a is null = yes
alive = 1 (no extra object)
out of scope, alive = 0
before early exit, alive = 1
after early exit, alive = 0 (released)

两件事被证实了：

  • 转移不产生第二个对象：move 之后 alive 还是 1， 只是「主人」从 a 换成了 b。
  • 提前退出也会释放：goto 跳出作用域后 alive 立刻回到 0 —— 没有任何一行代码显式 delete。
优先用 std::make_unique

std::make_unique<Widget>(参数) 比 std::unique_ptr<Widget>(new Widget(参数)) 更好：

  • 只写一次类型，改类型时不会漏
  • 异常更安全：new 成功、智能指针还没构造出来的时候， 如果别的参数求值抛了异常，那块内存就漏了。 make_unique 把分配和接管合成一步，没有这个缝

4shared_ptr：共享所有权与引用计数

需要「多个地方都用这块资源，谁最后放手谁释放」时，用 std::shared_ptr。它内部有一份引用计数， 拷贝一次加一，析构一次减一，减到 0 才真正释放。

运行结果（已核对）
s1 created, use_count = 1
after copy, use_count = 2
copy gone, use_count = 1
all gone, alive = 0

四条对得很整齐：计数归零的那一刻，对象才真正死掉 （alive 从 1 变 0）。这就是「共享所有权」的全部含义。

代价：它比裸指针大

实测这台机器上：sizeof(unique_ptr<int>) = 8（就是一个指针）， sizeof(shared_ptr<int>) = 16（两个指针： 对象地址 + 控制块地址，控制块里放引用计数）。

所以能独占就别共享：unique_ptr 更小、更快、语义更清楚。 shared_ptr 只在确实「谁都可能先用完」时才用。

拷贝是「共享」，不是「复制对象」

这一点最容易搞混：拷贝一个 shared_ptr，不会复制它指向的对象， 只是让计数加一。两个 shared_ptr 指向的是同一块内存。

因此：通过一个 shared_ptr 改对象，另一个也看得见。 如果你要的是「各自一份」，那就是深拷贝，得自己写 —— 智能指针不管这件事。

5weak_ptr：打破循环引用

shared_ptr 有一个致命的结构性缺陷： 两个对象互相持有时，计数永远减不到 0。

下面这段是可运行的、能直接看出泄漏的实验：

成环 → 泄漏；改成弱引用 → 正常释放复制
struct Node {
    std::shared_ptr<Node> next;   /* 强引用 */
    std::weak_ptr<Node>   wnext;  /* 弱引用 */
};

std::weak_ptr<Node> observe;      /* 放在外面，用来观察对象还在不在 */

/* ① 两边都强引用：成环 */
{
    auto a = std::make_shared<Node>();
    auto b = std::make_shared<Node>();
    a->next = b;
    b->next = a;
    observe = a;
}
/* ② 一条改成弱引用：环被打破 */
{
    auto a = std::make_shared<Node>();
    auto b = std::make_shared<Node>();
    a->next  = b;
    b->wnext = a;
    observe = a;
}
运行结果（已核对）
4) cycle, a.use_count = 2
   after scope, expired = 0 (0 = still alive = leak)
5) with weak_ptr, a.use_count = 1
   after scope, expired = 1 (1 = released)

这两行就是全部证据：

  • 成环时 use_count 是 2（a 自己一份 + b->next 一份）， 出作用域后谁也没放手 → expired() 还是 0，说明对象没被释放， 也就是漏了。
  • 改成 weak_ptr 之后 use_count 是 1 （弱引用不计入引用计数）→ 出作用域就归零 → expired() 变 1， 正常释放。
weak_ptr 的三条规矩
  1. 它是「观察者」，不是「所有者」：weak_ptr 构造/析构都不影响引用计数。
  2. 它不能直接解引用：没有 *w 也没有 w->。 必须先 w.lock() 拿到一个临时的 shared_ptr， 再判断是否为空。
  3. 为什么必须这样：如果我刚检查完「对象还在」， 另一个线程就把它释放了呢？lock() 把「检查」和「拿到」 合成一步，不给这个缝。
正确用法：先 lock 再判断复制
std::weak_ptr<Node> w = observe;

if (auto sp = w.lock()) {
    /* 到这里 sp 一定有效，而且在 sp 生命周期内不会释放 */
    std::printf("still alive, use_count = %ld\n", sp.use_count());
} else {
    std::printf("already gone\n");
}
别用 expired() 做「检查再使用」

if (!w.expired()) { w.lock()->doSomething(); } 是典型的错误用法：在 expired() 返回 false 之后、 lock() 之前，对象可能已经被释放 —— 这是竞态。 正确写法只有一种：直接 lock()，然后判断拿到的指针。

6常见错误

错误 1 · 用同一个裸指针造两个智能指针

两次接管同一块内存 = 迟早重复释放复制
int* raw = new int(1);
std::unique_ptr<int> a(raw);
std::unique_ptr<int> b(raw);   /* ✗ 两个「主人」都以为自己该 delete */
/* 程序结束时 a 和 b 各 delete 一次 raw → 重复释放 */

规则：一块 new 出来的内存，只交给一个智能指针。 要么从头就用 make_unique，不要中间经过裸指针。

错误 2 · 拷贝 unique_ptr

就是第 3 节那个 C2280。改法是把所有权转移出去 （std::move），而不是「复制一份」—— 因为按定义就只能有一个主人。

错误 3 · 从 shared_ptr 取出裸指针后又拿去 new

p.get() 只是「借看一眼」，不转移所有权。 拿这个裸指针再去造一个智能指针，就变成错误 1。

get() 的定位

get() 只该用于短时间把裸指针交给不接受智能指针的老接口 （比如某些 C 函数）。用完之后不要再保存它、更不要用它接管所有权。

错误 4 · 用 shared_ptr 成环

第 5 节实测过：expired() 一直是 0，对象永远不释放。 只要图里可能出现环，就必须有一条边用 weak_ptr。

7一页速查

想做的事写法 / 结论
独占一块资源 auto p = std::make_unique<T>(参数);
转移所有权 auto q = std::move(p);（之后 p 为空）
共享所有权 auto s = std::make_shared<T>(参数);
看有多少个持有者 s.use_count()
观察但不持有 std::weak_ptr<T> w = s;
从弱引用安全取值 if (auto sp = w.lock()) { … }
把裸指针交给老接口 p.get()（不转移所有权）
禁止拷贝 unique_ptr 本身就是；自己的类写 = delete
本讲要记住的四句话
  1. 手动 new / delete 的问题是结构性的 —— 每多一条退出路径就多一条泄漏路径，靠小心没用。
  2. RAII 把「什么时候释放」从你的记性交给了编译器： 析构函数一定执行，包括提前 return 和抛异常。
  3. unique_ptr 独占、shared_ptr 共享、 weak_ptr 只观察；能独占就别共享。
  4. shared_ptr 成环必漏，必须用 weak_ptr 打开一条边；取值一律走 lock()。
