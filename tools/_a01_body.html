C++ HarfBuzz 排版引擎

T03 拆过字体文件：cmap 是码位到字形的字典，GSUB 是替换规则， GPOS 是间距规则。那一篇是把字体拆开看。

这一篇反过来：谁来用这些表。答案是排版引擎 —— 本项目选的是 HarfBuzz。它要做的事只有一句：把一串 Unicode 码位，变成 「用哪几个字形、按什么顺序、各占多宽」。

A 系列是写给谁看的

写给项目组长自己 —— 所以默认你已经知道：阿拉伯字母的连写与四形、 天城文的组合与半形、埃及圣书体的转写惯例、日语的混排与竖排、 古典拉丁语的词界与空格、IPA 的宽严式标音、以及音位与变体的关系。

这篇不解释这些概念本身，只解释Harfbuzz 怎么处理它们。 没接触过排版引擎也不影响 —— 前面 45 篇打的地基够用。

1三层分工：谁把文字变成像素

从你敲下一个字，到屏幕上出现笔画，中间过三道手：

层输入 输出谁负责
① 编码按键 / 文本一串码位 编辑器、输入法
② 整形码位 + 字体 + 方向 字形号 + 位置 + 簇 HarfBuzz
③ 栅格化字形号 + 字号位图 / 轮廓 → 像素 FreeType、Skia、Qt
关键：第 ② 层的输出不是图，是「施工单」

HarfBuzz 交出的是字形编号 + 相对位置 + 回指输入的对照表。 没有像素，没有路径，没有颜色。

所以渲染方还得拿着这些编号，回到同一个字体文件去取字模。 编号是字体内部的下标 —— 换个字体文件，同一个编号就是另一个字。

2字形不是字符：四种对应关系

如果你熟悉音位学，这一节可以一句话概括：

用音位学打个比方

字符 ↔ 音位，字形 ↔ 音位变体。

/p/ 在不同环境里念成 [p] 或 [pʰ] —— 那还是同一个音位，只是条件变体。 阿拉伯字母的 BEH 在词首、词中、词尾、单独时是四个字形， 同样是同一个字符的位置变体。

「宽式标音」只写音位，「严式标音」写出变体 —— HarfBuzz 干的就是把宽式变成严式那一步。

四种对应关系，每种都有实例：

关系例子 说明
一对一拉丁字母 a 一个码位一个字形，最常见
一对多天城文 क् 的元音符号、 阿拉伯的 harakat 一个码位拆成基础字 + 附加标记
多对一阿拉伯 لا（LAM+ALEF）、 蒙文 GO 连字 几个码位合成一个字形（连字）
一对变体阿拉伯 BEH 的四形、 蒙文的 init/medi/fina/isol 同一个字符按环境取不同字形号

同一个词，不同字体给不同数量的字形

拿阿拉伯语 لا（LAM U+0644 + ALEF U+0627）实测三支系统字体：

字体码位 字形结果
Arial21 uniFEFB（LAM WITH ALEF ISOLATED FORM）
Times New Roman21 uniFEFB
Segoe UI22 glyph03941 + glyph03980
连字是不是「标准规定」？不是

标准只要求「视觉上必须连成一个」，用几个字形是字体的设计自由。 HarfBuzz 通过 rlig（Required Ligature）去问字体， 字体给什么就用什么。

推论很硬：换字体不能只换字形表。字形数量会变， 你缓存下来的排版结果、光标位置、选区边界统统作废。

蒙文这边是同样的故事，只是数字更夸张。整词 ᠮᠣᠩᠭᠣᠯ 有 6 个码位，整形出 5 个字形：

字形推进量 说明
u182E.M.init492词首
u1823.O.medi573词中
u1829.AG.medi614词中
u182D_u1823.GO.medi838 GA + O 合成的连字 —— 两个码位一个字形
u182F.L.fina383词尾

总数 2900 —— 也就是 2.9000 em（字体 UPEM = 1000）。 这个数和 report/harfbuzz-ground-truth.txt 里的记录一致。

3三张表，三件事

HarfBuzz 不「懂」任何语言。它的全部工作是查三张表、跑两个状态机：

表作用 读成一句话例子
cmap查 这个码位的「名义字形」是几号 U+0628 → uni0628
GSUB换 在某个上下文里，把 A 换成 B beh → uniFE91（initial）
GPOS挪 把 B 往左/右/上/下偏一点 haraka 贴到基字上方

如果按设计模式给它们各起一个名字：

三张表的模式语言
  • cmap 是字典（哈希表）：键是码位，值是字形号。
  • GSUB 是多态替换表 + 上下文策略： 表里存的是「条件 → 替换」，引擎负责匹配条件。 对应到代码就是 map<上下文, 替换>。
  • GPOS 是约束求解的简化版：若干条「相对位置」规则叠加， 最后落到每个字形的 x_offset / y_offset。

阿拉伯的四形走哪条路

BEH（U+0628）在四个位置上落成四个字形，靠的是四条 GSUB 特性， 按顺序跑：

特性的执行顺序（节选）
ccmp  → locl  → isol → fina → finl → init → medi → rlig → calt → liga
       ↑预组合  ↑本地化  └──────── 四形，按加入方向的连写状态挑 ────────┘

实测（Segoe UI，用 U+0640 tatweel 撑出位置）：

位置字形 推进量特性
单独 بuni0628 1881isol
词首 بـuniFE91 684init
词中 ـبـuniFE92 684medi
词尾 ـبuniFE90 1881fina

这四个字形在字体里是现成的（名字就是 FE90 / FE91 / FE92）， HarfBuzz 只是负责挑。蒙文不一样：字体里没预置四种形态， 86.1% 的字形要现场生成 —— 这就是为什么蒙文对引擎的依赖更重。

4一次完整的整形

七个步骤，顺序不能乱：

shape.cpp —— 最小可用流程
#include <hb.h>

/* ① 字体：blob → face → font，三级引用，各管一件事 */
hb_blob_t* blob = hb_blob_create_from_file_or_fail("NotoSansMongolian-Regular.ttf");
hb_face_t* face = hb_face_create(blob, 0);      /* 0 = 第一个字体（ttc 才有多个） */
hb_font_t* font = hb_font_create(face);

/* ② 缩放：不设这一行，后面所有推进量都是 em 单位（UPEM 一千倍） */
hb_font_set_scale(font, px * 64, px * 64);
hb_font_set_ppem (font, px, px);

/* ③ 装文本：QString 内部就是 UTF-16，直接给它 */
hb_buffer_t* buf = hb_buffer_create();
hb_buffer_add_utf16(buf, reinterpret_cast<const uint16_t*>(text.utf16()),
                    text.size(), 0, text.size());

/* ④ 猜属性：script / direction / language 一次到位 */
hb_buffer_guess_segment_properties(buf);

/* ⑤ 整形 —— 真正干活的一行 */
hb_shape(font, buf, nullptr, 0);

/* ⑥ 取结果：两条平行数组 */
unsigned n = hb_buffer_get_length(buf);
hb_glyph_info_t*     info = hb_buffer_get_glyph_infos(buf, nullptr);
hb_glyph_position_t* pos  = hb_buffer_get_glyph_positions(buf, nullptr);

/* ⑦ 用完要还 */
hb_buffer_destroy(buf);

每一步都有对应的坑，后面几节逐个说。这里先记住三条：

三个最常见的错
  1. 忘设 scale：推进量是 em 单位，排出来小了一千倍。
  2. 用 ttb 排蒙文：见第 10 节，实测每一个字形都是 −1750。
  3. 手写 feature 列表：等于覆盖掉默认集，86.1% 的连写全丢。

5缓冲区：一个会改变「内容类型」的数组

hb_buffer_t 是 HarfBuzz 里唯一可变的东西。它有两个阶段：

阶段一　content_type = UNICODE　里面是码位 + 每个码位的 cluster 号
　　↓　hb_shape()
阶段二　content_type = GLYPHS　里面换成字形号 + 位置
这是原地转换，不是新建一份

同一个缓冲区，整形前后长度可以不同（连字会让它变短，分解会让它变长）。 内部是两条平行数组：info[]（字号 + 簇）和 pos[]（推进 + 偏移）—— 典型的 SoA 布局， 比 struct 数组更省一次内存跳转。

用编辑器的话说：这个 buffer 就是一次排版事务的工作区。 所以它该复用，不该每次击键都新建：

函数什么时候用
hb_buffer_create()线程启动时建一次
hb_buffer_clear_contents() 每次整形前清空，保留已分配的内存
hb_buffer_destroy()线程结束时
忘了清空会怎样

上一次的文本还在缓冲区里，这一次的新文本接在后面一起整形 —— 表现为「打一个字，屏幕上多了好几个字」，而且越打越多。 这个 bug 很隐蔽：单次测试永远复现不了。

★6簇（cluster）：编辑器的命根子

cluster 是每个字形身上的一个整数，含义只有一个： 「我对应输入里的第几个字符」。

它存在的理由，是上面那些「多对一 / 一对多」的关系 —— 字形数量和字符数量不一样，你得有办法映射回去，否则光标往哪放？

实测：FVS 与 ZWJ 都不占自己的簇

输入码位 字形簇 : 推进量
蒙文 ᠮ11 c0:632
同上 + FVS1（U+180B）22 c0:632 c0:770
同上 + ZWJ（U+200D）22 c0:492 c0:0
同上 + FVS1 + ZWJ33 c0:492 c0:770 c0:0

三条结论，每条都能直接写成代码规则：

  1. FVS / ZWJ 全部并进 c0 —— 光标移动、退格删除必须按簇走，按字符删会把一个字形拆成两半。
  2. ZWJ 的推进是 0，但它把字形从 632 变成了 492（强制成词首形）。 这就是网页版 globpreview 用 ZWJ 逼出四种形态的原理。
  3. FVS1 把 632 变成了 770 —— FVS 不是「删掉」，是「换一个更宽的字形」。

阿拉伯那边同理

输入码位 字形说明
با（beh + alef）22 beh 取 initial、alef 取 final
بَا（beh + fatha + alef） 33 fatha 推进 0，簇并进 beh

加了 fatha 之后，beh 仍然是 initial 形、alef 仍然是 final 形 —— 透明字符不打断连写。这对你来说应该很眼熟：这正是区别特征里 「加一个不改变音位的成分」的排版版本。

把「簇」当成事务的原子单位

编辑器的所有文本操作都该以簇为最小单位：

  • 退格：删一簇，不是删一个码位
  • 方向键：跳一簇
  • 选区：边界永远落在簇边界上
  • 复制：复制簇对应的原始码位区间，不是字形

违反任何一条，用户看到的就是「删了一个字母，屏幕上少了半个字」。

7方向与脚本：谁决定连写方向

缓冲区身上有三个属性，整形前必须正确：

属性取值 作用
scriptMong / Arab / Deva 决定用哪套连写规则（不同文字的规则完全不同）
directionltr / rtl / ttb 决定连写朝哪个方向接，也决定输出顺序
language如 mn 影响 locl（本地化字形），多数场景可以不设

猜的属性够不够用？实测：够

同一串蒙文，一次用 guess_segment_properties()， 一次显式指定 Mong：

两种做法的结果
guess      → Mong / ltr   字形 5 个   总推进 2900
显式 mong  → Mong / ltr   字形 5 个   总推进 2900

完全一致。所以 不必手动设 script —— 除非你的文本是「一段里混了多种文字」，那要自己切段。

方向传错，不只是左右颠倒

阿拉伯词 مكتبة（5 个码位）两个方向各排一次：

字形号 + 簇号
rtl →  uniFE94/c4  uniFE92/c3  uniFE98/c2  uniFEDC/c1  uniFEE3/c0
ltr →  uniFEE2/c0  uniFEDC/c1  uniFE98/c2  uniFE91/c3  uni0629/c4
  • rtl：簇号 4 → 0（倒序）。第一个字形是最左边的 —— HarfBuzz 已经把视觉顺序排好了，客户端从左往右依次画就行。
  • ltr：簇号 0 → 4，而且字形换了一整批 （uniFEE3 ↔ uniFEE2，词尾形 ↔ 词首形）。
HarfBuzz 不管 bidi

「一段文字里既有阿拉伯文又有拉丁文」，必须先跑 Unicode Bidi Algorithm 把它切成若干单向段， 每段单独 hb_shape，最后按段拼版面。

HarfBuzz 只认「这一段的这一个方向」。数字、标点在阿拉伯文里的方向， 是 bidi 层的判断，不是整形层的。

8特性（features）：默认集与手动覆盖

hb_shape 的第三个参数是一组 hb_feature_t。 它默认是空的 —— 空就是对的。

不要手写特性列表

HarfBuzz 对 script=mong 默认就启用了 isol / init / medi / fina / rclt / ccmp。 你手写一串，看起来是「确保开启」，实际会覆盖掉默认集。

本项目实测过这件事（report/harfbuzz-features-compare.txt）： 手写之后蒙文的连写反而变差。正确做法是什么都不写。

什么时候才需要传？做对照实验的时候：

关掉 rclt 看差别
hb_feature_t f;
hb_feature_from_string("-rclt", -1, &f);   /* 减号 = 关闭 */
hb_shape(font, buf, &f, 1);

这条命令的价值在于：它能证明某个特性确实在起作用。 关掉 rclt 之后蒙文退回孤立字形 —— 一眼就能看出差别。

特性是「策略注入」，不是「参数」

四个常见开关的写法：+liga 开、-liga 关、 kern=0 带值、aalt=2 取第 2 个备选。 它们作用的不是字形内容，而是引擎跑哪几条规则 —— 策略模式里的「换一个策略实现」。

9单位、定点数与那个「一千倍」

HarfBuzz 的所有度量都是定点数：整数除以 64 才是像素。

数类型 含义
x_advance定点数 排下一个字形，笔要往右走多远
y_advance定点数 竖排时往下走多远（横排恒为 0）
x_offset / y_offset定点数 这个字形相对基线偏多少（不推进笔）

换算关系：

两处缩放，别混
字体侧   hb_font_set_scale(font, px*64, px*64);
         ↑ 此后所有度量都是「已经乘过 scale 的定点数」

应用侧   double px_value = pos[i].x_advance / 64.0;
         ↑ 定点数还原成像素

UPEM     只在你不给 scale 的时候才参与运算 —— 那时结果以 em 为单位
UPEM 是 1000 还是 2048，会咬人

Noto Sans Mongolian 的 UPEM 是 1000， 很多传统字体是 2048。如果你跳过 set_scale、 直接拿 x_advance 当像素用，排出来的字会小得几乎看不见 —— 而且换一支字体，大小错的倍数还不一样。

正确做法永远是：先 set_scale，再读结果。

★10竖排：为什么蒙文要走 ltr + 旋转

HarfBuzz 支持 ttb（top-to-bottom）。但对这支蒙文字体， 实测结果是这样的：

方向x_advance 序列 y_advance 序列
ltr492 573 614 838 3830 0 0 0 0
ttb0 0 0 0 0 0 −1750 −1750 −1750 −1750

ttb 给每个字形一律 −1750 —— 因为字体里没有 vmtx（竖排度量表），HarfBuzz 退回到「统一竖排推进」。 这个数不是真的，用它排版会把长短不一的词压成等宽。

所以竖排只能这样做
  1. 按 ltr 横排整形，拿到真实的 x_advance；
  2. 把整个排版结果整体旋转 −90°；
  3. 横排时的「宽度」变成竖排时的「列高」。

这与 FONT_ANALYSIS.md §309 的结论一致： 不依赖字体的竖排度量。

网页版做过更直接的对照：vertical-lr 与 rotate(90deg) 两种引擎并排比，墨迹像素逐位相同，只有起始 x 差一点（旋转基点不同）。 换句话说 —— 竖排不必是引擎的原生能力，几何变换就能办到。

标点要换字形

字体里有 25 个 .vert 变体（竖排标点）。 旋转方案下，这些标点要用 vert 特性换成竖排字形， 否则「（）」旋转后开口方向是错的。

这正是「方向是排版决策、取向是字形决策」两条线分开的证据。

11落到 Qt：从字形号到 QPainter

HarfBuzz 给出编号，Qt 负责画。中间的桥是 QGlyphRun：

draw.cpp —— HB → QGlyphRun → QPainter
QVector<quint32> idx;
QVector<QPointF> pt;
double pen = 0.0;

for (unsigned i = 0; i < n; ++i) {
    idx << info[i].codepoint;                     /* 字形号，两边通用 */
    pt  << QPointF(pen + pos[i].x_offset / 64.0,
                   -pos[i].y_offset / 64.0);      /* 屏幕 y 向下，取负 */
    pen += pos[i].x_advance / 64.0;               /* 64 = 定点精度 */
}

QGlyphRun run;
run.setRawFont(rawFont);                          /* 必须与 HB 用同一个文件 */
run.setGlyphIndexes(idx);
run.setPositions(pt);
painter.drawGlyphRun(QPointF(0, 0), run);
最阴的一个错：字体名一样，文件不一样

HarfBuzz 用的是 A.ttf，QRawFont 却加载了同名的 A'（不同版本）。字形号会整体错位 —— 画出来是别的字，而且不报任何错。

防护办法：把字体文件嵌进资源（QFontDatabase::addApplicationFont）， 让两边都用同一份内存数据。

竖排怎么画

第 10 节说过：横排整形 + 整体旋转。代码上就是先 rotate(-90) 再按上面的方式画 —— 此时 pen 累加的方向从「向右」变成「向下」。

和 QTextLayout 的分工

QTextLayout 内部也是 HarfBuzz。所以两条路可选：

  • 要快、要简单：直接用 QTextLayout， 用 QTextLine::glyphRuns() 取结果，不引额外依赖。
  • 要控制：自己调 HarfBuzz，拿最原始的 codepoint 与 x_advance，方便做缓存、逐簇排版、导 SVG。

本项目的导出功能走的是第二条。

12性能：该缓存的三处

整形本身是纯函数 —— 同样的入参永远同样的出参。纯函数就能缓存：

缓存键 命中率
整形结果 字体 + 字号 + 文本片段 + 特性集 打字时极高：只有改动的那一小段失效
字形栅格 字体 + 字号 + 字形号 极高：同一字形反复出现
整列排版 段落 + 列宽 中等：改一个字只重排一列
两个反面教材

① 逐簇整形。把每个字素簇单独 hb_shape， 连写就断了 —— 蒙文会显示成一串孤立字母。必须整词整形。

② 每次击键整篇重排。一万字的文档，每个键都重排全文， 延迟肉眼可见。正确做法是按段落或按列打脏标记。

整形出了问题，肉眼只能看到「显示不对」。要定位必须能读出字形名。

15换个文字系统：圣书体的四开组

前面十四节讲的都是一维线性文本：一串码位排成一行，难在「选哪个字形」。 圣书体正好反过来 —— 选字形一步几乎不需要，难在把符号拼成方块。

这一节用的引擎是 CheAV 项目的 MdCRndr （assets/egypt/MdCRndr.js，单文件零依赖）与 New Gardiner 字体（OFL 1.1，见 assets/egypt/OFL.txt）。

一码位一静态字形，HarfBuzz 在这儿几乎空转

圣书体的每个符号就是一个字形，没有 init/medi/fina，没有 rclt 连写。 把 𓀀 交给 hb_shape， 出来的就是一串「原样、等宽、无替换」的结果。

所以真正的排版问题换了地方

圣书体不是「一行字」，而是由若干符号组成的一个个方形区块， 古埃及学里叫 quadrat（四开组）。一个区块里的符号要按 视觉平衡摆：谁在上、谁在下、谁占满、谁缩小。

这件事 HarfBuzz 完全不管 —— 它只排一维。一维整形之后， 还得有一层二维组排。

MdC：把「怎么摆」写进字符串

渲染引擎的输入是 MdC（Manuel de Codage，JSesh 风格）。三个符号就够表达布局：

符号含义 例子
-分四开组 S34-N35:AA1 ＝ 两组
*同层并排 A1*B1
:下移一层（堆叠） O49:X1

A1 单个符号：坐着的男子

A1*B1 同层并排

O49:X1 上下堆叠：O49 在上，X1 在下

S34-N35:AA1 先前是你写的顺序，渲染后是两个区块

读序 ≠ 写序

组内符号的摆放顺序由视觉平衡决定，而读音顺序是 MdC 里写的顺序。 上面 O49:X1 读作「O49 然后 X1」，但 O49 画得比 X1 大得多 —— 两个符号的墨迹高度差了三倍多，引擎得把它们塞进一个方框里。

这和 RTL 的「逻辑序 vs 视觉序」是同一类问题

阿拉伯语的字符是逻辑顺序，HarfBuzz 输出的是视觉顺序 （簇号倒序，见第 7 节）。圣书体也是逻辑序 ≠ 视觉序， 只不过错位发生在二维，而且规则是审美而非语法。

HarfBuzz 一个都不管 —— 它只保证「一维的方向对」。

关键：用「墨迹」拼方阵，不能用 advance

第 9 节说过 advance 与墨迹是两回事。圣书体把这条推到极端 —— 拼方阵要用墨迹包围盒，字体给你的 advance 完全不够用。

visumetrics 就是这份数据（EM_SQUARE = 1000， 单位是字体设计单位）：

GardinerUnicode 墨迹宽墨迹高 形状
N35U+13216 983150 水纹：极宽极扁
A1U+13000 695999 坐人：接近满高
B1U+13050 561999妇人：细高
O49U+13296 556584圆形围栏：近方
X1U+133CF 494276面包：扁
换算一下就知道为什么不能用 advance

N35 的墨迹高只有 150，A1 是 999 —— 差 6.7 倍。 如果按字体 advance 拼方阵，一条水纹会和一个人占同样高度， 整个区块立刻歪掉。

所以引擎必须逐字形量墨迹，再按「层高 / 层内宽度」反推缩放比。 这就是 visual metrics 这个文件存在的理由。

放进源码看：它其实就是「这个项目的 umeshape」

对照第 12 节讲过的话 —— 竖排那部分没有现成库可加载，只能自己写，且该做成独立模块。 MdCRndr 就是同一个位置上的东西：

职责HarfBuzz（本项目） MdCRndr（圣书体）
输入码位串 + 字体MdC 串（含布局语法）
选字形cmap + GSUB（重活）查表（轻活）
定位置一维 advance二维组排
输出字形号 + 位置 + 簇DOM（直接出结构）
度量字体 advance墨迹包围盒

注意最后一行：MdCRndr 把「排版」和「出图」合并成了一步（直接吐 DOM）， 而 HarfBuzz 只吐数字、把出图交给 Qt。两种切法都对，取决于谁更复杂 —— 圣书体的二维约束太多，直接生成 DOM 反而更省事。
