前置条件：请先学完「多态与虚函数」

这一篇不是入门。C++ 课本已经详细讲过虚函数与多态， 所以本篇不再解释「什么是虚函数」「为什么基类指针能调到派生类的函数」 「override 起什么作用」——这些都默认你已经会了。

这里只补课本通常讲得不够透的两件事：抽象基类的设计初衷， 以及它在本项目的类型树里究竟怎么落地。

如果还没学过虚函数与多态，请先回去学完再读这一篇。 没有那个基础，下面的「纯虚」「抽象类」会变成死记的语法。

1设计初衷：抽象基类解决什么问题

先说清楚一件事：抽象基类不是为了「让代码更高级」而存在的， 它解决的是一个很具体的问题 ——

问题

有些概念在代码里存在、在现实中却不存在。

我们的游戏里有 Actor（角色）、Enemy（敌人）、 Tools（工具）、Mine（矿）。这些都能在屏幕上看到、能操作。

但「一个 Sprite」是什么？没法回答。 它只是一个统称：凡是能更新、能报出名字的东西，都叫 sprite。 你不会在游戏里放一个「光秃秃的 sprite」。

问题就在这里：既然「一个 sprite」不存在，那它就不该被造出来。 可如果 Sprite 是个普通类，编译器没有任何理由阻止你写 new Sprite —— 而这样造出来的对象没有意义： 它的 update() 该干什么？谁也不知道。

更强的理由是这个：如果 Sprite::update() 不是纯虚的， 你就必须给它写一个函数体。可写在里面的任何东西都是错的 ——

错误示范：给一个「不存在的概念」硬凑实现复制
class Sprite {
public:
    virtual void update() { /* 这里该写什么？ */ }
    virtual ~Sprite() = default;
};

写什么都不对。而只要它有了函数体，派生类忘了重写它，编译器也不会提醒 —— 于是你得到一个「什么都不做」的对象，而且它能通过编译。

抽象基类就是把这个漏洞堵上：它把「必须由派生类实现」这件事写进类型里， 让漏实现从「运行时的静默错误」变成编译期的硬性报错。

一句话概括设计初衷

抽象类 = 只描述「必须有什么」，不提供「怎么做」。 它是一份契约：想成为我的派生类，这几件事你必须自己交代清楚。

2纯虚函数与抽象类的语法

把虚函数写成 = 0，它就是纯虚函数； 含有纯虚函数的类就是抽象类。

抽象基类 Sprite复制
class Sprite {
public:
    virtual ~Sprite() = default;              /* ① 基类析构必须是虚的 */

    virtual void        update()          = 0;  /* ② 纯虚：更新一帧 */
    virtual const char* kindName()  const = 0;  /* ③ 纯虚：叫什么 */
};
能做到
  • 声明数据成员（比如坐标）
  • 写普通成员函数（有实现）
  • 定义构造函数（派生类会用到）
  • 定义虚析构函数
  • 作为指针 / 引用的类型使用
做不到
  • 不能声明对象：Sprite s; ✗
  • 不能 new：new Sprite ✗
  • 不能按值传参 / 按值返回（那要造对象）

「不能造对象」不是限制，正是它的全部意义。

派生类的两条路

派生类的做法结果
把所有纯虚函数都实现具体类 —— 可以 new 了
只实现一部分（或一个都没实现） 它自己仍然是抽象类 —— 仍然不能 new， 并把这个义务继续往下一层传

这条规则很关键，它是中间层能存在的原因（第 4 节会用上）。

编译器怎么报错（实机原文）

① 直接实例化抽象基类：

Sprite s;复制
class Sprite {
public:
    virtual void update() = 0;
    virtual ~Sprite() = default;
};

int main() { Sprite s; return 0; }   /* ✗ */
实机报错（已核对）
error C2259: “Sprite”: 无法实例化抽象类
note: 由于下列成员:
note: “void Sprite::update(void)”: 是抽象的

C2259 这个编号值得记住 —— 它几乎总是「你试图造一个抽象类」。 而且 note 里会指名道姓地告诉你缺哪个函数，照着补就行。

② 派生类漏实现一个：

实机报错（已核对）
error C2259: “Enemy”: 无法实例化抽象类
note: 由于下列成员:
note: “const char *Sprite::kindName(void) const”: 是抽象的

注意报错的措辞：它说「Enemy 无法实例化」， 但列出来的是 Sprite::kindName —— 这就是「义务往下传」的样子：你继承了它，就得替它办完。

3本项目的类型树

本项目的图形对象就是按这个思路分层的。先看全貌：

«abstract» 标注＝抽象类，不能 new  ·  空心三角箭头＝继承（从派生类指向基类）  ·  没标 «abstract» 的四个＝具体类，能 new ← 图较宽，可左右滑动 →

每一层放什么

层性质这一层放的东西
Sprite抽象 只有「所有图形对象共有」的两件事：update()、kindName()。 没有任何数据成员 —— 再往下才谈得上坐标。
Entity抽象 实体共有的：坐标 x, y、血量 hp。 但「一个实体」还是太笼统，不具体。
IntProp抽象 可交互道具共有的：坐标 x, y、耐久 durability。 同样不具体。
Actor / Enemy具体 各自实现 update()：角色回血、敌人扣血。
Tools / Mine具体 各自加自己的字段：efficiency（效率）、 kind（种类），并实现那两个纯虚函数。
一条贯穿全树的规律

越往上，共性越多、特性越少；越往下，共性越少、特性越多。

到了叶子（Actor/Enemy/Tools/Mine）， 才第一次凑齐「能更新 + 能报名字」，所以只有它们能 new。

4中间层为什么也要抽象

初学者常问：既然最后只有叶子能 new， 为什么还要 Entity 和 IntProp 这两层？直接 Sprite → Actor / Enemy / Tools / Mine 不行吗？

行，但你会在两个地方立刻后悔。

理由一：数据成员没地方放

Actor 和 Enemy 都需要 x, y, hp。 如果中间没有 Entity，这两个字段就要在两个类里各写一遍 —— 同一份数据定义写两次，改的时候必然漏一个。

Tools 和 Mine 都需要 durability，同理。 而更关键的是：实体和道具的共有数据并不相同（实体要血量，道具要耐久）， 所以它们不能都塞进 Sprite —— 必须分成两支。

理由二：按「类」做统一操作时没有抓手

假设你想写一个只处理实体的函数（比如「所有实体的碰撞检测」）。 没有 Entity 这一层，你就只能写 void collide(std::vector<Sprite*>&) 然后在里面 用 dynamic_cast 一个个试 —— 既慢又容易漏。

有了 Entity，直接写 void collide(Entity*) 就行， 类型系统替你保证了「进来的东西一定有 hp 和坐标」。

中间层是抽象的，但一点都不「多余」

「抽象」说的是不能直接造对象，不是说没有用。 Entity 这个类型有实实在在的用处：

  • 装共有数据（hp、坐标）
  • 当函数参数的类型（collide(Entity*)）
  • 当容器的元素类型（std::vector<Entity*>）
  • 规定「往下的分支必须是什么形状」

5实际应用：一套接口管四种东西

抽象基类真正的价值，在这里才显出来：你可以用一个容器装下全部四种对象， 用同一个调用更新它们。

完整例子：一棵树、一个容器、一次循环复制
#include <cstdio>
#include <vector>

/* ---------- 抽象基类 ---------- */
class Sprite {
public:
    virtual ~Sprite() = default;
    virtual void        update()          = 0;
    virtual const char* kindName()  const = 0;
};

/* ---------- 中间层：都是抽象类 ---------- */
class Entity : public Sprite {       /* 实体 */
public:
    int x = 0, y = 0;
    int hp = 100;
};

class IntProp : public Sprite {      /* 可交互式道具 */
public:
    int x = 0, y = 0;
    int durability = 100;
};

/* ---------- 具体类：四个叶子 ---------- */
class Actor : public Entity {
public:
    void update() override { hp += 1; }
    const char* kindName() const override { return "Actor"; }
};

class Enemy : public Entity {
public:
    void update() override { hp -= 1; }
    const char* kindName() const override { return "Enemy"; }
};

class Tools : public IntProp {
public:
    int efficiency = 1;                              /* 效率 */
    void update() override { --durability; }
    const char* kindName() const override { return "Tools"; }
};

class Mine : public IntProp {
public:
    enum Kind { Iron, Coal };
    Kind kind = Iron;                                /* 种类 */
    void update() override { --durability; }
    const char* kindName() const override { return "Mine"; }
};

/* ---------- 关键：一个容器装下四种 ---------- */
int main() {
    std::vector<Sprite*> world;
    world.push_back(new Actor);
    world.push_back(new Enemy);
    world.push_back(new Tools);
    world.push_back(new Mine);

    for (int frame = 0; frame < 2; ++frame) {
        std::printf("frame %d\n", frame);
        for (Sprite* s : world) {
            s->update();                              /* 同一个调用，四种行为 */
            std::printf("  %-6s ok\n", s->kindName());
        }
    }

    for (Sprite* s : world) delete s;       /* 虚析构：都能正确释放 */
    return 0;
}
运行结果（已核对）
frame 0
  Actor  ok
  Enemy  ok
  Tools  ok
  Mine   ok
frame 1
  Actor  ok
  Enemy  ok
  Tools  ok
  Mine   ok

请盯住这两行看：

整个例子里最关键的两行复制
std::vector<Sprite*> world;      /* 装的是「Sprite 的指针」 */
s->update();                   /* 调的是「它实际是什么」的 update */
这就是抽象基类的收益
  1. 容器只有一个类型：Sprite*。 不用为每种东西各写一个 vector。
  2. 循环里没有分支：不需要 if (它是 Actor) … else if (它是 Enemy) …。 真按类型写分支，每加一种东西就要改这串 if。
  3. 新增一种对象，循环一行都不用改：写个新类继承 Entity 或 IntProp， push_back 进去就自动被更新、被绘制。 这正是 Q05 讲的开闭原则 —— 对扩展开放，对修改关闭。
别忘了虚析构

上面用 new 出来的对象是通过基类指针删掉的： for (Sprite* s : world) delete s;。

如果 ~Sprite() 不是虚的，这一句只会调 ~Sprite()，派生类的析构函数根本不会执行 —— 派生类里申请的资源就漏了。所以抽象基类的析构函数一定写成 virtual ~Sprite() = default;。

现代写法（知道有就行）

手动 new / delete 容易漏。C++11 起可以用 std::vector<std::unique_ptr<Sprite>>： 存进去就自动管理，连 delete 那一行都不用写。 本篇为了聚焦在「抽象类」上，仍用裸指针。

6常见错误

错误 1 · 直接造抽象类

实机报错（已核对）
error C2259: “Sprite”: 无法实例化抽象类
note: 由于下列成员:
note: “void Sprite::update(void)”: 是抽象的

先看 note，它会列出缺哪些函数。多数情况不是「不该 new」， 而是你 new 错了类型 —— 该 new Actor 却写了 new Sprite。

错误 2 · 派生类漏实现某个纯虚函数

表现和上一条一模一样（也是 C2259）， 但报错的名字变成了你的派生类。看到 C2259 先数一件事： 基类有几个纯虚函数？我一个不漏地实现了吗？

错误 3 · 签名写错，override 帮不了你

这是最隐蔽的一种：把 update 写成 Update。 它算「实现」吗？不算 —— 它只是在你自己的类里加了个新函数， 基类的纯虚函数一个都没被实现。所以这个类仍然抽象。

好消息是：加了 override 编译器会当场指出来：

大小写错了复制
class Enemy : public Sprite {
public:
    void Update() override { }      /* ✗ 基类没有 Update */
};
实机报错（已核对）
error C3668: “Enemy::Update”: 包含重写说明符“override”的方法没有重写任何基类方法
所以：重写虚函数时override一个都别省

有 override，编译器帮你核对签名；没有它，写错就是个静默的新函数， 要等到 new 的那一刻才以 C2259 的形式暴露， 而且报错点在 new 那里，离真正的错误很远。

错误 4 · 纯虚析构函数忘了写函数体

纯虚析构函数是个特例：它可以声明为纯虚，但必须提供函数体。 因为派生类的析构函数执行完，一定会调用基类的析构 —— 它不能「没有」。

声明了纯虚，却没给定义复制
class A {
public:
    virtual ~A() = 0;      /* 只有声明 */
};
/* 少了 A::~A() {} —— 错误 */

class B : public A {
public:
    ~B() override = default;
};
实机报错（已核对）
error LNK2019: 无法解析的外部符号
      "public: virtual __cdecl A::~A(void)"，函数
      "public: virtual __cdecl B::~B(void)" 中引用了该符号
fatal error LNK1120: 1 个无法解析的外部命令

注意这是链接期错误（LNK 开头），不是编译期 —— 编译过了，链接时才说「找不到 ~A 的实现」。补上一行就好：

补上定义复制
A::~A() { }        /* 纯虚析构也必须有函数体 */

错误 5 · 以为纯虚函数「不能有函数体」

= 0 的意思是「派生类必须重写」，不是「基类不写实现」。 纯虚函数完全可以有函数体，派生类还能显式调用它来复用公共部分：

纯虚 + 公共实现复制
class Sprite {
public:
    virtual void update() = 0;                 /* 纯虚 */
    virtual ~Sprite() = default;
};

void Sprite::update() {                       /* 仍然可以给定义 */
    /* 所有对象都要做的公共部分 */
}

class Actor : public Sprite {
public:
    void update() override {
        Sprite::update();                     /* 先跑公共部分 */
        hp += 1;                            /* 再加自己的 */
    }
};

这个写法不算少见，但要记住：它仍然是抽象类，仍然不能 new。

7一页速查

想做的事写法 / 结论
声明纯虚函数 virtual void update() = 0;
抽象类的判定 含至少一个纯虚函数 → 抽象类
派生类成为具体类的条件 把所有纯虚函数都实现（签名完全一致）
派生类只实现一部分 它仍是抽象类，义务继续往下传
抽象类的析构 virtual ~Sprite() = default;（必须虚）
纯虚析构 可以纯虚，但必须给函数体
纯虚函数能有函数体吗 能。派生类可写 Base::f() 复用
抽象类能做什么 数据成员 / 普通成员函数 / 构造函数 / 当指针或引用的类型
抽象类不能做什么 声明对象、new、按值传参或返回
统一管理多种对象 std::vector<Sprite*> + virtual 调用
本项目的树 Sprite → Entity → { Actor, Enemy }
Sprite → IntProp → { Tools, Mine }
本讲要记住的四句话
  1. 抽象类描述「必须有什么」，不提供「怎么做」 —— 它是契约，不是半个实现。
  2. 纯虚 = 派生类必须重写；含纯虚的类不能被实例化。
  3. 漏实现会把抽象性传给下一层 —— 这就是中间层（Entity、 IntProp）能存在的原因。
  4. 收益在容器里兑现：一个 vector<Sprite*> 管住所有对象，新增类型不必改循环。
