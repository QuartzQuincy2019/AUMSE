这一篇讲互斥锁（std::mutex）。

和上一篇一样，重点不在「怎么加锁」，而在 它到底挡住了什么、以及加错了会出什么事。 所以先看一个能直接跑出错数的实验，再讲怎么修。

一句话

互斥锁保护的不是变量，是「一段代码同时只能有一个线程在里面」。 你要保护哪些操作，就把这段代码锁起来。

1竞态条件：非原子的读改写

8 个线程，每个把同一个计数器加 5 万次，最后应该得到 40 万。先不加锁跑一遍：

不加锁复制
#include <cstdio>
#include <thread>
#include <vector>

int main() {
    const int N = 8, M = 50000;
    long long counter = 0;

    std::vector<std::thread> ts;
    for (int i = 0; i < N; ++i)
        ts.emplace_back([&] { for (int k = 0; k < M; ++k) ++counter; });
    for (auto& t : ts) t.join();

    std::printf("counter = %lld  (expect %lld)\n",
                counter, (long long)N * M);
    return 0;
}
运行结果（已核对）
counter = 122439  (expect 400000)
这个数字每次都不一样

我这台机器上跑过 122439、122856、139002 三个数， 每次都不相同；极小概率下也可能碰巧得到 400000。 「跑一次是对的」不能证明没问题 —— 这正是竞态最麻烦的地方。

为什么丢：++counter 不是一步

看起来是一个动作，机器层面是三步：

① 读：把 counter 的值读进寄存器
② 加：寄存器里的值加 1
③ 写：把寄存器里的值写回 counter

只要两个线程在 ① 和 ③ 之间交错，就会丢：

线程 A 读到 100 → 加一得 101 → 还没写回
线程 B 也读到 100 → 加一得 101 → 写回 101
线程 A 写回 101
结果 加了两次，值只涨了 1 —— 丢掉一次更新

这叫竞态条件（race condition）：结果取决于线程的调度顺序， 而调度顺序不是你决定的。

2std::mutex 与 lock_guard

std::mutex 只有两个动作：lock() 和 unlock()。同一时刻只允许一个线程持有它，其余线程会等。

但不要手写 lock() / unlock() —— 理由和上一篇完全一样：中途 return 或抛异常，unlock() 就被跳过了，锁永远不释放，其他线程全部卡死。这种错误比数据错更糟， 因为程序会「静默地不再前进」。

正确做法是 RAII 的 std::lock_guard：构造时加锁，析构时解锁。

lock_guard：把解锁绑在析构上复制
#include <mutex>

std::mutex m;

/* 每个线程做： */
for (int k = 0; k < M; ++k) {
    std::lock_guard<std::mutex> g(m);   /* 加锁 */
    ++counter;                          /* 临界区：只有一段 */
}                                       /* g 析构 → 自动解锁 */
运行结果（已核对）
2) lock_guard  : 400000

40 万，一分不差。

临界区 = 被锁住的那几行

从 g 构造到 g 析构之间的代码叫临界区。 它同时只能有一个线程在里面 —— 这是「正确」的代价： 并发被这一段串行化了。所以临界区要尽量小，只包住真正需要保护的操作。

3临界区粒度：循环内与循环外

上面那个例子每加一次就加解一次锁，一共 40 万次。能对，但很慢。 如果我们只是想让每个线程把自己的 5 万次加完，可以把锁放到循环外面：

锁一次，包住整个循环复制
std::lock_guard<std::mutex> g(m);
for (int k = 0; k < M; ++k) ++counter;
运行结果（已核对）
3) lock once   : 400000

结果一样对，但这两段的差别不在正确性，在并发度：

锁的位置临界区效果
循环里（每次一个）一行 ++counter 8 个线程能交替进，但加解锁 40 万次，大部分时间花在锁上
循环外（锁一次）整个 5 万次循环 加解锁只有 8 次，但8 个线程变成完全串行， 等于单线程跑 8 遍
怎么选

看循环体里有没有「必须一起完成」的约束：

  • 如果每一次自增都是独立的，你只是想让总数对 → 锁外面更好（或者干脆用第 5 节的 atomic）。
  • 如果循环里还有别的共享状态、而且中间不能让别的线程插进来 → 只能锁外面。

反过来说：锁外面的写法牺牲了全程并发，如果那段代码要跑很久， 其他线程会一直等 —— 这时要考虑把工作拆开，而不是把锁放大。

4unique_lock：需要手动控制的场合

lock_guard 最简单，但它不能中途解锁， 也不能「先构造、晚点再锁」。需要这些时用 std::unique_lock：

lock_guardunique_lock
构造即加锁是是（也可 std::defer_lock 先不加）
中途 unlock()不行可以
能移动 / 传给函数不行可以
开销几乎没有略大（要记「当前锁没锁」）

默认用 lock_guard；确实需要「锁一会儿、放开、再锁」时才换 unique_lock。典型场景是条件变量、或者「锁内做一份快照， 锁外慢慢处理」：

锁内取快照，锁外处理复制
std::vector<int> snapshot;

{
    std::lock_guard<std::mutex> g(m);
    snapshot = sharedList;          /* 只复制，很快 */
}                                   /* 这里就解锁了 */

for (int v : snapshot) {           /* 耗时的处理在锁外做 */
    process(v);
}

这个模式比「拿着锁跑完整个处理」好得多：临界区只包含一次拷贝， 其余线程几乎不用等。

5两把锁：死锁与 scoped_lock

需要同时锁两把锁时，顺序不一致就会死锁：

❌ 会死锁
/* 线程 1 */
lock(m1);
lock(m2);   /* 等 m2 */

/* 线程 2 */
lock(m2);
lock(m1);   /* 等 m1 */
✅ 一次锁住两把
std::scoped_lock g(m1, m2);
/* 两把一起拿到，
   内部用「避免死锁」的
   算法，不会互相等 */

两个线程各拿到一把、又都在等对方那一把 —— 谁也走不了，程序卡死。 而且它不一定每次都发生，取决于调度，所以测试时可能一直正常。

修法不是「小心保持顺序」（约定靠人守不住），而是一次把两把都锁上。 C++17 的 std::scoped_lock 就是干这个的：

运行结果（已核对：8 线程 × 2000 次，没有卡死）
4) scoped_lock : a=16000 b=16000
为什么这里不能「先锁 m1 再锁 m2」

只要你写的是两次独立的 lock，中间就存在「已经拿着 m1、 还没拿到 m2」的状态。别的线程只要此时反向来一次，就能凑成环。

scoped_lock 把「锁两把」变成一个不可分割的动作， 从结构上消掉了那个中间状态。

6不必加锁的场合：单变量原子操作

如果共享的只是一个计数器，锁是重武器：std::atomic 就够了，而且没有「忘记解锁」的风险。

atomic：单变量的原子操作复制
#include <atomic>

std::atomic<long long> counter{0};
/* 各线程里 */
++counter;                       /* 这是一步，不会丢更新 */
运行结果（已核对）
5) atomic      : 400000
atomic 的边界

atomic 只保证单个变量的操作不可分割。 一旦你要保护的是两个变量之间的一致性（比如「扣钱」和「加货」必须一起成功）， 就必须用锁 —— 两行 atomic 加起来不是原子的。

7常见错误

错误 1 · 手写 lock() / unlock()

中途 return 就漏掉 unlock()，锁再也不释放， 其他线程全部永久等待。用 lock_guard，不要手写。

错误 2 · 只锁了一部分

读了两次，只锁了一次复制
/* ✗ 无效：锁只包住了一次读 */
{
    std::lock_guard<std::mutex> g(m);
    if (counter > 0) flag = true;
}
/* 两行之间别的线程可能已经改了 counter，判断和取值不是一个整体 */

凡是「必须一起成立」的读和写，都要在同一把锁里。

错误 3 · 锁的粒度太大

在临界区里做耗时的事（读文件、打印、等网络），等于让所有线程排队等它。 临界区只放必要的几行；耗时的处理放到锁外（第 4 节那个快照模式）。

错误 4 · 两把锁顺序不一致

就是第 5 节的死锁。用 scoped_lock 一次锁住， 或者从设计上避免「同时需要两把锁」。

错误 5 · 以为「没加锁但也没出错」就是对的

竞态的表现就是时对时错。不加锁的版本跑一次得到 40 万， 完全可能 —— 但代码依然是错的。

8一页速查

想做的事写法 / 结论
保护一段代码 std::lock_guard<std::mutex> g(m);
需要中途解锁 / 传给函数 std::unique_lock<std::mutex> g(m);
同时锁两把 std::scoped_lock g(m1, m2);
只保护一个计数变量 std::atomic<int> n{0};
临界区该多大 只包住「必须一起成立」的几行；耗时处理放锁外
锁的顺序 不要靠约定；要同时锁就用 scoped_lock
怎么确认真的修好了 跑多次；一次对不算数（竞态时对时错）
本讲要记住的四句话
  1. 竞态的来源是「看起来一步、实际三步」：读、改、写中间被插队就丢更新。
  2. 锁保护的是「一段代码」，不是「一个变量」 —— 凡是必须一起成立的读写，都要在同一把锁里。
  3. 用 RAII 包装，不手写 lock / unlock： lock_guard 就是「把解锁绑在析构上」。
  4. 两把锁要用 scoped_lock 一次锁住， 靠「保持顺序」的约定迟早会破。
