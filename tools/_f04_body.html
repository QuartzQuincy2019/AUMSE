这一篇讲构建系统：你写的那几行项目描述，是怎么一步步变成 一条条编译器命令的。

会出现的名字有点多 —— CMake、qmake、CMakeLists、Makefile、.sln、 Ninja、GNU Make、MSBuild。别怕，它们其实只是同一条流水线上的四个岗位， 每个岗位都有好几个「同岗不同人」的实现。看完这一篇，你应该能做到： 听到任何一个名字，立刻知道它站在哪一层、上面是谁、下面是谁。

1一条四层流水线

先看全貌。这张图是这一篇的地图，后面每一节只放大其中一层。

图里的箭头就是数据流：上一层的产物是下一层的输入。 竖着读一遍，就是一次构建的完整路径。

先记住这一句

除了最下面那层，没有任何一层在真正「编译」你的源码。

CMake 不编译，qmake 不编译，Ninja 也不编译 —— 它们的活是 把「要做什么」翻译成「谁在什么时候调哪条命令」。 真正把 .cpp 变成 .obj 的，只有最底下那个 g++ / cl.exe。

层输入 谁来干输出
① 项目描述你手写的文本 （不干，是你写的） CMakeLists.txt / .pro
② 生成器CMakeLists.txt / .pro CMake / qmake 构建文件（下一行那三种）
③ 构建文件生成器的输出 （不干，是文件） build.ninja / Makefile / .sln+.vcxproj
④ 构建引擎构建文件 Ninja / GNU Make·nmake / MSBuild 一条条编译命令
⑤ 编译器驱动一条条命令 + 源码 g++ / cl.exe .obj → .exe

图里画的是 4 层（把「项目描述」当输入、不算一层）， 上表把项目描述也算进来，所以是 5 行。两种数法都对，看你要不要把它当岗位。

2为什么要有这些东西：只有编译器行不行

看完那张四层图，正常的第一反应是：至于吗？

先把话说清楚：只有编译器也能编，而且真能编。 上一篇（F03）里我们就这么干过 —— 两条命令，两个 .cpp 变成一个 exe：

只有编译器（F03 的做法，已核对）
> cl /nologo /EHsc /std:c++17 /c main.cpp widget.cpp
> link /nologo main.obj widget.obj /out:app.exe
> app.exe
title = UME

那为什么真实项目还要在上面堆四层？ 因为手工敲命令有三件事，人做不到、但机器可以。

做不到 ①：记住依赖关系

改一行 widget.h，哪些 .cpp 需要重编？凡是 include 它的都要。

我们只动了 widget.h（一个 .cpp 都没改），再构建一次：

实机执行（只 touch 了 widget.h）
> ninja -C b
[1/3] Building CXX object CMakeFiles/demo.dir/main.cpp.obj
[2/3] Building CXX object CMakeFiles/demo.dir/widget.cpp.obj
[3/3] Linking CXX executable demo.exe

两个 .cpp 都重编了，因为两个都 #include "widget.h"。 两个文件还好记；二十个文件、三层嵌套的 include 呢？ 这张图人脑存不下，构建文件存得下。

做不到 ②：一份描述，多个平台

同一份源码，Windows 上要 cl.exe，Linux 上要 g++， 参数、后缀、库名全不一样。没有「生成器」这一层，就得 为每个平台各维护一套命令，而且它们会慢慢走歪。

有了生成器，你只写一份项目描述，换平台只是换一个 -G：

同一份 CMakeLists.txt（第 3 节会细讲）
cmake -B b -G Ninja              → build.ninja
cmake -B b -G "MinGW Makefiles"  → Makefile
cmake -B b -G "Visual Studio …"  → .sln + .vcxproj

做不到 ③：让 IDE 也读懂

人能读 Makefile，但 Visual Studio 要的是「解决方案 / 项目 / 配置 / 平台」 这整套概念 —— 它要拿这些去画配置面板、做跳转、下断点。 所以才有 .vcxproj 这种 XML。这不是重复劳动， 是给不同读者看的同一种信息：给人看一份，给 IDE 看一份。

每一层到底替你省了什么

层没有它，你得手工做 它替你做的
项目描述 把「有哪些文件、编成什么、用哪个标准」记在脑子里 / 每次现敲 把这份知识写成文件，能进版本库、能被别人复用
生成器 为每个平台、每种 IDE 各写一套命令 一份描述 → 多种后端
构建文件 自己记「谁依赖谁、改了什么要重编什么」 把依赖图写成机器可读的表
构建引擎 按正确顺序、逐个文件敲命令（还不敢并行） 按图调度，只重做该重做的，能并行
编译器驱动 —— 这个本来就得你自己敲，它就是干活的
这些层不是「编译器的一部分」

它们是规模变大之后，把重复劳动沉淀成文件的结果。

项目小的时候，这些层确实只是负担；项目一大，它们省下的是 每次改一个头文件都要猜「该重编哪些」的那种时间 —— 以及猜错的代价。

那什么时候真的只需要编译器

  • 单文件、几十行：验证一个语法、试一段库函数 —— 直接 g++ x.cpp -o x 最快，写 CMakeLists 反而是浪费。
  • 两三个文件、一次性的小实验：像 F03 那个 main.cpp + widget.cpp + widget.h，两条命令搞定。
  • 不打算长期维护、不跨平台的临时程序。

一旦越过这条线 —— 文件多了、要给别人编、要上 CI、要跨平台 —— 手工命令就开始还债了。债的形式是：忘了重编某个文件、 在自己机器上能编别人机器上不能、换个编译器全量报错。

所以上一篇为什么先教手敲

F03 让你直接用 cl / g++，不是为了复古，是因为 不知道最底下那层在干什么，用 CMake 报错时你连该看哪一层都不知道。

先会最底层，再学自动调度 —— 顺序不能反。

3项目描述：CMakeLists.txt 与 .pro

这是唯一由人写的一层。它只回答三个问题： 源码有哪些、产物叫什么、用什么标准编。

CMakeLists.txt（CMake 读）复制
cmake_minimum_required(VERSION 3.16)
project(demo CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_executable(demo main.cpp widget.cpp)
demo.pro（qmake 读）复制
TEMPLATE = app
TARGET   = demoq
CONFIG  += console c++17
CONFIG  -= qt app_bundle
SOURCES += main.cpp widget.cpp
HEADERS += widget.h

两份文件语法完全不同，说的是同一件事：

要表达的事CMakeLists.txtdemo.pro
产物是个可执行文件add_executable(…)TEMPLATE = app
产物叫什么第一个参数 demoTARGET = demoq
源码有哪些main.cpp widget.cppSOURCES += …
用 C++17CMAKE_CXX_STANDARD 17CONFIG += c++17
选哪个

新项目用 CMake。它是事实标准，CMake 能生成的后端比 qmake 多得多 （下一节就有清单）。

qmake 是 Qt 自己的老工具，Qt 5 时代到处是它；Qt 6 起官方主推 CMake， 但 qmake 仍在维护，遇到老项目必须看得懂 .pro。

4生成器：CMake 与 qmake

生成器的活只有一件：读项目描述，写构建文件。 它不编译，也不链接 —— 跑完你只会在目录里多出一堆文件。

同一份 CMakeLists.txt，换一个 -G 就换一种后端

-G 是 generator（生成器）的缩写。我们这台机器上实测：

实机执行（同一份 CMakeLists.txt，三个不同的 -G）
> cmake -S . -B b-ninja -G Ninja
-- Configuring done (3.4s)
-- Generating done (0.0s)
-- Build files have been written to: …/b-ninja

> cmake -S . -B b-make -G "MinGW Makefiles"
-- Configuring done (2.4s)
-- Generating done (0.1s)
-- Build files have been written to: …/b-make

注意最后那行的措辞：Build files have been written —— 它说的是「写文件」，不是「编译完成」。这就是生成器这一层的全部工作。

-G 后面能跟什么

cmake --help 会列出本机支持的全部生成器（节选）：

cmake --help（节选，已核对）
Visual Studio 17 2022        = Generates Visual Studio 2022 project files.
* NMake Makefiles              = Generates NMake makefiles.
MSYS Makefiles               = Generates MSYS makefiles.
MinGW Makefiles              = Generates a make file for use with mingw32-make.
Unix Makefiles               = Generates standard UNIX makefiles.
Ninja                        = Generates build.ninja files.
Ninja Multi-Config           = Generates build-<Config>.ninja files.

带 * 的是本机默认。同一个项目描述，后面接什么构建引擎， 全看你给哪个 -G —— 这就是「等价关系」最直接的证据。

qmake 也一样的两个后端

实机执行（qmake 6.12，MSVC 套件）
> qmake ..\demo.pro -tp vc
Info: creating stash file .qmake.stash
（生成 demoq.vcxproj）

> qmake ..\demo.pro
（生成 Makefile、Makefile.Debug、Makefile.Release）

-tp vc 是「template = Visual Studio C++ project」， 意思是改出 Visual Studio 工程；不加则是默认的 Makefile。

生成器命令实际产出（本机实测）
CMake
3.30.5		 cmake -B b -G Ninja build.ninja 18,914 B
cmake -B b -G "MinGW Makefiles" Makefile 6,092 B
qmake
6.12		 qmake demo.pro -tp vc demoq.vcxproj 9,513 B
qmake demo.pro Makefile 33,740 B（另有 .Debug/.Release 两个）

5构建文件：三种名字，一种内容

这一层是中间物，不长在源码树里（一般放在 b-xxx/ 这种构建目录）， 你可以整目录删掉重建 —— 因为它们不是手写的，是可再生的。

文件谁生成谁消费
build.ninja CMake -G Ninja Ninja
Makefile CMake -G "…Makefiles"
或 qmake（默认）		 GNU Make / mingw32-make / nmake
.sln + .vcxproj CMake -G "Visual Studio …"
或 qmake -tp vc		 MSBuild
三种构建文件，本质是同一张表

它们都在写同一件事：「哪个产物依赖哪些输入、过期了就用哪条命令重做」。

差别只在语法和表达能力：Ninja 极简（只给机器读，快）， Makefile 靠 Tab 缩进（人和机器都读），MSBuild 是 XML（能塞很多 IDE 属性）。 换一种写法，依赖关系本身不变。

6构建引擎：Ninja、GNU Make、MSBuild

引擎读构建文件，决定哪些目标过期了，然后逐条执行命令。 你平时敲的「生成 / 构建 / Build」按钮，按的就是这一层。

三个引擎的进度输出长得完全不一样，但说的都是同一件事（本机实测原文）：

Ninja（读 build.ninja）
> ninja -C b-ninja
ninja: Entering directory `b-ninja'
[1/3] Building CXX object CMakeFiles/demo.dir/widget.cpp.obj
[2/3] Building CXX object CMakeFiles/demo.dir/main.cpp.obj
[3/3] Linking CXX executable demo.exe
GNU Make（mingw32-make，读 Makefile）
> mingw32-make -C b-make
[ 33%] Building CXX object CMakeFiles/demo.dir/widget.cpp.obj
[ 66%] Building CXX object CMakeFiles/demo.dir/main.cpp.obj
[100%] Built target demo
MSBuild（读 .vcxproj）
> MSBuild demoq.vcxproj /p:Configuration=Release /p:Platform=x64
  main.cpp
  widget.cpp
正在生成代码...
  demoq.vcxproj -> …\release\demoq.exe

三种进度条后面，跑的都是同样的两步：先把每个 .cpp 编成 .obj，再把 .obj 链接成 .exe。 本章上一篇（F03）手工敲 cl /c 和 link， 做的正是这两步 —— 引擎只是替你按依赖顺序调度它们。

那 MSBuild 和另外两个的差别在哪

Ninja 与 Make 只认「文件依赖」，非常薄； MSBuild 认得解决方案、项目、配置、平台这一整套概念， 所以它能被 Visual Studio 直接打开、能在 IDE 里跳转。 代价是它读的那套 XML 文件比 Makefile 啰嗦得多。

7编译器驱动：g++ 与 cl.exe

流水线的最底下才是真正的编译器。上面前两种引擎都调 g++ （因为 -G` 选的是 MinGW 系），MSBuild 调 cl.exe。

三种路径跑出来的程序一模一样（本机实测）：

三个可执行文件，同一个输出
demo.exe   （CMake + Ninja 编出来的）      title = UME
demo.exe   （CMake + MinGW Makefiles）     title = UME
demoq.exe  （qmake + MSBuild，14,848 B）   title = UME
这一层你其实已经会了

F03 里手敲的 cl /c main.cpp widget.cpp + link …， 就是直接抱住了这一层、跳过上面全部。项目小的时候这么干最快； 一旦文件多了、要跨平台了，才需要上面那几层来管调度。

8等价关系总表

把四层摊平成一张表，「谁和谁是同一个岗位」就一目了然了：

岗位CMake 路线 qmake 路线能不能换
项目描述CMakeLists.txt xxx.pro要重写，但语义可以一一对应
生成器cmake qmake能，换的是「谁来翻译」
构建文件build.ninja / Makefile / .sln+.vcxproj 同上三种能，而且同一个生成器就能产出三种
构建引擎Ninja / GNU Make / MSBuild 同上能，但它必须认得第 3 层给的文件
编译器驱动g++ / cl.exe 同上能，但整条链必须统一（见常见错误 5）
同一层可以换人，跨层不能跳过。
Ninja 不能直接吃 CMakeLists.txt；MSBuild 也不认识 .pro。 每一层只认它上面那一层的产物 —— 这正是图上箭头只在相邻层之间连的原因。

9流程控制：一次构建到底怎么走

从零开始

  1. 生成：cmake -S . -B build -G Ninja → 读 CMakeLists.txt，写 build/build.ninja。 这一步不编译任何源码。
  2. 构建：ninja -C build → 读 build.ninja，发现所有目标都过期，于是 g++ … 一条条跑。
  3. 得到 demo.exe。

改了一个 .cpp 之后 —— 增量构建

只把 widget.cpp 的修改时间改一下，再构建： 只重编它一个，然后重链接，另外那个 main.cpp 不动。

Ninja（已核对）
> ninja -C b-ninja
[1/2] Building CXX object CMakeFiles/demo.dir/widget.cpp.obj
[2/2] Linking CXX executable demo.exe
mingw32-make（已核对）
> mingw32-make -C b-make
[ 33%] Building CXX object CMakeFiles/demo.dir/widget.cpp.obj
[100%] Built target demo

三个目标里重做了 1 个（33%）—— 依赖图就是这么省时间的： 它比较「源文件和 .obj 谁新」，只重跑不新鲜的那些。

改了 CMakeLists.txt 却直接构建，会怎样

CMakeLists.txt 变了，构建文件本身还是旧的 —— 引擎照着旧文件跑，等于你的修改没生效。

正确做法：重新跑一次 cmake（或让 IDE 帮你「重新生成」）。 CMake 生成的 Makefile / build.ninja 里有依赖规则盯着这件事， 但手敲命令时容易漏。

10常见错误

错误 1 · 以为 cmake . 就等于编译

它只写构建文件。看到「Build files have been written」别以为编完了， 还要再跑一次引擎。

错误 2 · 在源码目录里直接 cmake

不要这样
> cmake .            ✗ 构建文件全塞进源码树，和 .cpp 混在一起

用 -S . -B build 把产物集中到一个目录。 这样「清干净重来」只要删掉那一个目录。

错误 3 · 换了编译器却没清缓存

CMake 会把第一次检测到的编译器写进 CMakeCache.txt。 换编译器（比如从 MinGW 换 MSVC）却沿用同一个构建目录，会报 「compiler has changed」或直接编出诡异错误。换编译器就换个目录，或删掉缓存。

错误 4 · CMake 的 VS 生成器找不到 Visual Studio

实机报错（已核对，这台机器上真的踩到了）
CMake Error at CMakeLists.txt:2 (project):
  Generator
    Visual Studio 17 2022
  could not find any instance of Visual Studio.

指定实例路径也未必管用：

再试（已核对）
  could not find specified instance of Visual Studio:
    D:/MicrosoftVisualStudio/Community
  The directory exists, but the instance is not known to the Visual Studio
  Installer, and no 'version=' field was given.

意思是：目录在，但它没有登记到 Visual Studio Installer 的实例列表里， CMake 不认。这种情况下换用 -G Ninja + cl， 或者干脆走 qmake -tp vc 生成 .vcxproj 再交给 MSBuild —— 本文第 4 节就是这么绕过去的。

错误 5 · 混用编译器

MinGW 编出来的 .obj 和 MSVC 的 .lib ABI 不兼容， 不能链在一起。整条链必须统一：

选定的编译器生成器 / 引擎搭配
g++（MinGW） -G Ninja / -G "MinGW Makefiles" + mingw32-make
cl.exe（MSVC） -G "Visual Studio …" + MSBuild，或 -G "NMake Makefiles" + nmake

11一页速查

你想干的事命令 / 结论
写项目描述 CMakeLists.txt（新项目）或 xxx.pro（Qt 老项目）
生成构建文件 cmake -S . -B build -G Ninja
看有哪些后端 cmake --help（-G 清单）
构建 ninja -C build / mingw32-make -C build / MSBuild xxx.vcxproj
qmake 出 Makefile qmake xxx.pro
qmake 出 VS 工程 qmake xxx.pro -tp vc
清干净重来 删掉构建目录（b-xxx/），源码树不动
改了 CMakeLists 重跑一次 cmake，别直接构建
本篇要记住的四句话
  1. 四层：项目描述 → 生成器 → 构建文件 → 构建引擎 → 编译器驱动。 只有最后一层在真正编译。
  2. 同一层可以换人：CMake/qmake 换翻译，Ninja/Make/MSBuild 换调度， g++/cl 换编译。换的是实现，不是依赖关系。
  3. 跨层不能跳过：每层只认上一层给的东西。
  4. 构建文件可再生：它不该进源码树，删了能重建； 但你手写的那份项目描述要进版本库。
