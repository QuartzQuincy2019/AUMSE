阅读提示

建议在学习完 C++ 课本的「类继承」之后学习本章 —— 本篇要用到 public 继承、纯虚函数和 virtual 析构。

Q04 讲过：接口是「对外承诺能做的事」。这一篇讲一个更要紧的问题 —— 这个承诺该有多大。

1先看一个「胖接口」

还是那个 Actor。把它的能力抽成接口，很自然会写成一大块：

IActor.h —— 什么都能干复制
class IActor {
public:
    virtual ~IActor() {}

    virtual int  getHp() const = 0;      // 读血量
    virtual void attack() = 0;           // 攻击
    virtual void defend() = 0;           // 防御
    virtual void buyItem() = 0;          // 买东西
    virtual void changeMap() = 0;        // 换地图
    virtual void save() = 0;             // 存档
};

看起来挺整齐。但把它交给不同的人用，问题就出来了：

谁在用它其实只需要 可是它不得不
血条 UIgetHp 也看得见 attack / buyItem / save —— 还得跟着这份头文件一起编译
商店系统buyItem 也看得见战斗和存档
写测试的人只想测 getHp 得先造一个把 6 个方法全实现的假对象
问题出在哪

不是「接口写错了」，而是 接口太胖 —— 它把好几个不相干的能力捆成了一份承诺。

结果：只想用其中一条的人，被迫接受全部。

2接口隔离原则

一句话

调用方不应该被迫依赖它用不到的方法。

换句话说：接口要按「谁来用」切，不要按「谁来实现」堆。

宁可多几个小接口，也不要一个大而全的。

注意它约束的是接口，不是类。实现者可以同时实现好几个接口， 但每个调用方只看到它要的那一个。

3按调用方拆开

把上面那个胖接口按「谁来用」切：

拆成三个小接口复制
// 只管「血量」—— 血条 UI 要的就是这个
class IHealth {
public:
    virtual ~IHealth() {}
    virtual int getHp() const = 0;
};

// 只管「打」—— 战斗系统要的
class ICombat {
public:
    virtual ~ICombat() {}
    virtual void attack() = 0;
    virtual void defend() = 0;
};

// 只管「买卖」—— 商店系统要的
class IShop {
public:
    virtual ~IShop() {}
    virtual void buyItem() = 0;
};

实现者该实现的都实现 —— 多继承接口，这正是它最正当的用法：

Actor 同时实现三个复制
#include <cstdio>

class Actor : public IHealth, public ICombat, public IShop {
public:
    int getHp() const override { return hp_; }
    void attack() override { printf("Actor 攻击\n"); }
    void defend() override { printf("Actor 防御\n"); }
    void buyItem() override { printf("Actor 购买\n"); }

private:
    int hp_ = 100;
};

而每个调用方只拿它需要的那一个接口：

调用方的参数类型收窄到小接口复制
// 血条 UI：只要 IHealth，根本不知道 Actor 还会打架
void drawHpBar(const IHealth& h) {
    printf("[HP %d]\n", h.getHp());
}

// 战斗流程：只要 ICombat
void runTurn(ICombat& c) {
    c.attack();
    c.defend();
}

int main() {
    Actor a;
    drawHpBar(a);   // Actor 同时也是 IHealth
    runTurn(a);     // 同时也是 ICombat
    return 0;
}
运行结果
[HP 100]
Actor 攻击
Actor 防御
这一拆换来了什么

drawHpBar 的签名是 const IHealth& —— 它在类型上就保证了自己碰不到 attack／buyItem。

这比「约定别乱调」强得多：写错了编译不过，而不是等到运行时出问题。

4拆到什么程度为止

接口隔离不等于「一个方法一个接口」。切分的标准是调用方：

该拆不该拆
两个方法被不同的系统用 两个方法总是一起被同一处调用
一个调用方只用到一半 所有调用方都用到全部
出现「为了编译过而写空实现」 实现得都挺实在
一个很灵的判断信号

如果你为了实现某个接口，写出了 void attack() override {}（空函数）或 { return 0; }（随便糊一个）， 那就是这个接口太胖了 —— 它逼你实现了用不到的东西。

别拆过头

getHp 和 getMaxHp 总是成对出现、总被同一处用 —— 把它们拆成两个接口只会让人多点两次、多传一个参数。

标准始终是那一条：有没有一个调用方被迫依赖它用不到的方法？ 没有就别拆。

5一页速查

接口隔离原则：调用方不应该被迫依赖它用不到的方法。
切分标准：按「谁来用」切，不按「谁来实现」堆。
手法：胖接口 → 几个小接口；实现者多继承它们，调用方只拿需要的那一个。
信号：写出空的 override，就说明接口太胖了。
边界：没有调用方被迫多依赖，就别拆。
