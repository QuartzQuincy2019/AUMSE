Q04 讲过：接口就是这个类对外公开的那几个函数。这一篇只讲一件事 —— 这几个函数，越少越好。

1先看一个具体的小问题

假设有个人要给游戏写血条 UI。它需要的东西只有一样： 角色现在还剩多少血。

于是他 #include "Actor.h"，看到的公开函数是这样一份清单：

Actor.h —— 血条 UI 拿到的是这份复制
class Actor {
public:
    int  getHp() const;      // ← 血条 UI 只用这一个

    void setMaxHp(int v);
    void changeMap(int id);
    void attack();
    void buyItem(int id);
    void save();
    // …… 还有十几个
};

它只要 1 个，拿到手的却是一整份。

这有什么不好

不是「看着乱」，而是三笔具体的账：

① 看得见的，都是「可以调的」

attack 在 public 区 —— 编译器不会阻止血条 UI 调它。

写 UI 的人顺手就写了 actor.attack();。 过一阵，一个纯显示的血条里，长出了战斗逻辑。 没有人违规，因为没有规矩可违。

② 改别人的函数，你也得跟着重编

战斗组把 attack 的签名改了 → Actor.h 变了 → 所有 #include "Actor.h" 的文件都要重新编译， 包括血条 UI —— 虽然它一行战斗代码都没写。

③ 测别人的函数，你也得跟着测

血条 UI 一旦用过 attack，测血条就得同时把战斗也搭起来。 本来一个纯显示的小东西，变成了要拖着半个游戏才能测。

所以「被迫依赖」到底指什么

指的不是「你调用了它」，而是 —— 你明明没打算用它，却不得不跟它打交道：

环节你要为那十几个用不到的函数
读代码把它们的声明都读一遍，才敢确认「哪个是我要的」
编译它们一改，你就要重编
判断它们摆在那里，就在引诱你顺手用
测试你一旦用了，就得连带测它们

这就是「只想用其中一条，却被迫接受全部」里那个「全部」—— 全部公开函数；「接受」——你什么都没做，它们就已经挂在你要用的类型上了。

2把接口做小：接口隔离原则（ISP）

上面三笔账，病根只有一个：这个类公开的东西太多了。

五个字

把接口做小。

一个类对外公开的函数，应该只剩调用方真正要用的那几个。

正式的说法是接口隔离原则（ISP）：调用方不应该被迫依赖它用不到的函数。

做小了，是什么样没做小，是什么样
血条 UI 的类型上只有 getHp 血条 UI 的类型上有 getHp 和十几个别的
想调 attack？根本不存在 想调就调，谁也拦不住
战斗代码改了，血条 UI 不用重编 战斗代码改了，血条 UI 跟着重编
一句话抓住它

不是「类和类之间别耦合」，而是「你面前这个类型上，别摆我用不着的东西」。

考量的单位是调用方：它能看见多少，只该由它要做什么决定。

3怎么拆：按「谁来用」

做法很直接：把公开函数按「谁来用」分成几组，每组做成一个小的能力类。

上面那份清单，按使用方分是这样三组：

谁来用它要用哪几个 分成一组叫
血条 UI / 界面getHp、setMaxHp Health
战斗系统attack、defend Combat
商店 / 背包buyItem、sellItem Shop

每组的公开函数只剩自己那一小块：

三块能力，各自只公开自己的函数复制
class Health {
public:
    int  getHp() const { return hp_; }
    void setMaxHp(int v) { maxHp_ = (v < 1) ? 1 : v; }
private:
    int hp_ = 100;
    int maxHp_ = 100;
};

class Combat {
public:
    void attack() { printf("攻击\n"); }
    void defend() { printf("防御\n"); }
};

class Shop {
public:
    void buyItem(int id) { printf("买 %d\n", id); }
    void sellItem(int id) { printf("卖 %d\n", id); }
};

Actor 自己不再公开这些函数，只负责把三块交出去：

Actor 只做组合，自己一个新函数都不加复制
class Actor {
public:
    Health& health() { return health_; }
    Combat& combat() { return combat_; }
    Shop&   shop()   { return shop_; }

private:
    Health health_;
    Combat combat_;
    Shop   shop_;
};

于是调用方各自只拿它那一块：

血条 UI 的参数类型就是 Health复制
// 血条 UI：参数写 Health，它在这个类型上找不到 attack
void drawHpBar(const Health& h) {
    printf("[HP %d]\n", h.getHp());
}

int main() {
    Actor a;
    drawHpBar(a.health());    // 只交出健康那一块
    a.combat().attack();      // 战斗那块另找它要
    return 0;
}
运行结果
[HP 100]
攻击
注意这一步的关键

drawHpBar 的参数类型是 const Health&。 在这个类型上，压根没有 attack 这个名字 —— 不是「说好别调」，是写出来编译器就报错。

规矩从「口头约定」变成了「类型上做不到」。

4做小之后，三笔账都消了

回到第 1 节那三笔账，逐条对一遍：

原来的账现在还欠不欠
① 看得见的都能调 不欠 —— 血条 UI 只看得见 Health， 那上面没有 attack，想调也没有
② 改别人的函数要跟着重编 不欠 —— Combat 改了，只有战斗相关的东西要重编
③ 测别人的函数要跟着测 不欠 —— 测血条就只需要一个 Health 对象

另外还多出来两样好处：

每块都小 Health 只有两个函数，一眼能看完， 不用翻到第五屏才知道它到底会干什么
可以单独测 造一个 Health 就能测血量逻辑， 不需要先造出整个角色、商店、地图

5小到什么程度为止

「做小」不等于「一个函数一个类」。切分的标准是调用方：

该拆不该拆
这些函数被不同的人用 这些函数总被同一处一起调用
某个调用方只用得到其中一部分 所有调用方都要用到全部
一组函数改了，另一组的使用者也会被牵连 它们本来就是一回事，改总是一起动
一个很灵的自查信号

盯着一个类的公开函数清单，问一句：「这里面有多少个，跟我现在这个场景无关？」

如果答案是「一半以上」—— 那就该拆了。 如果只无关一两个，说明还没到非拆不可的地步。

别拆过头

getHp 和 getMaxHp 总是成对出现、总被同一处用 —— 把它们拆成两个类只会让人多绕一圈、多传一个参数。

标准始终是那一条：有没有一个调用方，被迫依赖了它用不到的函数？ 没有就别拆。

6一页速查

核心五个字：把接口做小。
接口隔离原则（ISP）：调用方不应该被迫依赖它用不到的函数。
「被迫依赖」指：你没打算用它，但它挂在你的类型上 —— 要读、要编、会被引诱去调、用了还得跟着测。
怎么拆：按「谁来用」把公开函数分组，每组做成一个小能力类； 外面按需交出那一组。
好处：调不到不该调的、改别人不牵连、每块都小到能一眼看完。
边界：没有调用方被迫多依赖，就别拆。
