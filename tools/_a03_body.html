C++ Qt 编辑器架构 增量渲染

A01 讲整形，A02 讲落笔。两篇合起来解决了「一个字怎么画」。 本篇往上走一层：一整篇文档怎么画，以及改一个字之后怎么只重画该画的那一块。

画
把字形变成像素
写上去
擦
用背景色抹掉旧像素
擦干净

一篇 17 节的文章，说到底就这两个字。

全篇摘要：绕不开「画」和「擦」

屏幕是有记忆的 —— 你画上去的东西不会自己消失，必须有人擦。 于是编辑器在屏幕上永远只做两件事：画上去、把旧的擦掉。

整篇 17 节，其实只在回答四个问题：

问题落在哪个字 在哪几节
凭什么必须擦？擦 第 3–5 节：屏幕有记忆 → 残影 → 脏矩形
怎样少画？画 第 6–9 节：全量太贵 → 缓存 → 按内容建键 → 局部坐标
画成什么样？画 第 10–13 节：簇 → 钳制 → 分段 → 映射
擦画多大一块？擦 + 画 第 14–15 节：扩张 → 三个范围 → 脏矩形 = 旧 ∪ 新

第 16 节把这条流程串一遍（3000 段的文档删一个字母）， 第 17–18 节回头交代：每个角色是几样功能买来的，以及理解时最容易偏在哪。

本篇的路子

不从术语开始 —— 从最笨的编辑器开始。

先看 Notepad 是怎么把字画在屏幕上的（第 1–5 节）， 再看不做增量会付出什么代价（第 6–9 节）， 最后才是蒙文特有的东西：簇、钳制、分段、映射、扩张（第 10–15 节）。

顺序很重要：先有「擦和写」的直觉，才看得懂「增量」要解决什么； 先知道「重画整屏很贵」，才明白为什么需要那么多记账。

1一个能用的编辑器只要三件事

Notepad 那一级的文本编辑器，骨架只有三个角色：

角色回答什么问题数据
存储文档里有哪些字符一块字符数组
排版哪个字放在屏幕的哪个位置行号 + 行内偏移
绘制把字形画成像素调 GDI / Qt 的画字接口

没有属性表、没有撤销栈、没有缓存 —— 因为 Notepad 不需要。 它的字体是全局的一种，格式根本不存在。

2懒惰：不读全、不排全、不画全

你以为 Notepad 打开几百万字的《三体》时，会把所有字都给你抄一遍？

不会。它连「把所有字读进内存」这一步都懒得做满。真正被处理的永远只有 当前那一屏需要的东西 —— 这就是惰性（lazy）。

三层懒惰，一层比一层省
层懒在哪儿 不懒会怎样
懒得读文件不整块读进内存，按需分块 打开一亿字的文件要等几秒、吃几百 MB 内存
懒得排只排可见的那一屏，其余段落不碰 打开 3000 段的文档，先排 3000 段再说 → 白屏
懒得画只画脏矩形，其余像素直接复用 每敲一个键重画整屏 → 打字卡顿

三层是独立的：可以只做其中一层，也可以三层都做。 本篇的主角是第三层（懒得画），但前两层会一直出现 —— 因为它们是「只处理一屏」这个前提的来源。

「懒惰」这个说法不是修辞。这三层的共同点只有一句： 只处理当前需要的那一小块，剩下的假装不存在。

懒惰的代价，是记账

懒省下来的是时间，付出去的是记录：你得记住哪些已经算过（缓存）、 哪些过期了（脏矩形）、哪些还没算（未排版区域）。

后面十几节讲的全是这本账。不肯记账的懒，就是 bug。

3屏幕是有记忆的

这是本篇最重要的一句话，后面所有东西都从它推出来：

绘制不是「重新生成屏幕」，是「往已有的像素上盖」

你以为的：屏幕 = 我这次画的东西
实际的：屏幕 = 上次画的 + 这次画的（叠在一起）

屏幕不会自己忘事。上一次画上去的像素，会一直待在那里， 直到有人主动用背景色把它涂掉。

所以「画」这个动作在那个循环里其实是两步：

擦　用背景色涂掉一块矩形 —— 让那块回到「空白」
　　↓
写　把新的字形画上去

少掉「擦」这一步，就会出事。

4残影——汉字是狗，越描越丑

屏幕上画着一个蒙文词，五个字形：

删之前：屏幕上的像素x: 0 31 68 107 161 185.6 ┌────┐ ┌────┐ ┌────┐ ┌──────┐ ┌────┐ │ ᠮ │ │ ᠣ │ │ ᠩ │ │ ᠭᠣ │ │ ᠯ │ └────┘ └────┘ └────┘ └──────┘ └────┘

用户删掉最后一个字母。整形结果变成四个字形，而且第 4 个字形变窄了 （从「词中形」变成「词尾形」，53.62 → 44.92）。

只画新内容、不擦旧内容 —— 屏幕上会是这样x: 0 31 68 107 152.4 185.6 ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐ │ ᠮ │ │ ᠣ │ │ ᠩ │ │ ᠭᠣ │ │ ᠯ │ ← 旧的 ᠯ 没被擦掉 └────┘ └────┘ └────┘ └────┘ └────┘ ↑ 152.4~161 这段旧墨迹也留着

用户看到的是：「删了，但那个字母还在」。这就是残影。

「字是黑狗，越描越丑」

老话说字是黑狗，越描越丑 —— 写坏了一个字，你要是拿笔去描， 只会越描越黑、越描越糊，最后连原来那个字都认不出来。

残影的手感一模一样。屏幕上那层旧墨迹没人擦，新的字形又压上去， 两层笔画叠在一起：竖画变粗、拐角发毛、两个字形像长了四只眼睛。 它不是「少画了一个字」这种干净的错，而是脏的错。

这也是为什么这个问题必须从根上治：擦掉重画是干净的一笔， 在旧墨迹上再描一遍，永远描不回来。

所以修残影的思路不是「画得更准」，而是先擦。 擦这件事看起来笨，但它把状态归零了 —— 归零之后画的每一笔都是新的。

每个人都见过的一种残影

文本光标。光标从位置 A 移到位置 B，如果只画新光标、不擦旧光标， 屏幕上就会出现两个光标。老式远程桌面里那种「一排光标」就是这么来的。

5脏矩形：把「该擦哪儿」记下来

既然擦是必须的，那就要知道擦哪儿。这个信息有个通用名字：

脏矩形（dirty rectangle）

脏 = 我在这块地方画过东西，但现在不敢保证它还是对的。
矩形 = 它是一块屏幕区域，用四个数表示：左、上、宽、高。

它是给绘制器的指令：这块先清空，再重画。

这不是 Office 的发明，是 GUI 的通用机制。Windows 的 WM_PAINT 消息传给你的 ps.rcPaint 就是一个脏矩形 —— 系统直接告诉你「这块过期了，你重画它」。

为什么要「攒」

用户连敲 5 个键，会产生 5 个脏矩形。如果每个键都立刻重画：

键1 ▓ 键2 ▓ 键3 ▓▓ 键4 ▓ 键5 ▓ ↓ 绘制帧到了，合并成包围盒 ▓▓▓ ← 只重画一次

合并 = 取它们的包围盒。五次编辑，一次重绘。

6全量重排——计算机也讨厌肉鸽游戏

肉鸽游戏的核心规则：死了一次，从头再来

肉鸽（roguelike）这类游戏有一条铁律：角色一死，进度清零，从第一关重打。 没有存档、没有继承，上一局的一切都不算数。

玩家讨厌它，因为每一局的前半段都在重复做同一件事。

全量重排就是技术版的肉鸽。用户只改了一个字， 引擎却把整篇文档当作一局新游戏：从第一个字符开始重新整形、重新断行、重新算坐标。 上一帧算出来的 3000 段结果，一个都不继承。

所以「增量」这件事，说白了就是给重排加个存档： 上一局算过的东西留着，这一局只重打改动的那一小段。

到这里为止都没问题 —— 只要文档小。文档一大，账就不一样了。

文档规模每帧做什么代价
一屏几十行（Notepad）重画可见区不到 1 ms，随便画
3000 段、60 万码位全部重排3000 × 200 µs ≈ 600 ms
同上只重排 1 段 + 平移0.2 ms + 0.05 ms ≈ 0.25 ms

差三个数量级。600 ms 意味着每敲一个键卡半秒。

Notepad 为什么可以整屏重画

因为它一屏只有几十行、纯文本推进几乎免费，而且没有整形—— 不需要问 HarfBuzz「这几个字合成哪个字形」。

一旦加上「格式」「蒙文连写」「竖排」「撤销」，每条便宜路都被堵死， 就不得不做增量。

7缓存：什么能存，什么不能存

要增量，就得把上次算的结果留着。这份留着的东西叫缓存。

判断标准只有一条：能不能从真值重新算出来
东西能重算吗所以是
文本、属性不能（用户输入的唯一来源）真值
字形序列能（喂给 HarfBuzz 就有了）缓存
每个字形的屏幕坐标能（按 advance 累加）缓存
簇边界的位置表能（从布局里查）缓存

关键性质：把所有缓存删掉，程序结果必须完全一样，只是变慢。 做不到这一点，说明有东西被错当成了缓存。

8缓存按什么建键

这一条决定了缓存的命中率，也决定了「撤销要不要重算」。

整形缓存的键
键 = { 字体族, script, 语言, 方向, 特征集, 词文本 }
值 = 5 个字形（字形号 + 推进量）

注意：键里没有「文档偏移」这一项。

因为它回答的问题是「这个词长什么样」，而不是「第 3000 号位置长什么样」。 位置不在问题里，自然也不在答案里。

场景位置命中？
在另一个位置输入同一个词变了✅ 命中
删掉后撤销回来了✅ 命中，零整形开销
文档里本来就有 200 处同一个词各不相同✅ 只存一条
反例：如果按位置建键

3000 行的文档，在第 1 行插入一个字符 —— 后面所有位置都变了， 3000 条缓存全部失效，整篇重排。

这叫位置漂移。任何按偏移量建的缓存，都会被「在前面插一个字」整体打穿。

9局部坐标 + 原点

还有一个让「只重排一段」成立的前提：不要存绝对坐标。

存法前面插入一个字符时
每个字形存绝对 y3000 段全部要改 → 等于全量重排
每段存原点 + 段内局部坐标只改原点偏移 → 一次加法

所以第 1 行插入一个字、行高增加 20px 之后：

第 1 行 内部布局重排 + 高度 112 → 132 第 2 行 内部布局不动，原点 y += 20 第 3 行 内部布局不动，原点 y += 20 ... 第 3000 行 内部布局不动，原点 y += 20

2999 行的内部布局一个字节都不用动，只是整体下移了 20px。 「重排」只有一行，「平移」是全体 —— 而平移便宜到可以忽略。

10蒙文让这件事变难：簇

到这里，前面说的都是任何编辑器都有的东西。蒙文从这一节开始插进来。

屏幕上这个词 ᠮᠣᠩᠭᠣᠯ 有 6 个码位，但只有 5 个字形：

字形推进量码位说明
u182E.M.init31.480词首
u1823.O.medi36.671词中
u1829.AG.medi39.302词中
u182D_u1823.GO.medi53.623（吃掉 4） GA + O 合成一个字形
u182F.L.fina24.525词尾
码位 4 是没有光标位置的

第 4 个字形占了两个码位（3 和 4）。所以码位 4 不是合法的插入点 —— 它在一个不可分的单位内部。

这个单位叫簇（cluster）。手册的定义是 「a sequence of codepoints that must be treated as an indivisible unit」。

于是编辑器多了一条硬规则：

命令删多少
退格一簇（可能是两个码位）
方向键一簇（从 3 直接跳到 5，跳过 4）
选区端点只能落在簇边界上
复制簇对应的原始码位，不是字形

11删掉半个字符行不彳——钳制

行不彳

「行」这个字，拆开是「彳」加「亍」。 你要把「行」删掉一半，剩下的是一个「彳」—— 它不是一个字，是一个残件。

所以「删掉半个字符行不行」这个问题，答案是个双关：行不彳。

蒙文的簇就是同一个道理：GA 和 O 合成一个字形， 你要是允许只删其中的 O，剩下的 GA 就变成了那个「彳」—— 排版引擎拿到它，会自己去补一个连接符把空档填上， 看起来还连着，其实文本已经是一串谁也没打算写的字符。

钳制（clamp）

把编辑位置对齐到合法边界。合法边界 = 簇边界。

它回答的问题：这次改动改得对不对。

用户能给出的位置是任意的（鼠标点击、拖选、程序调用），但合法插入点只有簇边界。 钳制就是那道校正 —— 而且它往哪边钳取决于语义：

操作钳制方向
点击定位看点落在簇的前半还是后半
退格钳到簇的起点
Delete钳到簇的终点
拖选两端都外扩到簇边界（不能只选半个）

不钳制会怎样：实测

假设实现偷懒，退格老实删一个码位 —— 从 ᠮᠣᠩᠭᠣᠯ 里只删掉 O（第二个码位）， 留下 GA 后面直接跟 L：

整形结果（noto sans mongolian，64px）
u182E.M.init      31.48
u1823.O.medi      36.67
u1829.AG.medi     39.30
u182D.G.medi      21.12
nirugu.extend     10.75      ← 字体自己插进来的连接符
u182F.L.fina      24.52
总宽             163.84

那个 nirugu.extend 是字体在 GA 和 L 之间 自己补的一个长连接符。它看起来「还连着」，但文本已经变成一串谁也没打算写的字符。

用户下次复制这段、或者换一支字体，问题就会暴露出来。

12分段：所有合法边界的唯一来源

分段器（segmenter）

给定一段文本和属性表，输出哪些位置是边界： 簇边界、词边界、整形单元边界、绘制单元边界。

它是唯一有权说「这里要断开」的地方。别人只许读，不许自己算。

为什么必须唯一：如果整形自己判一次、绘制自己判一次、光标自己判一次， 就会有三份边界，而且必然不一致。结果是光标和文字差半个字 —— 这是编辑器里最难查的一类 bug。

它的策略是「尽量不断」

切整形单元会切断整形上下文。实测：把一个词从不同位置切成两段分别整形：

怎么切字形数总推进
整词一个 run511878
在 3\|4 之间切615405
每码位一个 run619701（+66%）

最后一行说明：切到最后，连写全没了，宽度涨了三分之二。

所以分段器的规则是：整形属性不同才切，词内其他情况一律不切。

13有了它，我马上就到你家门口——映射

「有了它，我马上就到你家门口」

快递员能上门，不是因为他认得你，而是因为他手上有一张地址表： 名字 ↔ 门牌号，两个方向都能查。给他名字，他能找到门；给他门牌，他能说出是谁。

映射器干的就是这件事，只不过两边换成了屏幕像素与码位： 你点屏幕上一个位置，它告诉你那是第几个字； 你说第几个字，它告诉你该把光标画在哪儿。

而且和地址表一样，它必须两个方向都对得上 —— 只认门牌不认人，或者只认人不认门牌，都不叫地址表。

映射器（mapper）

三个坐标系之间的双向翻译：模型（码位偏移）、簇（字素序号）、 视觉（行 + 像素）。

它回答两个方向的问题：这个像素点是哪个字（命中测试）和 这个字画在哪儿（光标几何）。

方法方向用在哪
hitTest(点)像素 → 码位鼠标点击、拖选
caretRect(码位)码位 → 像素画光标、滚到光标处

两个方向必须互逆：任意落在字上的点，hitTest 之后再 caretRect，必须回到附近。这是它唯一有效的验收测试。

映射器绝不自己算布局

它必须去问排版器要几何。否则就会出现两套坐标，光标和文字错开 —— 看起来「差一点点」，查起来要命。

14扩张：从「改了哪儿」到「重算多少」

扩张（expand）

把重算范围从「改动的范围」放大到「整形上下文的范围」，也就是整个词。

它不改「改哪儿」，只改「算多少」。往大处放。

为什么必须放大：删末尾，前面的字会变

回到第 10 节那个词 ᠮᠣᠩᠭᠣᠯ（6 个码位 / 5 个字形，64px 下总宽 185.59），删掉末尾的 ᠯ —— 改动范围只有一个码位：

删之前删之后
倒数第二个字形GO.medi 宽 53.62 GO.fina 宽 44.92
总宽185.59152.37

用户只删了末尾一个字母，倒数第二个字母的字形却变了 —— 因为它现在成了词尾。

如果只按改动范围重算

只让最后一个字形失效：第 5 个字消失了，但第 4 个还是旧的 medi（宽度 53.62）。

屏幕上：「删了一个字，但前一个字看起来怪怪的」。 这种 bug 极难查，因为它是「差一点」而不是「明显坏了」。

插入方向也一样：改一处，后面全变

删除会让前面的字变形；插入会让后面的字变形。 在同一个词的中间插入一个码位，它右边所有字形的取值都要重新决定 —— 因为「谁现在是词首、谁现在是词尾」变了。

这就是为什么扩张的范围不能是「插入点」， 而必须是「整个整形上下文」—— 也就是那个词。

最狠的一种：粘贴把两个词缝成一个

前面说的都是词内部的改动。粘贴不一样：它可能把两个词连成一个新词。

内容字形数总宽
一个词 ᠮᠣᠩᠭᠣᠯ5185.59
两个词直接拼接（粘贴的结果）10351.52
两个词用空格隔开11387.82

两个词各 185.59，加起来应该是 371.18，实际只有 351.52 —— 少了 19.66。 因为接缝处那两个字母换了形态：

拼接后接缝处发生的事
原来的词尾 ᠯ    u182F.L.fina    24.52
拼接后在中间 →   u182F.L.medi    18.17      ← 不再是词尾了

原来的词首 ᠮ    u182E.M.init    31.48
拼接后在中间 →   u182E.M.medi    18.17      ← 不再是词首了

更极端的是「粘到半个词中间」：前半个词末尾的 ᠩ 会和粘进来的 ᠮ 合成一个跨粘贴边界的连字 ——

前 3 个码位 + 整个词，共 9 个码位
u1829_u182E.AGM.medi   54.91    ← 这个连字在粘贴前两边都不存在
所以粘贴的重算范围是整个「合并后的新词」

不是粘贴进来的那一段，也不是「粘贴点附近」。 只要粘贴让两个词接上了，它们就成了一个词，整段都要重算。

这也是为什么「粘贴」在编辑器里总是一个大动作： 它不只改文本，还会改变词边界。

边界到底在哪：谁切断连写，谁就是边界

扩张要扩到「词」，那就得知道词在哪儿结束。判据只有一条：

能让连写断开的字符，就是词边界。

在蒙文里通常是空格（U+0020）和窄不换行空格（U+202F）。 它们本身不参与连写，所以两侧的字母各自取「词首 / 词尾」形。

反过来：零宽字符不是边界。ZWJ（U+200D）和 NON-JOINER（U+200C）都是零宽，但它们参与连写判断 —— 一个把两边连起来，一个把两边切断，作用正好相反。

屏幕上的表现 留着旧结果：前一个字还是 medi， 或者接缝处还是旧形态 —— 「删了但看着怪」 看不出任何异常
代价 错，而且极难查：它是「差一点」，不是「明显坏了」 慢一点，多算了没变的东西
可接受吗 不可接受 可接受，但要有个上限

所以实现上一律偏保守：宁可多算，不可少算。 极端情况是「整篇作废」——那就退化成全量重排，增量白做了。 所以上限通常按词或段截断，不无限放大。

扩张管范围，缓存键管对错

这里有个容易混的地方：既然缓存是按内容建键的（第 8 节）， 那文本一变，键就变了，自然未命中 —— 好像根本不需要扩张。

两件事要分开：

问题谁负责怎么保证
算出来的结果对不对缓存的键 键里含全六个维度，少一个就会「命中」一个错误答案
要重排、重画多少扩张 把改动范围放到词边界，再和可见区求交，得到脏矩形
内存会不会涨爆LRU 淘汰 与对错无关，纯粹是容量管理
一句话分清

键回答「这个答案还能用吗」；扩张回答「哪一块需要重算重画」。

撤销时能零成本命中，是因为键还在；屏幕上没有残影，是因为扩张给够了范围。 两个机制各管一头，不能互相顶替。

15三个范围，和脏矩形的正确算法

一次编辑会产生三个不同的数字，混用任何一个都会出问题：

范围例子用途
改动范围1 个码位① 存储真的改了这么多
重算范围整个词让 ③ 分段器、④ 整形缓存、⑤ 排版器、⑥ 映射器 作废重算
脏矩形一小块像素让绘制器擦这块、重画这块
脏矩形必须覆盖「旧 ∪ 新」

因为旧内容必须被擦掉。只按新内容算范围，旧内容多出来的那一截就会留在屏幕上。

拿 ᠮᠣᠩᠭᠣᠯ 这个词说（64px，从 x = 0 画到 x = 185.59），删掉末尾的 ᠯ 之后：

  • 新内容只有四个字形，画到 152.37 为止
  • 旧内容有五个字形，画到 185.59 为止
  • → 脏矩形必须到 185.59，否则 152.37 ~ 185.59 这一截留下残影

这就是为什么编辑器必须记住「上一帧画了什么」—— 不记就不知道该擦哪里。

18组长的说法

这一节照录项目组长读完前 16 节之后的复述，每条后面附一句校准。 放在正文里而不是别处，是因为这些复述本身就有价值：它们标出了 「第一次读会怎么理解」和「哪里最容易偏」。

组长的原话判定 校准
「用户在实际编辑时以簇为单位，那么编辑器处理命令时也以簇为单位。」 ✅ 对。补一句理由：不是「因为用户觉得一个字母」，而是引擎把簇定义为 indivisible unit。两者恰好重合，所以用起来顺手。
「分段和钳制，返回簇边界，确保不把簇裂开。」 ⚠ 两件事的性质不同：分段产出边界清单（只读地图）， 钳制消费它、改的是参数。
分段是地图，钳制是按地图办事的人 —— 地图不办事，人也画不出地图。
「扩张，返回词边界，用于重新渲染整个词。」 ⚠ 「返回词边界」对；「重新渲染」要改一个字：作废并重算。 扩张的产出是「哪段结果不再可信」，渲染是链条最后一环、被作废引发。
「映射，确定用户要改哪里／哪个字。」 ⚠ 只说了一半。它是双向的： hitTest 是「点 → 字」（改哪里）， caretRect 是「字 → 点」（光标画在哪）。少了后一半，光标画不出来。
「钳制是『删哪些，防止裂开』，扩张是『从哪到哪重新渲染』。」 ✅⚠ 前半全对。后半改成「从哪到哪作废重算」—— 作废先发生，重算按需发生，渲染最后发生。三者不是一件事。
「只重排第一行？2999 行的坐标不需要改变吗？」 ✅ 问到点子上了。要变，但只是原点平移（一次加法，30 ns）， 不是重排（200 µs）。差了三个数量级 —— 前提是存的是局部坐标 + 原点，不是绝对坐标。
「删除是一个码位，但重算是整个词。用户输入时需要整词地输入， 删除时可以逐个字符地删除。」 ✅ 完全正确，而且这正是「四个单位」的核心： 提交按词、失效按词、删除按簇、撤销按事件。混用任何一个都会出问题。
「被作废的词……可能在用户接下来的修改中用到，所以保留，只是暂时不用？」 ⚠ 方向对，用词要改：它不是「失效」，是失去引用。 结果仍然正确（问它同一个词，答案一字不差），只是文档里暂时没有位置指向它。 撤销时键重新出现，直接命中 —— 所以保留是对的，理由是这个。
「本质上就是一个文档渲染器，类似于 notepad.exe 的最基本功能。」 ✅ 对，而且 Notepad 也在用脏矩形 —— Win32 的 WM_PAINT 传的 ps.rcPaint 就是。 差别不在机制，在需要几个角色：Notepad 三个就够， 要做到字符级格式 + 蒙文连写 + 撤销 + 大文档不卡，就要十个。
这九条里，最容易偏的三处
  1. 「分段返回边界」与「钳制返回边界」混成一句 —— 一个是数据源，一个是动作，混起来就说不清谁依赖谁。
  2. 「扩张 = 重新渲染」 —— 渲染是结果，不是它的产出。
  3. 「作废 = 失效」 —— 多数时候只是失去引用，结果还是对的。

这三个偏差有一个共同点：都把「动作」和「结果」说成了一件事。
