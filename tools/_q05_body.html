Q04 讲了接口：数据藏起来，改动走接口函数。那一步做对了。

但接着往下写，很容易滑到一个地方 —— 把所有「角色能做的事」都塞进 Actor 类。

先把话说明白

Q04 里的 Actor 是克制的：只有 三个改名 + 三个上限，一共六个函数，没有任何一行多余的东西。

这一篇要批的不是它，而是它接下来的走向 —— 当「切换地图、攻击、防御、购买物品」这些需求一个个来时， 顺手全加进 Actor 会发生什么。

1一个类是怎么长胖的

这个过程从来不是一次发生的，而是一步一步，每一步看起来都很合理：

阶段来需求了 于是
开始「角色要有名字、血量、攻击力」 一个干净的 Actor
第 1 步「名字要能改」 加 changeName
第 2 步「血量上限要能改」 加 setMaxHp
第 3 步「角色要能换地图」 加 changeMap
第 4 步「角色要能打人」 加 attack
第 5 步「角色要能挨打」 加 defend
第 6 步「要能买东西」 加 buyItem
……技能、背包、组队、交易、任务、聊天 继续加

每一步都只有几行代码，每一步单独看都没问题。 问题是它们加起来的结果：

Actor　一个类，什么都管
改名 / 改上限 / 改地址 —— 属性维护
切换地图 —— 地图系统的事
攻击 / 防御 —— 战斗系统的事
购买物品 —— 经济与背包系统的事
（还在继续长）
这时候的 Actor 已经不是「角色」了

它变成了整个游戏的入口。想知道怎么买东西要去翻 Actor；想知道地图怎么切也要去翻 Actor； 战斗出问题还是去翻 Actor。

一个类的职责越模糊，所有人都会往里面加东西 —— 因为它「反正什么都有」。这是个自我加速的过程。

2开闭原则

一句话

对扩展开放，对修改关闭。

意思是：来了新需求，应该靠「加新东西」来满足， 而不是靠「改老东西」。

这句话听起来像口号。它不是 —— 它是一个 关于「改动会伤到谁」的判断工具，下面两节讲它到底在防什么。

先排除一个误会

「对修改关闭」不是「代码不许改」。 第一次写出来的设计不可能一步到位，改是必然的。

它说的是：一个已经被很多人依赖、已经测过的模块， 应该尽量不再被改。不是禁止改，而是让改动尽量落在 没人依赖的新地方。

★

3为什么它在实际开发里这么重要

这一节是重点。开闭原则值钱的地方，全在「改动的代价」上。

① 改动会波及所有人

Actor 是项目里被依赖最多的类。战斗、背包、地图、 界面、存档，全都在用它。它的每一次改动，都是在 所有人脚下的地面上动土。

而一个「只做自己那件事」的类（比如一个负责算伤害的类）， 改它只影响它自己。这就是差别。

② 改老代码要重新测老功能

这是最容易被低估的一条，也是最贵的。

加新东西改老东西
新代码是新的 → 只需要测新功能 老代码被动过 → 所有用到它的老功能都要重测
出问题 → 一定在新代码里 出问题 → 可能是这次改坏的，也可能是早就有的
可以两个人同时做两件新事 两个人同时改同一个类 → 冲突、覆盖、互相打架

第二条特别值得记住：在 Actor 里加一个 buyItem，理论上可能弄坏「攻击」，也可能弄坏「存档」 —— 因为它们在同一份代码里，共享同一批成员。你得把那些都重跑一遍。

③ 分支会越堆越多

所有逻辑挤在一个类里，最典型的后果是条件判断层层套：

加一种新道具 → buyItem 里多一个 if
加一种新技能 → attack 里多一个 if
加一种新地图 → changeMap 里多一个 if
过一阵 → 每个函数都是一长串 if / else if / else if …

这就是「对修改开放」的样子：每来一个新东西， 都要回头去改那几个老函数，再往里面插一条分支。 函数越长，改错的概率越高。

④ 编译与协作会变慢

成员多的类，改动时牵连的文件也多。往 Actor 里加一个函数， 所有 #include "Actor.h" 的地方都要重新编译。 一个只有几百行的类，能拖慢整个项目的编译时间。

把四条合起来看：开闭原则防的不是「代码不好看」， 而是「每来一个新需求，都要回头动那块所有人都在踩的地面」。 改动越集中、被依赖越多，代价就越高 —— 这才是它在实际开发里重要的真正原因。

4回头看：那些 set / get 和「角色能做的事」

现在可以具体说 Q04 那条路的三个问题了。

问题一：set / get 一多，数据就重新裸露了

Q04 里已经讲过判据：「外面直接改它会不会出问题？」 会 → 放 private + 开接口；不会 → 直接 public。

但很多属性本来就没有规则 —— 敏捷、幸运、防御力， 改它不会出任何问题。给这种属性也配一对 setAgi / getAgi，等于：

表面 数据是 private 的，看起来封装得很好
实际 外面照样能随便改名、随便读 —— 只是多绕了一层函数
代价 类的接口区被几十个 set / get 淹没， 真正有规则的那几个（比如 setMaxHp）反而被埋住了

接口的价值在于「这少数几个口子有讲究」， 不在于「口子多」。口子一多，读者就分不出哪个是有规矩的。

问题二：把「角色是什么」和「角色能做什么」混在一起

Actor 本来负责的是状态： 我叫什么、我有多少血、我在哪。这是「角色是什么」。

而攻击、防御、买物品是行为：它们要跟别的对象打交道 —— 打谁？买什么？钱从哪来？地图怎么切？这些都需要 别的系统参与。这是「角色能做什么」。

混在一起的后果

Actor 为了能「攻击」，就得知道伤害公式； 为了能「买东西」，就得知道价格表和背包； 为了能「换地图」，就得知道地图数据结构。

于是这个类开始 #include 越来越多的头文件， 依赖越铺越广。最后它谁也离不开，谁也都离不开它。

问题三：每加一种新东西，都得回来改它

这正是开闭原则要防的。加一种新道具要改 buyItem； 加一种新技能要改 attack。而这两个函数在 所有人都在用的那个类里。

一个直接的检验方法：问自己 —— 「加一种新道具，需要改 Actor 吗？」 如果答案是「要」，那就已经违反了开闭原则。

5大致的方向

不写具体代码，先讲清楚往哪走、为什么这么走。

方向一：把「角色能做的事」搬出去

让 Actor 只负责状态，以及状态的规则 （比如血量不许超过上限）。别的都搬到各自的系统里去：

现在塞在 Actor 里 应该归谁
改名字 / 改上限 / 改地址 留在 Actor —— 这就是它自己的状态，且有规则要守
攻击 / 防御 战斗系统：伤害怎么算、谁先出手，是战斗的事
购买物品 商店 / 背包系统：价格、库存、钱够不够，是它们的事
切换地图 地图系统：地图长什么样、怎么走，不该由角色知道

关键在于关系反过来：不是「角色会换地图」， 而是「地图系统把角色挪过去」。 角色只需要知道自己现在在哪，不需要知道地图怎么运作。

方向二：新东西靠「加一个」，不靠「改一处」

这是开闭原则最直接的落地方式。目标很具体：

1出一种新道具 只加一个新的道具定义，不动 Actor、不动商店代码
2出一种新技能 只加一个新的技能定义，不动 Actor、不动战斗代码
3加一张新地图 只加一份新的地图数据，不动 Actor

能不能做到这一步，就是开闭原则做没做到的验收标准。

方向三：用「能力」代替「一堆 set / get」

与其给每个属性配一对读写函数，不如想清楚 这个类对外真正需要暴露的「能力」是什么。

不要 setHp / getHp / setAgi / getAgi / setDef … —— 几十个口子，读者看不出重点
而要 被扣血、被治疗、 升级 —— 每个都是一件完整的事， 规则写在里面，外面看不出实现

这两种写法的区别不在「封装得好不好」， 而在于：前者把内部结构漏给了所有人，后者把「角色能承受什么」表达清楚了。 前者一改内部结构，所有人跟着改；后者不用。

判断一个 set 函数该不该存在

问一句：「这个名字是在描述「一件事」，还是在描述「一个字段」？」

  • setHp —— 一个字段。为什么直接赋值不行？说不出来。
  • 受伤(伤害值) —— 一件事。要扣血、可能致死、可能触发护盾。

是「一件事」就值得开接口；是「一个字段」，而字段又确实可以随便改， 那就直接公开，别包一层。

6目标状态

走完上面三个方向，会得到两个明显的结果：

改造前改造后
新需求 → 改 Actor 新需求 → 加一个新的模块
改 Actor → 要重测战斗、背包、地图、界面、存档 加新模块 → 只测新模块
一个类几百上千行，谁都得读它 每个类只管一件事，改动落在没人依赖的地方
所有人改同一个文件 几个人可以同时各加各的
开闭原则不是一句口号，它可以被验收

就用那一个问题：「加一种新道具 / 新技能 / 新地图， 需要改哪些已有文件？」

答案里没有任何一个「大家都要用」的核心类 —— 那就是做到了。
答案里有 Actor —— 那就是没做到。

7一页速查

三句话

① 对扩展开放，对修改关闭 —— 新需求靠「加新东西」满足，不靠「改老东西」。
② 它防的是「改动波及面」 —— 一个类被依赖越多，改它的代价越大：要重测、要协调、要冒连带风险。
③ 验收标准很具体 —— 「加一种新道具，要不要改 Actor？」要改，就是没做到。

把「角色能做的事」塞进 Actor 的三宗罪

问题具体后果
set / get 泛滥 封装变成走过场：外面照样随便改，只是多绕一层； 真正有规则的那几个接口被埋在几十个字段存取里
状态与行为混在一起 为了能攻击、买东西、换地图，Actor 不得不 #include 伤害公式、价格表、地图结构 —— 依赖越铺越广，谁也离不开谁
每加一种新东西都要回头改它 而它在所有人的脚下 —— 改一处，所有人重测
这一篇的落点

具体怎么把战斗、背包、地图拆出去，涉及 组合与接口两件事 —— 那是接下来的内容。

这一篇只需要记住一件事： 类应该因为「它自己的规则变了」而改， 而不应该因为「游戏多了一种道具」而改。
